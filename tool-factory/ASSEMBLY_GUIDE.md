# 組み立てガイド — AIツールデザインキャンバス方式

ビジネスモデル・キャンバスと同じ発想で、ツールの機能を因数分解した
**7ブロックの「AIツールデザインキャンバス」**に部品を埋めて、新ツールを設計・製造する。

## AIツールデザインキャンバス

新ツールの設計は、コードやプロンプトを書く前に必ずこのキャンバスを埋めることから始める。

```
┌─────────────────────────────────────────────────────────────┐
│ ツール名：                                                    │
│ 一言で何をするツールか：                                        │
├──────────────┬──────────────────────┬──────────────────────┤
│ ① INPUT       │ ③ PROCESS            │ ⑤ OUTPUT             │
│ 入力をどう受け  │ 中核の処理は何か       │ 何をどんな形で出すか   │
│ 取り分岐するか  │                      │                      │
│              │ 部品：               │ 部品：               │
│ 部品：        │                      │                      │
├──────────────┤ ④ DATA               ├──────────────────────┤
│ ② QUALITY     │ 外部データをどう       │ ⑥ INTEGRATION        │
│ 出力の質を何で  │ 取り・貯め・捌くか     │ 他ツール・外部サービス │
│ 担保するか     │                      │ とどう連携するか       │
│              │ 部品：               │                      │
│ 部品：        │                      │ 部品：               │
├──────────────┴──────────────────────┴──────────────────────┤
│ ⑦ SAFETY  何を確認し、何を推定と明示し、どこで止まるか            │
│ 部品：                                                       │
└─────────────────────────────────────────────────────────────┘
```

各ブロックには PARTS_CATALOG.md の部品IDを書く。埋まらないブロックは：
- **不要**（そのツールにその機能が要らない）→「なし」と明記
- **欠品**（必要だが部品がない）→「新造」と書き、製造後に parts/ へ登録

## 既存ツールをキャンバスで表すと（実例）

### keiba-yoso をキャンバス分解

| ブロック | 部品 |
|---|---|
| ① INPUT | mode-detection（レース指定/おまかせの判定） |
| ② QUALITY | ※EVスコア＝案件固有ロジック |
| ③ PROCESS | ※EV計算・レース選定＝案件固有ロジック |
| ④ DATA | web-scraping + file-per-item + auto-parse + diff-cache + screening |
| ⑤ OUTPUT | html-report |
| ⑥ INTEGRATION | notion-task + scheduled-task |
| ⑦ SAFETY | hallucination-guard（実データ主義） |

→ **7ブロック中5ブロックが汎用部品で構成されている。**案件固有なのはEV計算だけ。
これが「同じ部品を何回も作っている」の正体であり、工場が効く理由。

### noe-brain をキャンバス分解

| ブロック | 部品 |
|---|---|
| ① INPUT | mode-detection + context-intake |
| ② QUALITY | branch-table（収益化チェック）+ concreteness-rules + confidence-score |
| ③ PROCESS | ※3型設計＝固有ロジック + stress-test + action-design |
| ④ DATA | なし |
| ⑤ OUTPUT | summary-table + meta-evolution |
| ⑥ INTEGRATION | skill-handoff（→noe-relay） |
| ⑦ SAFETY | hallucination-guard |

## 製造手順

1. **ニーズの一言化**：「誰が・何に困っていて・このツールは何を出すのか」を1行で書く
2. **キャンバスを埋める**：PARTS_CATALOG.md を見ながら7ブロックに部品IDを割り当てる
3. **固有ロジックの特定**：部品で賄えない部分（＝そのツールの独自価値）を明確にする。
   固有ロジックが1つもないなら既存ツールのカスタマイズで済む（新造不要）
4. **SKILL.md を組み立てる**：下のテンプレに部品の組み込みブロックをコピーして埋める
5. **欠品部品の登録**：新造した機能は汎用化して parts/ に追加し、カタログを更新する
6. **試運転→メタ進化**：1回実行して、meta-evolution の改良ポイントを部品側に還元する

## SKILL.md テンプレート

```markdown
---
name: [ツール名（英小文字-ハイフン）]
description: >
  [一言で何をするツールか]。
  [どんな構造の依頼に使うか]。

  以下のキーワードや文脈で必ずこのスキルを使うこと：
  - 「[トリガーワード1]」「[トリガーワード2]」
  - [トリガーとなる依頼の形]
---

# [ツール名]

[ツールの目的を2〜3行で]

## 入力の受け取り
[① INPUT の部品ブロックをここに展開]

## 実行プロセス
[③ PROCESS の部品ブロック＋固有ロジックをSTEP形式でここに展開]

## データ取得（データ系ツールのみ）
[④ DATA の部品ブロックをここに展開]

## 品質ルール
[② QUALITY の部品ブロックをここに展開]

## 出力
[⑤ OUTPUT の部品ブロックをここに展開]

## 連携
[⑥ INTEGRATION の部品ブロックをここに展開]

## 安全ルール
[⑦ SAFETY の部品ブロックをここに展開]
```

## 組み立て時の鉄則

- **部品の組み込みブロックは[角括弧]部分だけ書き換える**。構造を崩すと部品の意味がなくなる
- **description のトリガーワードは具体的に列挙する**（既存スキル群のdescriptionが手本）
- **固有ロジックは全体の3割以下**が目安。それ以上なら因数分解が足りていない
- **1ツール1責務**。キャンバスに収まらない場合は2つのツール＋skill-handoff に分割する
