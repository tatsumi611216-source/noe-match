# ツール発注フォーム — 自動化ヒアリングシート

発注の軸は**「自動化したいこと」**。ユーザーに部品や技術を選ばせない。
作業をブレイクダウンして聞き（ヒアリング）、実現可否を判定してから発注する。
部品選定は工場が裏側で行う。

```
❶ ヒアリング（作業のブレイクダウン）＝ 受付票。これだけでは製造に入らない
   ↓
❷ 実現可否判定（◎そのまま可 ／ ○条件付き可 ／ △要相談＋ネック明示）
   ↓
❸ 追加質問（工場が回答を読み、案件専用の質問を1回にまとめて生成）
   ↓ 対象URL・判断基準の数値・出力項目・完成の定義を確定
❹ 提案書（出力サンプル・スコープ外・検収条件を提示）→ ユーザー承認
   ↓
製造 → 試運転 → 検収（完成の定義を満たすまで）
```

**ヒアリング（❶）は汎用7問のトリアージであり、仕様ではない。**
案件の具体（どのサイトか・基準の数値・出力項目）は❸で確定させる。
汎用フォームに質問を足しても具体は取れない——具体的な質問は回答を読んで初めて作れるからだ。

運用は2ルート：

- **ルートA：Webフォーム**（`order-form.html`）— 回答に連動して実現可否がその場で判定され、
  発注書が自動生成される。コピーしてClaudeに貼るだけ
- **ルートB：Google Form** — 下の質問セットを転記して使う。回答をClaudeに貼れば
  noe-tool-factory が実現可否を判定してから製造する

## ヒアリングシート 質問セット（Google Form転記用）

タイトル：**Noe ツール発注フォーム — 自動化ヒアリングシート**
説明：自動化したい作業について答えてください。実現できるかどうかの判定から始めます。

### Q1. 自動化したいこと〔記述式・必須〕
今は手でやっている（またはやれていない）作業を、そのまま書いてください。
例：毎週、気になる中古物件をサイトで見て回って、良さそうなものをスプレッドシートにメモしている。

### Q2. きっかけ — その作業はいつ始まる？〔ラジオ・必須〕
- 自分が頼んだとき
- 毎日・毎週など決まったタイミング
- 何かが起きた瞬間（メールが来たら即、など）

### Q3. 材料 — 何を見て・何を使う作業？〔チェックボックス〕
- 誰でも見られるWebサイト
- ログインが必要なサイト・アプリ
- Gmail・カレンダー・Notion・Drive
- 手元のファイル（Excel・PDFなど）
- 社内システム・専用ソフト
- 特になし（頭の中の考え・相談ごと）

### Q4. 加工 — その材料に何をしている？〔チェックボックス〕
- 集める・整理する・まとめる
- 決まった基準で選別・計算・判定する
- 文章・資料・レポートを作る
- 案を考える・検証する・意思決定する
- 感覚で判断している（基準をまだ言葉にできない）

### Q5. 成果 — 最後に何がどこにあれば完了？〔チェックボックス〕
- チャットで報告してくれれば良い
- レポート・一覧表になっている
- Notion・スプレッドシート等に記録されている
- メール送信・SNS投稿など外に発信されている

### Q6. 自分の関わり方〔ラジオ〕
- 全部おまかせでいい
- 最後に自分が確認してから確定したい
- 途中の大事な判断は自分がやりたい

### Q7. 頻度と量・補足〔記述式・任意〕
どのくらいの頻度・件数か、判断基準、その他伝えたいこと

## 実現可否の判定基準（工場スキルが正式判定に使う）

| 回答 | 判定 | 理由・条件 |
|---|---|---|
| きっかけ＝頼んだとき／定期 | ○可 | mode-detection ／ scheduled-task で対応 |
| きっかけ＝イベント即時 | ▲条件付き | 「即座」は不安定。短い間隔の定期チェックに置き換える |
| 材料＝公開Webサイト | ○可 | web-scraping 一式で対応 |
| 材料＝ログインが必要なサイト | ▲条件付き | ブラウザ操作で対応。サイトにより不安定な場合あり |
| 材料＝Gmail/カレンダー/Notion/Drive | ○可 | 接続済み |
| 材料＝手元のファイル | ○可 | そのまま読み書き可能 |
| 材料＝社内システム・専用ソフト | ✕要相談 | 直接接続不可。CSV等のエクスポートで「手元ファイル」化できれば可に変わる |
| 加工＝収集/判定/文章/思考 | ○可 | 既存部品＋固有ロジックで対応 |
| 加工＝感覚的判断 | ▲条件付き | 製造前に基準を引き出すヒアリング（context-intake）が必要 |
| 成果＝報告/レポート/記録 | ○可 | secretary-tone ／ html-report ／ notion-task で対応 |
| 成果＝メール送信・投稿 | ▲条件付き | 不可逆操作。直前に本人確認（irreversible-confirm）を必須化 |

**総合判定：**
- ✕が1つでもある → **△要相談**：ネックと代替案を提示して製造前に停止し、ユーザーの判断を仰ぐ
- ▲がある → **○条件付き可**：条件を織り込んで製造に進む
- すべて○ → **◎そのまま可**：製造に進む

## 回答→部品マッピング表（工場が参照。発注者には見せなくてよい）

| ヒアリングの回答 | 割り当て部品 | ブロック |
|---|---|---|
| 頼んだとき起動 | input/mode-detection | ① INPUT |
| 定期・イベント起動 | integration/scheduled-task（＋data/diff-cache） | ⑥／④ |
| 公開Webサイト | data/web-scraping + file-per-item + auto-parse + screening | ④ DATA |
| ログインが必要なサイト | data/web-scraping（find+read_page系） | ④ DATA |
| 基準による選別・計算・判定 | quality/branch-table ＋ 新造（判定ロジック） | ②／③ |
| 案を考える・検証する | process/stress-test + quality/confidence-score | ③／② |
| 感覚的判断の言語化 | input/context-intake | ① INPUT |
| チャット報告 | output/secretary-tone | ⑤ OUTPUT |
| レポート・一覧表 | output/html-report + summary-table | ⑤ OUTPUT |
| Notion等に記録 | integration/notion-task | ⑥ INTEGRATION |
| メール送信・投稿 | safety/irreversible-confirm | ⑦ SAFETY |
| 最後に本人確認／途中判断は本人 | safety/irreversible-confirm ／ quality/branch-table | ⑦／② |
| （全案件共通） | safety/hallucination-guard | ⑦ SAFETY |

**マッピングのルール：**
- 表にない自由記述の要望は、まずカタログ全体から近い部品を探す。なければ新造候補とする
- Q1（自動化したいこと）が空欄・曖昧な場合のみ、製造前に1問だけ確認する
- フォーム経由の発注はキャンバス確認を省略してよい。ただし回答間に矛盾がある場合のみ質問する
