# AIツールデザインキャンバス — 理論と実践

AIツール（エージェント・スキル・自動化ワークフロー）を、
**部品の組み合わせ**として設計するためのフレームワーク。

ビジネスモデル・キャンバスがビジネスを9ブロックに因数分解したように、
AIツールデザインキャンバスはAIツールの機能を**7ブロック**に因数分解する。
本書は前半でキャンバスの理論を説明し、後半で実在するツールをキャンバスで解剖し、
最後に読者が自分のツールを設計できる手順を示す。

---

# 第1部 理論編

## 1. なぜAIツールは「作るたびにゼロから」になるのか

AIツールを2つ3つと作っていくと、必ず同じ現象が起きる。
**前に作ったものと同じ機能を、また最初から書いている。**

これは実際に起きたことだ。ある個人の作業環境には5つのAIツールがあった。
事業仮説を設計するツール、多エージェント討論ツール、競馬予想ツール、
Webデータ収集ツール、個人秘書ツール。用途はバラバラに見える。
ところが中身を分解してみると：

- 「出力の信頼度を採点する仕組み」が2つのツールで**別々に**実装されていた
- 「Webからデータを取るときのルール」がほぼ同じ文章で2箇所に書かれていた
- 「Notionに記録する処理」が2つのツールで別々に書かれていた
- 「抽象論を禁止して具体的に語らせるルール」も2箇所にあった

なぜこうなるのか。**ツールを「1つの完成品」として捉えているから**だ。
完成品単位で作ると、中に含まれる汎用機能が完成品の中に埋没する。
次のツールを作るとき、埋没した機能は取り出せないので、また書く。

解決策は製造業が100年前に通った道と同じ——**部品化と規格化**である。

## 2. 因数分解という考え方

`6x + 9y` という式は `3(2x + 3y)` と書ける。共通因数をくくり出すと、
式の構造が見え、再利用できる形になる。

AIツールも同じだ。一見バラバラな5つのツールから共通因数をくくり出すと、
**21個の部品**が抽出できた。そして重要な発見はこうだ：

> **ツールの7〜8割は汎用部品でできている。**
> **そのツール固有の価値（固有ロジック）は、実は2〜3割しかない。**

競馬予想ツールの固有ロジックは「期待値計算」だけだった。
残り——データの取り方、保存の仕方、レポートの出し方、記録の残し方——は
全部、不動産でも株でもECでも使える汎用部品だった。

因数分解ができれば、逆の操作もできる。**部品を組み合わせて新しいツールを合成する**。
これがキャンバスの役割だ。

## 3. AIツールデザインキャンバス — 7つのブロック

あらゆるAIツールは、次の7つの問いに答えると輪郭が決まる。

```
┌─────────────────────────────────────────────────────┐
│ ツール名／一言定義：誰が・何に困っていて・何を出すか      │
├─────────────┬──────────────────┬──────────────────┤
│ ① INPUT      │ ③ PROCESS        │ ⑤ OUTPUT         │
│ 入力をどう    │ 中核の処理は      │ 何をどんな形で    │
│ 受け取り      │ 何か             │ 出すか           │
│ 分岐するか    │ （固有ロジックの  │                  │
│              │   置き場所）      │                  │
├─────────────┤ ④ DATA           ├──────────────────┤
│ ② QUALITY    │ 外部データを      │ ⑥ INTEGRATION    │
│ 出力の質を    │ どう取り・貯め・  │ 他ツール・外部    │
│ 何で担保      │ 捌くか           │ サービスとどう    │
│ するか        │                  │ つなぐか          │
├─────────────┴──────────────────┴──────────────────┤
│ ⑦ SAFETY 何を確認し、何を推定と明示し、どこで止まるか   │
└─────────────────────────────────────────────────────┘
```

| ブロック | 問い | 代表的な部品 |
|---|---|---|
| ① INPUT | 入力をどう受け取り、分岐するか | モード自動判定／文脈引き出し |
| ② QUALITY | 出力の質を何で担保するか | 具体性強制／数字の裏取り／信頼度採点／合否ゲート |
| ③ PROCESS | 中核の処理は何か | ストレステスト／討論エンジン／アクション設計＋**固有ロジック** |
| ④ DATA | 外部データをどう取り・貯め・捌くか | Web取得／1件1ファイル／自動パース／差分キャッシュ／足切り |
| ⑤ OUTPUT | 何をどんな形で出すか | サマリー表／HTMLレポート／秘書口調／自己改良フッター |
| ⑥ INTEGRATION | 他ツール・外部サービスとどうつなぐか | Notion記録／定期実行／ツール間連携 |
| ⑦ SAFETY | 何を確認し、どこで止まるか | 不可逆操作の確認／推定と事実の区別 |

配置には意味がある。中央の列（PROCESS・DATA）がツールの**エンジンルーム**。
左の列（INPUT・QUALITY）が**入口と検査場**、右の列（OUTPUT・INTEGRATION）が**出口と配送**。
底面のSAFETYは全ブロックを支える**土台**で、どんなツールでも省略しない。

## 4. 部品の3要件

キャンバスのブロックに置く「部品」は、次の3つを備えて初めて部品と呼べる。

1. **名前がある** — `fact-check` `diff-cache` のように短い固有名を持つ。
   名前がないものは呼び出せず、呼び出せないものは再利用されない
2. **機能が明示されている** — 「何をする部品か」が1〜2行で書いてある。
   さらに「組み込みブロック」（コピーして使える実体）と
   「カスタマイズポイント」（どこを書き換えてよいか）が分離されている
3. **カテゴライズされている** — 7ブロックのどこに属すか決まっている。
   所属が決まっているから、設計時に「このブロックに置ける部品はどれか」を一覧できる

この3要件は図書館の蔵書ルールと同じだ。書名（名前）と内容紹介（機能）と
配架場所（カテゴリ）があるから、本は探せて、借りられて、また戻せる。

## 5. 設計の3原則

**原則1：固有ロジックは3割以下。**
キャンバスを埋めたとき、汎用部品で賄えない部分が3割を超えたら、
それは因数分解が足りていないサインだ。要望をもう一段分解すると、
中から汎用部品が見つかる。逆に固有ロジックがゼロなら、
新しいツールは要らない——既存ツールの設定変更で済む。

**原則2：1ツール1責務。**
キャンバス1枚に収まらないツールは、必ず運用が破綻する。
収まらないときは2つのツールに分割し、ツール間連携の部品でつなぐ。
「太った1つ」より「つながった2つ」。

**原則3：新造したら還元する。**
新しいツールのために新しい機能を書いたら、汎用化して部品ライブラリに登録する。
これを怠ると、ライブラリは古びて工場は止まる。逆に守り続けると、
ツールを作れば作るほど次のツールが速く作れるようになる——**逓増する生産性**が生まれる。

# 第2部 実践編 — 実在ツールをキャンバスで解剖する

ここからは、実際に稼働している4つのツールをキャンバスに載せて解剖する。
タイプの違う4例を見ると、キャンバスの使い方が体で分かるはずだ。

## 事例1：keiba-yoso（競馬予想）— データ型ツール

netkeibaから出馬表・オッズ・過去成績を取得し、各馬の期待値
（EV＝推定勝率×オッズ−1）を計算して予想とレポートを出すツール。

| ブロック | 中身 | 汎用／固有 |
|---|---|---|
| ① INPUT | レース指定／おまかせの自動判定 | 汎用 |
| ② QUALITY | EVスコアの足切り基準 | 固有 |
| ③ PROCESS | **EV計算・レース選定** | **固有** |
| ④ DATA | Web取得＋1件1ファイル＋自動パース＋差分キャッシュ＋足切り | 汎用（5部品） |
| ⑤ OUTPUT | HTMLレポート | 汎用 |
| ⑥ INTEGRATION | Notion記録＋定期実行（朝取得・夜突合） | 汎用 |
| ⑦ SAFETY | 実データ主義（推測での回答禁止） | 汎用 |

**読み解き：** 7ブロック中、固有なのは実質1ブロック（EV計算）だけ。
つまりこのツールの「競馬らしさ」はPROCESSに集中していて、
残りは**丸ごと他ドメインに転用できる**。実際、DATAブロックの5部品と
OUTPUT・INTEGRATIONをそのまま使い、PROCESSだけ「割安度計算」に
差し替えれば不動産ツールになる。株でもECでも同じだ。
これがデータ型ツールの典型構造：**DATAが厚く、PROCESSが薄く鋭い。**

## 事例2：noe-brain（事業仮説設計）— 思考型ツール

ユーザーの固有文脈（職歴・失敗体験）から、3つの型（逆張り・接続・除去）で
事業仮説を生成し、テストして72時間アクションまで落とすツール。

| ブロック | 中身 | 汎用／固有 |
|---|---|---|
| ① INPUT | モード判定＋文脈引き出し（質の採点付き） | 汎用（2部品） |
| ② QUALITY | 収益化チェックの合否ゲート＋具体性強制＋信頼度採点 | 汎用（3部品） |
| ③ PROCESS | **3型の問い（逆張り・接続・除去）**＋ストレステスト＋アクション設計 | **固有1**＋汎用2 |
| ④ DATA | なし | — |
| ⑤ OUTPUT | サマリー表＋自己改良フッター | 汎用 |
| ⑥ INTEGRATION | 討論ツール（noe-relay）への引き継ぎ判定と起動コマンド生成 | 汎用 |
| ⑦ SAFETY | 推定前提の明示 | 汎用 |

**読み解き：** 思考型ツールはDATAが空になる代わりに、
**INPUTとQUALITYが厚くなる**。入力（ユーザーの文脈）の質が出力の質を
決めるため、文脈を引き出して採点する部品が必須になる。
また「AIがそれっぽい嘘を言う」リスクが高いジャンルなので、
具体性強制・合否ゲート・信頼度採点と、QUALITYを3枚重ねている。
固有ロジックは「3型の問い」だけ。ここがこのツールの思想であり、代替不可能な核だ。

## 事例3：noe-relay（多エージェント討論）— 検証型ツール

論題に対して討論者2名（懐疑側・肯定側）と審判を自動設計し、
2ラウンドの討論で仮説の穴を外から壊すツール。

| ブロック | 中身 | 汎用／固有 |
|---|---|---|
| ① INPUT | （論題1行を受けるだけ） | — |
| ② QUALITY | 具体性強制＋Web検索での数字裏取り＋信頼度採点 | 汎用（3部品） |
| ③ PROCESS | **討論エンジン**（キャスティング→8ターン→審判介入） | 汎用化済みの核 |
| ④ DATA | なし | — |
| ⑤ OUTPUT | メタサマリー（確定事実・アクションリスト） | 汎用 |
| ⑥ INTEGRATION | （noe-brainから呼ばれる側） | — |
| ⑦ SAFETY | （審判が具体性違反を叩く＝QUALITYが兼務） | — |

**読み解き：** このツールは面白い構造をしている。中核の討論エンジン自体が
**部品として切り出せる**ほど汎用的なのだ。「事業仮説の検証」にも
「投資判断」にも「キャリア相談」にも、論題を変えるだけで使える。
つまりnoe-relayは「ほぼ1つの大きな部品＋品質部品」でできた、
**部品がそのまま製品になった例**。空欄のブロックが多いのは手抜きではなく、
1ツール1責務の徹底——入力も連携も、呼び出す側（noe-brain）に任せている。

## 事例4：secretary（個人秘書）— 定型業務型ツール

予定確認・メール確認・タスク登録を秘書口調でこなすツール。
「宿題:」で始まるメッセージは最優先でNotionに登録する。

| ブロック | 中身 | 汎用／固有 |
|---|---|---|
| ① INPUT | 「宿題:」キーワードの最優先トリガー | 汎用 |
| ② QUALITY | なし | — |
| ③ PROCESS | 依頼の仕分け（予定／メール／タスク） | 固有（小） |
| ④ DATA | なし（接続済みサービスを直接参照） | — |
| ⑤ OUTPUT | 秘書口調・要点先出しの報告フォーマット | 汎用 |
| ⑥ INTEGRATION | Notion登録・更新 | 汎用 |
| ⑦ SAFETY | **不可逆操作（メール送信等）は必ず本人確認** | 汎用 |
| | 下書きまでは自動・送信だけ確認、という線引き | |

**読み解き：** 定型業務型はPROCESSが最も薄い。仕分けて、つないで、報告するだけ。
その代わり**SAFETYが主役**になる。メール送信・予定削除という
「取り返しのつかない操作」を扱うからだ。ここの設計原則は
「準備は自動・実行は確認」——下書き作成は勝手にやってよいが、
送信ボタンだけは人間が押す。この線引きの部品は、
外部に何かを発信するすべてのツールにそのまま移植できる。

## 4事例から見えるパターン

| タイプ | 厚くなるブロック | 固有ロジックの居場所 |
|---|---|---|
| データ型（keiba-yoso） | ④ DATA | スコア計算式 |
| 思考型（noe-brain） | ① INPUT・② QUALITY | 問いの型 |
| 検証型（noe-relay） | ② QUALITY・③ PROCESS | （核自体が汎用部品化） |
| 定型業務型（secretary） | ⑦ SAFETY・⑥ INTEGRATION | 仕分けルール |

**どのタイプでも、固有ロジックは1〜2箇所に集中し、残りは汎用部品で組める。**
これがキャンバスが機能する根拠であり、あなたのツールでも同じことが起きる。

# 第3部 応用編 — 自分のツールを設計する

## 手順1：自動化したいことを1行で書く

技術から考えない。**作業から考える。**

> 「毎週、気になる中古物件をサイトで見て回って、
> 良さそうなものをスプレッドシートにメモしている。これを自動でやりたい」

この1行が書ければ設計の半分は終わっている。書けなければ、
まだツールを作る段階ではない——自動化したい作業を1週間手でやってみて、
手順をメモすることから始める。

## 手順2：作業をブレイクダウンする

1行を、次の5つの問いで分解する。これはヒアリングシートの構造でもある。

1. **きっかけ**：その作業はいつ始まる？（頼んだとき／定期／何かが起きたら）
2. **材料**：何を見て・何を使う？（Webサイト／メール／手元のファイル／頭の中）
3. **加工**：材料に何をしている？（集める／基準で選別する／文章にする／考える）
4. **成果**：最後に何がどこにあれば完了？（報告／レポート／記録／発信）
5. **関与**：自分はどこに関わりたい？（全部おまかせ／最後に確認／途中判断は自分）

先の例なら：きっかけ＝毎週、材料＝公開Webサイト、加工＝基準で選別
（駅徒歩10分以内・相場より1割安い）、成果＝スプレッドシートに記録、
関与＝最後に自分が見る。

## 手順3：実現可否を判定する

作り始める前に、できるかどうかを判定する。基準は単純だ。

| 回答 | 判定 |
|---|---|
| きっかけが「頼んだとき」「定期」 | ○そのまま可 |
| きっかけが「起きた瞬間に即」 | ▲短い間隔の定期チェックに置き換えれば可 |
| 材料が公開Web・接続済みサービス・手元ファイル | ○そのまま可 |
| 材料がログイン必須のサイト | ▲可能だが不安定な場合あり |
| 材料が社内システム・専用ソフト | ✕直接は不可。エクスポートで手元ファイル化できれば可 |
| 加工の基準を言葉にできる | ○そのまま可 |
| 加工が感覚的判断 | ▲基準の言語化から始めれば可 |
| 成果が報告・レポート・記録 | ○そのまま可 |
| 成果が外部への発信（メール送信・投稿） | ▲実行前の本人確認を挟めば可 |

✕が1つでもあれば、代替案を考えてから進む。▲は条件として設計に織り込む。
**この判定を飛ばして作り始めるのが、ツール開発の失敗の最大原因**だ。

## 手順4：キャンバスを埋める

ブレイクダウンの結果は、そのままキャンバスに流し込める。

- きっかけ → **① INPUT**（＋定期なら **⑥ INTEGRATION** の定期実行）
- 材料 → **④ DATA**
- 加工 → **③ PROCESS**（選別基準＝あなたの固有ロジック）と **② QUALITY**（合否ゲート）
- 成果 → **⑤ OUTPUT** と **⑥ INTEGRATION**（記録先）
- 関与 → **⑦ SAFETY**（確認をどこに挟むか）

物件の例を埋めるとこうなる：

| ブロック | 中身 | 出どころ |
|---|---|---|
| ① INPUT | 定期起動（毎週） | きっかけ |
| ② QUALITY | 足切り基準（徒歩10分・相場比▲10%）の合否ゲート | 加工の基準 |
| ③ PROCESS | **割安度スコア計算** ← 固有ロジック | 加工 |
| ④ DATA | Web取得＋1件1ファイル＋差分キャッシュ＋足切り | 材料 |
| ⑤ OUTPUT | 一覧レポート | 成果 |
| ⑥ INTEGRATION | スプレッドシート記録＋毎週の定期実行 | 成果・きっかけ |
| ⑦ SAFETY | 推定値（相場)は推定と明示。問い合わせ送信は本人確認 | 関与 |

気づいただろうか。**これは事例1（競馬予想）とほぼ同じキャンバス**だ。
違うのはPROCESSの計算式だけ。ドメインが違っても構造は同じ——
だからこそ部品が効く。

## 手順5：埋まらないブロックの扱い

- **「なし」で埋まる**：そのツールに不要な機能。空欄は手抜きではなく設計判断
  （事例3のnoe-relayを思い出してほしい）
- **「新造」で埋まる**：既存部品にない機能。それがあなたのツールの固有価値だ。
  ただし新造が3割を超えたら要望をもう一段分解する（原則1）
- **1枚に収まらない**：2つのツールに分割してつなぐ（原則2）

## 手順6：作ったら、部品を返す

ツールが完成したら、新造した部分を汎用化して部品ライブラリに登録する（原則3）。
物件ツールの「割安度計算」は、汎用化すれば「相場比較スコア」という部品になり、
次は中古車ツールや転職オファー比較ツールで使える。

**あなたの2つ目のツールは、1つ目より必ず速く作れる。**
3つ目はさらに速い。部品が貯まるとは、そういうことだ。

# 終章 — キャンバスの本当の効用

AIツールデザインキャンバスの効用は、製造の高速化だけではない。

**第一に、会話の道具になる。**「このツール、QUALITYが空じゃないか？」
「SAFETYはどうする？」——キャンバスがあると、ツールの議論が
ブロックの言葉でできる。作る人と使う人の共通言語になる。

**第二に、診断の道具になる。**既存ツールをキャンバスに載せると、
弱点が見える。出力が信用できないツールはQUALITYが空いている。
事故が怖いツールはSAFETYが空いている。埋めるべき部品も同時に分かる。

**第三に、資産の地図になる。**部品ライブラリとキャンバスは、
あなたが今まで作ってきたツール群の「持ち物リスト」だ。
新しい要望が来たとき、地図を見れば「ほぼ持っている」ことが分かる。
ゼロから作る不安は、組み合わせる楽しさに変わる。

ツールは完成品ではなく、部品の一時的な編成である——
この見方の転換こそが、キャンバスが運ぶ最も大きな価値だ。
