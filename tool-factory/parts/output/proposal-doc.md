# 部品: proposal-doc（提案書）

- カテゴリ: output ／ 由来: ツール発注フロー改善（製造前の認識合わせ工程） ／ 使用実績: noe-tool-factory

## 何をする部品か

製造に入る前に「こう作ります」を1枚の提案書にして承認を取る。
完成後の「思ってたのと違う」を防ぐ最後の関所。
**出力サンプル（完成イメージのモック）を必ず含める**のがこの部品の核心。

## 組み込みブロック

```markdown
### 提案書の構成（この順で1枚に）

━━━━━━━━━━━━━━━━━━━━━━
[ツール名] 製造提案書
━━━━━━━━━━━━━━━━━━━━━━

**1. 作るもの（1行）**
[誰が・何に困っていて・何を出すツールか]

**2. 完成イメージ（出力サンプル）**
[実際の出力を模したサンプルを具体値で示す。
 レポートなら項目と並びを実データ風に、報告ならその文面例を]

**3. 動き方**
[いつ動く → 何を見る → どう判断する（基準の数値） → 何を出す、を4行で]

**4. 設計（キャンバス）**
[7ブロックの割り当て表。再利用部品N個＋新造M個も明記]

**5. 条件・制約**
[実現可否判定で付いた条件（確認ステップ・定期チェック置換など）]

**6. 今回は作らないもの（スコープ外）**
[要望から意図的に外したものと、外した理由を1行ずつ]

**7. 検収条件**
[追加質問で確認した「完成の定義」。初回試運転でこれを満たせば完成]

━━━━━━━━━━━━━━━━━━━━━━
この内容で製造に入ってよいですか？
修正点があれば該当番号を指摘してください。
━━━━━━━━━━━━━━━━━━━━━━
```

## カスタマイズポイント

- 「2. 完成イメージ」は省略禁止。文章の説明より1つのサンプルが認識ズレを潰す
- 「6. スコープ外」も省略禁止。書かないと完成後に「あれも入ってると思った」が必ず起きる
- 承認は1回。細かい修正は承認後の試運転→検収サイクルで拾う
