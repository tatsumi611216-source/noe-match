# 部品: notify（通知・送信）

- カテゴリ: output ／ 由来: 発注フォームQ5「メール送信・投稿」に実行手段がなかった欠品補充 ／ 使用実績: —

## 何をする部品か

処理結果をユーザーや相手先に**届ける**。下書きまでで止めるか、実際に送るかを明確に分ける。
`safety/irreversible-confirm` が「確認する」部品なのに対し、こちらは「届ける」部品。
2つはセットで使う。

## 重要な制約（実装前に必ず読む）

**Gmail連携は下書き作成までしかできない。実送信の手段を持たない。**
実際に送るには Apps Script（`MailApp.sendEmail`）を使う。この制約は弱点ではなく、
「準備は自動・送信は人間か、明示的に組んだ経路だけ」という安全設計とかみ合っている。

## 組み込みブロック

```markdown
### 通知・送信

**送り先と手段を、届け方の強さで選ぶ：**

| 届け方 | 手段 | 確認の要否 |
|---|---|---|
| チャットで報告 | 応答に書く | 不要 |
| メール下書きを置く | `create_draft`（宛先・件名・本文・添付を指定） | 不要 |
| メールを実送信 | Apps Script `MailApp.sendEmail`（`tool-factory/gas/lab_bridge.gs`） | **必須** |
| 定期実行での自動通知 | Apps Script のトリガー | 初回設定時のみ |

**原則：**
- **下書きまでは自動でよい。送信だけ確認を挟む**（parts/safety/irreversible-confirm）
- 無人の定期実行で送る先は、**本人（オーナー）に限る**。
  外部の相手に無人で送る設計は、誤送信が取り返しがつかないため作らない
- 通知本文には「何が起きたか」と「次に何をすればよいか」を必ず入れる。
  数値の羅列だけ送っても人は動けない
- 変化がないときは送らない（毎回届く通知は読まれなくなる）。
  parts/quality/change-detection のしきい値と組み合わせる

**メール本文の構成：**
```
■ [起きたこと]（1行）
■ [内訳・数字]（箇条書き3つまで）
■ [次にすること]（1行・具体的に）
■ [詳細へのリンク]
```
```

## カスタマイズポイント

- 送信経路（Apps Script）は案件ごとに1度だけ設定し、URLとトークンを控える
- SNS投稿は接続がないため、**下書きをファイル・シートに出して人が投稿する**形にする。
  「投稿まで自動」と約束しない
- 通知の頻度は「変化があったときだけ」を既定にする。定時報告は読み飛ばされる
