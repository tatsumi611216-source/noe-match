# Noe ツールメイキング工場

部品ライブラリから部品を選び、AIツールデザインキャンバスに組み付けて新ツールを製造する。
発想はビジネスモデル・キャンバスと同じ：機能を因数分解し、ブロックに埋め、つなげる。

## 工場の資材置き場

すべて noe-match リポジトリの `tool-factory/` にある：

- `PARTS_CATALOG.md` — 部品カタログ（全部品の一覧・由来・使用実績）
- `parts/{input,quality,process,data,output,integration,safety}/` — 部品本体（コピペで使える組み込みブロック）
- `ASSEMBLY_GUIDE.md` — AIツールデザインキャンバスとSKILL.mdテンプレ
- `canvas.html` — キャンバスの可視化（既存ツールの部品構成を投影できる設計図）
- `ORDER_FORM.md` — 発注フォームの質問セットと回答→部品マッピング表
- `order-form.html` — Webフォーム（回答→発注書を自動生成）

リポジトリが手元にない場合は GitHub の `tatsumi611216-source/noe-match` から取得する。

## 製造プロセス

### STEP 0：ヒアリングシートの受付（該当する場合のみ）

入力が以下のいずれかなら、フォーム発注として扱う：
- 「【自動化ヒアリングシート】」を含むテキスト（Webフォームが生成）
- Google Form等の回答の貼り付け（質問と回答の羅列）
- **「Google Formの発注を確認して」等の指示**：回答スプレッドシート
  「Noe ツール発注 回答」（ID: `1GCjb_S944rh5Pzd2F5RBkJf6gIjiePr1VSpgkzjuCtQ`）を
  Google Drive連携で開き、**最新行**（タイムスタンプが最も新しい行）を
  ヒアリングシートとして読み込む。未処理の行が複数ある場合は一覧を見せてどれを製造するか確認する。
  IDで見つからない場合は名前「Noe ツール発注 回答」でDriveを検索する。
  （フォーム自体の作り方は `tool-factory/google-form-setup.gs` を参照。
  フォーム回答用URL: https://docs.google.com/forms/d/e/1FAIpQLSc_wpqT4VoR40J4sWU41VWm6evK-U5T96LIEwb1MuuTd2eNYQ/viewform ）

**ヒアリングは受付票であり、仕様ではない。**フォーム発注は必ず以下の工程を通す：

```
❶ フォーム受付
   ↓
❷ オーナー確認 …… トオルさんがFormの回答を見て「この発注で進める」と指示するまで待つ。
                    工場が発注を自動で拾って動き出すことはしない
   ↓
❸ 実現可否判定 ＋ 追加質問（要件確定）
   ↓
❹ 提案書の提示
   ↓
❺ 契約 …… オーナーの承認＝契約。ここで仕様（出力サンプル・スコープ外・検収条件）が確定する
   ↓
❻ 作業開始 → 試運転 → 検収（完成の定義を満たすまで）
```

「Google Formの発注を確認して」という指示は❷のオーナー確認そのものなので、
そこから❸以降を進める。契約前に製造物を作り始めない。
契約後の仕様変更は検収後の次サイクル（改修発注）として扱う。

### STEP 0.5：実現可否の正式判定（フォーム発注では必須）

ORDER_FORM.md の「実現可否の判定基準」表に沿って、ヒアリング内容を判定する
（部品：parts/quality/feasibility-check）：

- **◎そのまま可**：既存部品で実現できる → STEP 0.7へ
- **○条件付き可**：条件（定期チェック置換・確認ステップ必須・基準の言語化など）を
  明示し、織り込んでSTEP 0.7へ
- **△要相談**：ネック（社内システム接続など）と代替案を提示して**停止**し、
  ユーザーの判断を仰ぐ

フォームの暫定判定があっても鵜呑みにせず、必ず正式判定をやり直す。
判定結果は提案書と製造レポートに含める。

### STEP 0.7：追加質問 — 要件の確定（フォーム発注では必須）

ヒアリングだけでは製造できない。回答を読んで**その案件専用の追加質問**を生成し、
1回にまとめて聞く（部品：parts/input/spec-drilldown）。

必ず埋める未確定事項：対象の特定（URL・ファイル名）／判断基準の数値化／
出力項目／**完成の定義**／量とタイミング／例外時の挙動。
分かっていることは聞き直さず、推測で埋められるものは推測前提を明示して確認に代える。

### STEP 0.8：提案書の提示と承認（フォーム発注では必須）

追加質問の回答が揃ったら、製造前に提案書を1枚出して承認を取る
（部品：parts/output/proposal-doc）。

提案書には**出力サンプル（完成イメージのモック）**と**スコープ外（作らないもの）**を
必ず含める。キャンバス表（STEP 2相当）もここに含めるため、承認が取れたら
STEP 1〜3は省略してSTEP 4（組み立て）へ直行する。
検収条件＝追加質問で確認した「完成の定義」。試運転（STEP 6）でこれを満たすまでが製造。

### STEP 1：ニーズの一言化

依頼から「誰が・何に困っていて・このツールは何を出すのか」を1行で確定する。
不明瞭な場合のみ1回だけ質問する（parts/input/context-intake の思想を適用）。

### STEP 2：AIツールデザインキャンバスの設計

PARTS_CATALOG.md を読み、7ブロックに部品を割り当てたキャンバス表を出力する：

| ブロック | 問い | 割り当て部品 |
|---|---|---|
| ① INPUT | 入力をどう受け取り分岐するか | |
| ② QUALITY | 出力の質を何で担保するか | |
| ③ PROCESS | 中核の処理は何か | |
| ④ DATA | 外部データをどう取り・貯め・捌くか | |
| ⑤ OUTPUT | 何をどんな形で出すか | |
| ⑥ INTEGRATION | 他ツール・外部サービスとどう連携するか | |
| ⑦ SAFETY | 何を確認し、どこで止まるか | |

各ブロックは「部品ID／なし（不要）／新造（欠品）」のいずれかで埋める。

**判定：**
- 固有ロジック（新造＋案件固有）が全体の3割超 → 因数分解が足りない。ニーズを分割して再設計
- 固有ロジックがゼロ → 新ツール不要。既存ツールのカスタマイズを提案する
- キャンバスに収まらない → 2ツールに分割し parts/integration/skill-handoff でつなぐ

### STEP 3：ユーザー確認

キャンバス表と「固有ロジックとして新造するもの」を提示し、方向性を1回だけ確認する。

### STEP 4：組み立て

1. ASSEMBLY_GUIDE.md の SKILL.md テンプレートをベースにする
2. 各ブロックの部品ファイルから「組み込みブロック」をコピーし、[角括弧]をツール用に書き換える
3. 固有ロジックをSTEP形式で実装する
4. description には具体的なトリガーワードを列挙する（既存スキル群が手本）
5. 完成した SKILL.md を `~/.claude/skills/[ツール名]/SKILL.md` と
   リポジトリの `tool-factory/skills/[ツール名]/SKILL.md` の両方に保存する

### STEP 5：部品の還元（必須・スキップ禁止）

新造した機能があれば：
1. 汎用化して `tool-factory/parts/[カテゴリ]/[部品名].md` に登録する
   （部品ファイルの形式：何をする部品か／組み込みブロック／カスタマイズポイント。
   由来と使用実績を必ず書く）
2. PARTS_CATALOG.md の該当カテゴリ表に1行追加する
3. 既存部品を使った場合はカタログの「使用実績」列を更新する
4. リポジトリにコミット・プッシュする

### STEP 6：試運転とメタ進化

1. 代表的な入力で1回試運転する（またはユーザーに試運転を依頼する）
2. 出力末尾に改良ポイントを1つ出す（parts/output/meta-evolution）
3. 改良ポイントが部品側の欠陥なら、ツールではなく部品を直す（全ツールに波及させる）

## 工場の鉄則

1. **部品ファースト**：書く前にカタログを引く。同じ機能を二度作らない
2. **新造したら登録**：ライブラリに還元しない新造は工場の敵
3. **部品の構造は崩さない**：組み込みブロックは[角括弧]だけ書き換える
4. **1ツール1責務**：太ったツールは分割して skill-handoff でつなぐ
5. **改良は部品側へ**：複数ツールに波及する改善は部品を直す
