# Noe ツールメイキング工場

部品ライブラリから部品を選び、ツールキャンバスに組み付けて新ツールを製造する。
発想はビジネスモデル・キャンバスと同じ：機能を因数分解し、ブロックに埋め、つなげる。

## 工場の資材置き場

すべて noe-match リポジトリの `tool-factory/` にある：

- `PARTS_CATALOG.md` — 部品カタログ（全部品の一覧・由来・使用実績）
- `parts/{input,quality,process,data,output,integration,safety}/` — 部品本体（コピペで使える組み込みブロック）
- `ASSEMBLY_GUIDE.md` — ツールキャンバスとSKILL.mdテンプレ

リポジトリが手元にない場合は GitHub の `tatsumi611216-source/noe-match` から取得する。

## 製造プロセス

### STEP 1：ニーズの一言化

依頼から「誰が・何に困っていて・このツールは何を出すのか」を1行で確定する。
不明瞭な場合のみ1回だけ質問する（parts/input/context-intake の思想を適用）。

### STEP 2：ツールキャンバスの設計

PARTS_CATALOG.md を読み、7ブロックに部品を割り当てたキャンバス表を出力する：

| ブロック | 問い | 割り当て部品 |
|---|---|---|
| ① INPUT | 入力をどう受け取り分岐するか | |
| ② QUALITY | 出力の質を何で担保するか | |
| ③ PROCESS | 中核の処理は何か | |
| ④ DATA | 外部データをどう取り・貯め・捌くか | |
| ⑤ OUTPUT | 何をどんな形で出すか | |
| ⑥ INTEGRATION | 他ツール・外部サービスとどう連携するか | |
| ⑦ SAFETY | 何を確認し、どこで止まるか | |

各ブロックは「部品ID／なし（不要）／新造（欠品）」のいずれかで埋める。

**判定：**
- 固有ロジック（新造＋案件固有）が全体の3割超 → 因数分解が足りない。ニーズを分割して再設計
- 固有ロジックがゼロ → 新ツール不要。既存ツールのカスタマイズを提案する
- キャンバスに収まらない → 2ツールに分割し parts/integration/skill-handoff でつなぐ

### STEP 3：ユーザー確認

キャンバス表と「固有ロジックとして新造するもの」を提示し、方向性を1回だけ確認する。

### STEP 4：組み立て

1. ASSEMBLY_GUIDE.md の SKILL.md テンプレートをベースにする
2. 各ブロックの部品ファイルから「組み込みブロック」をコピーし、[角括弧]をツール用に書き換える
3. 固有ロジックをSTEP形式で実装する
4. description には具体的なトリガーワードを列挙する（既存スキル群が手本）
5. 完成した SKILL.md を `~/.claude/skills/[ツール名]/SKILL.md` と
   リポジトリの `tool-factory/skills/[ツール名]/SKILL.md` の両方に保存する

### STEP 5：部品の還元（必須・スキップ禁止）

新造した機能があれば：
1. 汎用化して `tool-factory/parts/[カテゴリ]/[部品名].md` に登録する
   （部品ファイルの形式：何をする部品か／組み込みブロック／カスタマイズポイント。
   由来と使用実績を必ず書く）
2. PARTS_CATALOG.md の該当カテゴリ表に1行追加する
3. 既存部品を使った場合はカタログの「使用実績」列を更新する
4. リポジトリにコミット・プッシュする

### STEP 6：試運転とメタ進化

1. 代表的な入力で1回試運転する（またはユーザーに試運転を依頼する）
2. 出力末尾に改良ポイントを1つ出す（parts/output/meta-evolution）
3. 改良ポイントが部品側の欠陥なら、ツールではなく部品を直す（全ツールに波及させる）

## 工場の鉄則

1. **部品ファースト**：書く前にカタログを引く。同じ機能を二度作らない
2. **新造したら登録**：ライブラリに還元しない新造は工場の敵
3. **部品の構造は崩さない**：組み込みブロックは[角括弧]だけ書き換える
4. **1ツール1責務**：太ったツールは分割して skill-handoff でつなぐ
5. **改良は部品側へ**：複数ツールに波及する改善は部品を直す
