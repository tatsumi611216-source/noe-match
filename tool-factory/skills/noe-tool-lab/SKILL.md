# Noeツールラボ

AIツールの**一生**（受注 → 設計 → 製造 → 運用 → 改修 → 部品の還元）を扱う統合スキル。
発想はビジネスモデル・キャンバスと同じ：機能を因数分解し、ブロックに埋め、つなげる。

## 資材置き場

すべて noe-match リポジトリの `tool-factory/` にある：

| ファイル | 中身 |
|---|---|
| `PARTS_CATALOG.md` | 部品カタログ（全部品の一覧・由来・使用実績） |
| `parts/{input,quality,process,data,output,integration,safety}/` | 部品本体（コピペで使える組み込みブロック） |
| `ASSEMBLY_GUIDE.md` | AIツールデザインキャンバスとSKILL.mdテンプレ |
| `AI_TOOL_DESIGN_CANVAS.md` | 理論書（外部公開用。キャンバスの考え方と実例） |
| `ORDER_FORM.md` | 発注ヒアリングシート・実現可否の判定基準・回答→部品マッピング |
| `order-form.html` / `google-form-setup.gs` | 発注フォーム（Web版／Google Form版） |
| `canvas.html` | キャンバス可視化（内部資料） |
| `lab_inventory.py` | 在庫棚卸し（部品・ツール・カタログとの不一致を検知） |
| `skills/` | 製造済みツールの正本 |

リポジトリが手元にない場合は GitHub の `tatsumi611216-source/noe-match` から取得する。

---

## 入口：5つのモード（parts/input/mode-detection）

最初のメッセージから用件を判定し、対応するモードに入る。判断が難しい場合のみ1問だけ確認する。

| モード | 起動する言葉 | やること |
|---|---|---|
| **① 受注** | 「発注を確認して」「Formを見て」「提案書を作って」 | 発注を読み、実現可否判定→追加質問→提案書→契約 |
| **② 設計** | 「キャンバスで設計して」「どう作る？」 | 製造せず、キャンバスを埋めて構成だけ出す |
| **③ 製造** | 契約済みの発注、「作って」 | 部品を組んでSKILL.mdを生成し、試運転する |
| **④ 棚卸し** | 「部品の棚卸し」「何が作れる？」 | `lab_inventory.py` を実行し、在庫と抜けを報告 |
| **⑤ 改修** | 「〇〇を直して」「精度が悪い」 | 原因が部品側かツール側かを切り分けて直す |

## ① 受注モード

**ヒアリングは受付票であり、仕様ではない。** 以下の工程を必ず通す：

```
❶ フォーム受付
   ↓
❷ オーナー確認 …… オーナー（トオルさん）が発注を見て「進める」と指示するまで待つ。
                    ラボが発注を自動で拾って動き出すことはしない
   ↓
❸ 実現可否判定 ＋ 追加質問（要件確定）
   ↓
❹ 提案書の提示
   ↓
❺ 契約 …… オーナーの承認＝契約。ここで仕様（出力サンプル・スコープ外・検収条件）が確定
   ↓
❻ 製造モードへ
```

### 発注の受け取り口

- 「【自動化ヒアリングシート】」を含むテキスト（Webフォームが生成）
- Google Form等の回答の貼り付け
- **回答スプレッドシート**「Noe ツール発注 回答」
  （ID: `1GCjb_S944rh5Pzd2F5RBkJf6gIjiePr1VSpgkzjuCtQ`）をDrive連携で開き、**最新行**を読む。
  未処理が複数あれば一覧を見せてどれを進めるか確認する。IDで開けない場合は名前で検索する。
  フォーム: https://docs.google.com/forms/d/e/1FAIpQLSc_wpqT4VoR40J4sWU41VWm6evK-U5T96LIEwb1MuuTd2eNYQ/viewform
- 会話での直接依頼（この場合❶❷は省略し❸から入る）

### ❸-a 実現可否の正式判定（parts/quality/feasibility-check）

ORDER_FORM.md の判定基準表に沿って判定する。フォームの暫定判定は鵜呑みにせず必ずやり直す。

- **◎そのまま可** → 次へ
- **○条件付き可** → 条件（定期チェック置換・確認ステップ必須・基準の言語化）を明示して次へ
- **△要相談** → ネックと代替案を提示して**停止**し、オーナーの判断を仰ぐ

### ❸-b 追加質問（parts/input/spec-drilldown）

ヒアリングだけでは製造できない。回答を読んで**案件専用の質問**を生成し、1回にまとめて聞く。
必ず埋める未確定事項：対象の特定（URL・ファイル名）／判断基準の数値化／出力項目／
**完成の定義**／量とタイミング／例外時の挙動。
分かっていることは聞き直さず、推測で埋まるものは推定前提を明示して確認に代える。

### ❹ 提案書（parts/output/proposal-doc）

**出力サンプル（完成イメージのモック）**と**スコープ外（作らないもの）**は省略禁止。
キャンバス表も提案書に含める。検収条件＝「完成の定義」。

## ② 設計モード

製造せず、AIツールデザインキャンバスを埋めて構成だけ出す。

| ブロック | 問い |
|---|---|
| ① INPUT | 入力をどう受け取り分岐するか |
| ② QUALITY | 出力の質を何で担保するか |
| ③ PROCESS | 中核の処理は何か |
| ④ DATA | 外部データをどう取り・貯め・捌くか |
| ⑤ OUTPUT | 何をどんな形で出すか |
| ⑥ INTEGRATION | 他ツール・外部サービスとどう連携するか |
| ⑦ SAFETY | 何を確認し、どこで止まるか |

各ブロックは「部品ID／なし（不要）／新造（欠品）」のいずれかで埋める。

**判定：**
- 固有ロジックが全体の3割超 → 因数分解が足りない。要望を分割して再設計
- 固有ロジックがゼロ → 新ツール不要。既存ツールのカスタマイズを提案する
- キャンバスに収まらない → 2ツールに分割し parts/integration/skill-handoff でつなぐ

## ③ 製造モード

1. ASSEMBLY_GUIDE.md の SKILL.md テンプレートをベースにする
2. 各部品ファイルから「組み込みブロック」をコピーし、**[角括弧]だけ**ツール用に書き換える
3. 固有ロジックをSTEP形式で実装する（スクリプトが必要なら `scripts/` に置く）
4. description には具体的なトリガーワードを列挙する（既存スキル群が手本）
5. 完成した SKILL.md を `~/.claude/skills/[名前]/` と
   `tool-factory/skills/[名前]/` の**両方**に保存する（正本はリポジトリ側）
6. **試運転する。** 実データで1回動かし、検収条件を満たすか確認する
7. **部品を還元する**（下記）
8. リポジトリにコミット・プッシュする

### 部品の還元（必須・スキップ禁止）

新造した機能があれば：
1. 汎用化して `tool-factory/parts/[カテゴリ]/[部品名].md` に登録する
   （形式：何をする部品か／組み込みブロック／カスタマイズポイント。由来と使用実績を必ず書く）
2. `PARTS_CATALOG.md` の該当カテゴリ表に1行追加する
3. 既存部品を使った場合は「使用実績」列を更新する
4. `python3 tool-factory/lab_inventory.py` で不一致がないことを確認する

## ④ 棚卸しモード

```bash
python3 tool-factory/lab_inventory.py        # 在庫一覧
python3 tool-factory/lab_inventory.py --json # 機械可読
```

部品数・ツール数・部品の利用回数（★）・カタログとの不一致を報告する。
「何が作れる？」と聞かれたら、在庫を踏まえて**具体的なツール候補**を型別に挙げる
（データ収集型／思考型／検証型／定型業務型）。抽象的な可能性の列挙はしない。

## ⑤ 改修モード

不具合・精度不足の報告を受けたら、**まず原因の所在を切り分ける**：

| 原因 | 直す場所 | 波及 |
|---|---|---|
| そのツール固有のロジックの問題 | ツールのSKILL.md／スクリプト | そのツールのみ |
| 部品そのものの欠陥 | `parts/` の部品ファイル | **その部品を使う全ツール**に反映する |

部品側を直した場合は、その部品を使っている他のツールも点検する（カタログの「使用実績」列で追える）。

## ラボの鉄則

1. **部品ファースト** — 書く前にカタログを引く。同じ機能を二度作らない
2. **新造したら登録** — ライブラリに還元しない新造はラボの敵
3. **部品の構造は崩さない** — 組み込みブロックは[角括弧]だけ書き換える
4. **1ツール1責務** — 太ったツールは分割して skill-handoff でつなぐ
5. **改良は部品側へ** — 複数ツールに波及する改善は部品を直す
6. **契約前に作らない** — 提案書の承認を得てから製造に入る
7. **試運転していないものを納品しない** — 実データで1回動かすまでが製造

| 項目 | 内容 |
|---|---|

| 再利用した部品 | [部品ID一覧]（[N]点） |
| 新造した部品 | [部品ID一覧]（[N]点・ライブラリ登録済み） |
