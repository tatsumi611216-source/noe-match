## あなたのタスク（毎回実行）

1. `agent/keyword_queue.json` を読み、`status: "pending"` の先頭 **2件** を選ぶ。キューが空の場合は、既存クラスタの空白キーワードを自分で発掘してキューに補充してから処理する。**発掘時はデータ・統計型（type: data）を最優先する**——2026-07-26のGSC実測で、データ型はページあたり表示回数が他クラスタの2.5倍（31 imp/頁 vs 地域12.7 imp/頁）と最も効率が高いことが確認済み。
   **キューを自分で補充する場合・新しいテーマを検討する場合は、先に `agent/PHILOSOPHY.md` を読み、その判定チェックを通してから決めること**
2. 各キーワードについて記事を1本生成する（下記の品質基準に厳密に従う）
3. `sitemap.xml` に新記事のURLを追加する
4. `index.html` の記事一覧はテーマ別グループ構造（`<h3>`見出し＋グループ内連番の`arc-link`）になっている。新記事は**内容に最も近いテーマグループの末尾**に追加し、そのグループの`arc-no`連番と見出しの「（N記事）」を更新する。該当グループがなければ新グループを追加してよい。
   **記事総数は `index.html` 内の2箇所に書かれている。両方とも更新すること**（過去に片方だけ更新して9本ぶんズレた）
   - hero-badge（冒頭の「📅 2026年◯月更新 ｜ 全N記事・編集部検証」）
   - `#articles` セクション見出しの「全N記事」
5. 処理したキューの `status` を `"done"` に、`published` に日付を記入する
6. **`python3 scripts/check_consistency.py` を実行し、終了コード0を確認する**。
   articles/・sitemap.xml・index.html の記事集合、記事数表記、内部リンクの
   実在性をまとめて検証する。不整合が出たら修正してから次に進むこと
   （過去に7本の載せ漏れと記事数表記の乖離が発生しており、目視では取りこぼす）
7. すべてコミットして `main` にプッシュする（プッシュ権限がない場合はPRを作成する）

## 記事の品質基準（必須）

### フォーマット
- テンプレート：`articles/tokyo-guide/index.html` および `articles/osaka-guide/index.html` の構造を踏襲する
- 出力先：`articles/<slug>/index.html`（slugはキューに指定済み）
- `<head>` に必ず含める：title / meta description / canonical / og:title / og:url / BlogPosting JSON-LD / BreadcrumbList JSON-LD / FAQPage JSON-LD
- 既存記事と同じCSS（テンプレートの `<style>` ブロックをそのまま使用）
- 画像は `/images/` 内の既存ファイルから未使用のものを選ぶ

### コンテンツ
- 文字数：本文6,000〜10,000字目安
- 必須セクション：導入 / 比較表 / 本題（キーワード固有の深掘り）/ 体験談2本 / FAQ 5問 / まとめ / 著者情報
- 体験談は日本人の姓＋年齢＋職業で、**既存記事と名前・エピソードが重複しないこと**（既存記事をgrepして確認）
- 内部リンクを最低3本入れる（関連する既存記事へ。`/articles/<slug>/` 形式）
- FAQはFAQPage JSON-LDと本文の両方に同内容を記載

### 法令・表現ルール（絶対厳守）
- フッターに【PR】表記（テンプレートに含まれている。削除しないこと）
- 断定できない数値は「（各社公式発表）」「（〜より推計）」を必ず付ける
- 効果の断定表現（「必ず出会える」等）は禁止
- 各アプリの料金は既存記事の料金表をそのまま使う（勝手に変更しない）
- Pairsのアフィリエイトは2024年9月に終了している。「Pairsに登録すれば報酬」のような記述はしない

### 映像作品を扱う記事のルール

- 作品レビュー記事は作らない。主語は常に「2人の関係」であり、作品は道具として扱う
  （例：×「この映画は名作」→ ○「この種の作品は会話が生まれやすい」）
- 作品名は例示にとどめ、あらすじの詳細な再現・長い引用はしない（著作権配慮）
- 特定作品への否定的な断定は避け、「傾向」として記述する
- 動画配信サービスへの言及は、デート・おうち時間の文脈でのみ行う

### やってはいけないこと
- 既存記事の削除・改名
- `about.md` / `privacy-policy.md` / `disclaimer.md` / `CNAME` / `robots.txt` の変更
- 1回の実行で3記事以上の生成（品質低下防止のため2記事まで）
- キューにないキーワードでの記事生成

### CTA密度のガードレール（2026-07-28制定・YMYL評価の保護）

- **1記事のアフィリエイトリンクは合計4箇所まで**（CTAブロック・表内の公式ボタン・本文中テキストリンクを合算して数える）
- **同一広告主のリンクは1記事2箇所まで**。3箇所以上は重複とみなし、最も効果の低い位置（本文中インラインリンク）から削る
- 新しい案件を既存記事に追加する際は、**追加前に必ずその記事の現在のリンク数を数える**。4箇所に達している記事には追加しない（別の記事を受け皿にする）
- 月次メンテ（Phase 3）で全記事のリンク数を集計し、5箇所以上の記事があれば削減する
- 探偵・離婚・保険・住宅ローン等のYMYL寄りクラスタは**上限3箇所**とし、より保守的に運用する

- CTAブロックのデザインは既存記事の「ユーブライド公式サイトを見る」ボタン（#ff4d7e系）を踏襲する
- 提携していないサービスへの外部リンクは公式サイトへの通常リンク（rel="nofollow"）のみ
- 誇大表現（「必ず出会える」「絶対」等）をCTA周辺に置くことは禁止

### 収益導線ルール（出口設計）

- アフィリエイト提携が終了しているアプリ（Pairs・with）を主題とする記事には、必ず提携中アプリ（ユーブライド・Omiai・Tapple・マリッシュ）への比較・代替導線を1箇所以上設ける
- 導線は自然な文脈で（「〜が目的なら◯◯の方が近道」形式）。無理な誘導・断定表現は禁止
- 専用ガイド記事（youbride-guide・marrish-guide・omiai-guide・tapple-guide）が存在する場合はそこへリンクする

## Phase 2：データ駆動の記事強化（稼働中）

`agent/gsc_data.json` が存在する場合、キュー記事の生成に**加えて**以下を実行する（詳細ルールは `agent/phase2_gsc.md`）：

1. `agent/gsc_data.json` を読む（過去28日のクエリ×ページデータ。ローカルの週次ジョブが日曜夜に更新する）
2. **強化対象の選定**：表示回数5回以上 かつ 平均掲載順位11〜50位 のクエリを抽出する
3. 対象クエリに対応する記事（pageのURLから特定）に、そのクエリの検索意図に合うセクションを追記する
   - 1回の実行で強化するのは最大2記事・1記事あたり追記2セクションまで
   - タイトル・meta descriptionにクエリ語が入っていなければ前方に組み込む（og:title/JSON-LDも同期）
   - 順位10位以内のクエリの記事は触らない
   - `agent/run_log.md` を確認し、2週間以内に強化済みの記事はスキップする
4. **新規需要の発見**：表示されたクエリに対応する記事が存在しない場合、`keyword_queue.json` に `status: "proposed"` で追加する（自動生成はしない・人間レビュー用）
5. 実行結果（生成・強化した記事、対象クエリ、判断理由の要約）を `agent/run_log.md` に追記する

`gsc_data.json` が存在しない・14日以上古い場合はPhase 2をスキップし、その旨を run_log.md に記録する。

以下の 2-A 〜 2-D は、いずれも Phase 2 の一部として同じ `gsc_data.json` から実施する。

### 2-A. タイトルCTR最適化（2026-07-26追加）

gsc_data.jsonの by_query_page から、**平均掲載順位10位以内なのにクリック率が2%未満**の
クエリ×ページを抽出する。該当があれば、そのページのタイトル・meta descriptionを
以下の観点で改善する（1回の実行で最大2記事）。

- 数字・年号・【】等でSERP上の視認性を上げる
- 検索クエリの語をタイトル前方に置く
- 「結論が中にある」ことが伝わる文言にする（〜を徹底検証／〜の答え 等）
- 誇大化はしない（クリック後の失望は直帰としてマイナス評価になる）
- 変更したら run_log.md に新旧タイトルを記録し、2週間は同一記事を再変更しない

### 2-B. クエリカニバリゼーションの自動検知（2026-07-26追加）

gsc_data.jsonの by_query_page で、**同一クエリに複数の自サイトページが表示されている**
組み合わせを抽出する。検出した場合：

1. どちらのページがそのクエリの「正規ページ」かを判断する
   （専用記事＞総合記事。例：「with 結婚率」なら with専用記事が正規）
2. 非正規側のページから正規ページへ、そのクエリを明示したアンカーテキストで
   内部リンクを追加する（過去の実績：success-rate-data → with-seriousness-data で解消）
3. run_log.md に「カニバリ検知・正規化」として記録する
4. 2週間後も解消しない場合のみ、非正規側の該当セクションを要約に圧縮して
   正規ページへ誘導する形に書き換える（段階的対応・いきなり削らない）

### 2-C. ミドル競合クエリのSERP網羅チェック（2026-07-26追加）

Phase 2で強化対象を選定する際、**平均掲載順位11〜30位で2週間以上足踏みしている記事**に限り、
追記の前に以下を行うこと。

1. 対象クエリでWebSearchを実行し、上位表示されている記事のタイトル・要約から
   「上位陣が共通してカバーしているトピック」を洗い出す
2. 自記事に欠けているトピックを特定し、それを埋めるセクションを追記する
   （ただし記事の主語・切り口は変えない。網羅は手段であり、
   「大手が書けない視点」という差別化が本体であることを忘れない）
3. run_log.mdに「SERP網羅チェック実施」として、追加したトピックを記録する

適用範囲の限定（重要）：
- 競合が弱いクエリ（無料ブログ等しか上位にいない）には適用しない（過剰品質）
- 50位以下の記事にも適用しない（まず基礎評価待ち）
- 対象は「戦っている中間層」のみ。1回の実行で最大2記事まで

### 2-D. ゼロ検索クエリの自動検知（2026-07-26追加）

このサイトは記事公開前の検索ボリューム調査を行わず「先に書いて事後検証する」運用のため、
Phase 2実行時に以下も追加で行うこと。

1. `agent/gsc_data.json` の `by_page` を確認し、**公開から21日以上経過しているのに
   表示回数が合計3回未満**のページを抽出する
2. 該当ページの `keyword_queue.json` 内エントリを参照し、`target_queries` が
   実際に検索されていない可能性が高いと判断する
3. 対応は記事の削除ではなく、**タイトル・meta description・h1・h2の言い回しを
   より一般的な検索語に寄せて修正する**（本文の構成・情報自体はそのまま活かす）
4. 修正した記事は `agent/run_log.md` に「ゼロ検索クエリ修正」として記録し、
   どのクエリからどのクエリへ寄せたかを明記する
5. 3回目の修正でも表示が増えない記事は、削除せず本ファイル末尾の
   「要観察リスト・警告」に追記し、次回以降は触らず様子を見る

## Phase 3：月次メンテナンス（2026-07-26制定・毎月第1週の実行時に併せて行う）

週次のPhase 1/2とは別に、月に1回（その月の最初の実行時）、以下を行う。

### 3-1. 鮮度メンテナンス
- タイトル・本文中の年号表記（【2026年版】等）を確認し、年が変わった直後の
  1月の実行では全記事の年号を一括更新する
- 料金表を持つ記事（アプリ料金・相談所料金等）は、各社公式サイトの現行料金と
  照合し、変わっていれば表と「※2026年◯月時点」の表記を更新する
  （1回の実行で確認するのは主要10記事まで。翌月に続きを行う）
- dateModified（JSON-LD）を実際に更新した記事のみ更新する（空更新はしない）

### 3-2. 技術ヘルスチェック
- `python3 scripts/check_consistency.py` を実行する（記事集合の一致・記事数表記・
  内部リンクの実在性・sitemap.xmlとsitemap-all.xmlの一致を機械的に検証する）。
  リンク切れが報告されたら、実在する最も近い記事に貼り替える
- `redirects.json` の各エントリについて、旧slug側が実際にリダイレクトstubのままか
  確認する。実記事に育っているエントリは削除する
  （2026-08-01に7件の残存を検出。放置するとローカル確認時に実記事が別記事へ飛ぶ）
- 孤立記事（どの記事からも内部リンクされていない記事）を検出し、
  関連するハブ記事からリンクを1本追加する

### 3-3. 勝ちパターン分析
- gsc_data.jsonから「順位10位以内 かつ CTR5%以上」の記事を勝ち記事として抽出する
- 勝ち記事に共通する要素（タイトルの型・記事タイプ・クラスタ）をrun_log.mdに記録する
- 次月のキュー消化順を、勝ちパターンに近いテーマ優先に並べ替えてよい

### 3-4. クラスタ依存度モニタ（リスク分散ルールの実行部分）
- クラスタ別のGSC表示回数シェアを集計しrun_log.mdに記録する
- 特定クラスタが50%を超えていたら本ファイル末尾の「要観察リスト・警告」に警告を書き残す
  （上限の考え方は `agent/PHILOSOPHY.md` の「リスク分散ルール」を参照）

## note転載用の要約生成（毎回実行）

生成した各記事について、note投稿用の要約を `agent/note_drafts/<slug>.md` に保存する：

- 冒頭：記事の最重要データ・結論を2〜3行（noteユーザーの興味を引く書き出し）
- 本文：**1,500〜2,500字**（2026-07-29改定。従来の600〜800字は「告知」の長さで、
  note内で読まれず、note.comのドメイン評価を借りる意味も失われるため引き上げた）
- 構成：H2見出しを2〜3本立て、note単体で完結する価値を持たせる。
  サイトへの導線は「表・シミュレーション・全データはこちら」という位置づけにし、
  「続きはサイトで」型の出し惜しみにはしない
- 末尾：「詳細なデータ・比較表はこちら →（記事URL）」で必ずサイトへ誘導
- **さらに末尾へ「▼あわせて読みたい」として関連記事2本のURLを付ける**（回遊を作るため）。
  選ぶ基準は①その記事から内部リンクしている実在記事 ②**CTA設置済みの収益記事を優先**
  ③文脈が自然につながること。3本以上は宣伝色が強くなるので付けない
- 注意：記事本文のコピペ転載は禁止（Google重複判定防止のため必ず書き下ろす）
- 文体：です・ます調（noteの読者層に合わせる。サイト記事のだ・である調と変える）
- タイトル：記事タイトルとは別の、noteで引きのある問いかけ型
  （例：「マッチングアプリで結婚した人、実は4組に1組って知ってました？」）

過去分の削除は不要。人間が投稿済みのものを判断して使う。
