# サイト運営の基本哲学：軸展開モデル（2026-07-26制定）

個人がアフィリエイトサイトを運営する場合、「複数ドメインに広く分散する」より
「1つの強い軸に、あらゆるジャンルを吸収させる」方が構造的に有利である。

## なぜ軸展開が個人に向くか

- ドメイン・被リンク・E-E-A-Tは1ドメインに集中した方が複利で効く
  （新記事が旧記事の権威を借りられる。分散すると評価がゼロから積み直しになる）
- GSC連携・自動生成工場・ASP審査・法令対応のインフラは1セットで済む
- 個人が同時に深く見られるサイトは実質1つ。専門性の深さでGoogleにも
  ASPの審査にも評価される以上、「浅く広い6サイト」は「深い1サイト」に必ず負ける

## 軸として機能するための条件

1. 読者の母数が大きい普遍的なライフイベント・関心事であること
2. 他の無関係なジャンル（転職・お金・エンタメ・美容・スキル等）と
   自然に接続できる汎用性を持つこと
3. 「大手が書けない切り口」（本文書 別項）を無数に作れる懐の深さがあること

noe-matchは「結婚・婚活」を軸に採用し、転職・固定費・エンタメ・子育てといった
無関係に見えるジャンルを「結婚を視点に整理し直す」ことで全て吸収した。
新しいジャンルの記事を検討する際は、まずこの軸展開モデルに沿えるかを確認すること。

# NOE 記事工場エージェント 運用マニュアル

このファイルは、週次で自動実行されるエージェントへの指示書です。エージェントはこのリポジトリ（noe-match.com のソース）をcloneした状態で起動します。

## あなたのタスク（毎回実行）

1. `agent/keyword_queue.json` を読み、`status: "pending"` の先頭 **2件** を選ぶ。キューが空の場合は、既存クラスタの空白キーワードを自分で発掘してキューに補充してから処理する。**発掘時はデータ・統計型（type: data）を最優先する**——2026-07-26のGSC実測で、データ型はページあたり表示回数が他クラスタの2.5倍（31 imp/頁 vs 地域12.7 imp/頁）と最も効率が高いことが確認済み
2. 各キーワードについて記事を1本生成する（下記の品質基準に厳密に従う）
3. `sitemap.xml` に新記事のURLを追加する
4. `index.html` の記事一覧はテーマ別グループ構造（`<h3>`見出し＋グループ内連番の`arc-link`）になっている。新記事は**内容に最も近いテーマグループの末尾**に追加し、そのグループの`arc-no`連番と見出しの「（N記事）」、および`#articles`セクション見出しの「全N記事」を更新する。該当グループがなければ新グループを追加してよい。一覧とsitemapの記事集合は常に一致させること（過去に7本の載せ漏れと記事数表記の乖離が発生した）
5. 処理したキューの `status` を `"done"` に、`published` に日付を記入する
6. すべてコミットして `main` にプッシュする（プッシュ権限がない場合はPRを作成する）

## コンテンツの核心原則：「大手が書けない場所」を狙う（2026-07-26制定）

本サイトの記事選定・執筆は、**大手メディア・当事者企業が利害関係上・専門外・立場上書けない切り口**を
常に優先する。これはSEO戦略であると同時に、E-E-A-Tの独自性そのものである。

### 判定チェック（新規記事を書く前に自問する）

1. この切り口を、当事者企業（ASP提携先も含む）の公式サイトは書けるか？
   → 書けるなら没。書けない・書きにくいなら採用。
   （例：「成婚実績は本物か」の検証はユーブライド公式には書けない）
2. この切り口を、業界大手ポータルサイトは書けるか？
   → 式場ポータルは「見積もりが100万円上がる仕組み」を書かない。
     探偵ポータルは「まず自分で確認する方法」を書かない。
     映画メディアは「作品を関係性の道具として評価する」ことをしない。
3. 読者が「利害関係のない第三者の本音」として受け取れる内容か？

この3条件を満たす記事は、新規ドメインでも上位表示されやすく
（大手が競合として存在しないため）、CTAのクリック率も高くなる傾向がある。

### 実例（すでに実践している型）

- 探偵業界が書けない「まず自分でできる確認」（kekkon-sokou-chousa）
- 相談所公式が言えない「料金差の正体」（soudanjo-hikaku）
- 写真業者が言わない「投資に値するかの損得」（konkatsu-photo-guide）
- スタジオが隠す「追加料金が発生する項目」（maedori-photo-guide）
- 映画メディアが取らない「関係性への作用」という評価軸（ouchi-date-sakuhin等）

新しい記事テーマを追加する際は、この原則に沿っているかを最初に確認すること。
沿っていないテーマ（単なる比較・単なるレビュー）は、書く前に切り口を寄せ直す。

## 広視聴読者パターン：「入口は広く、視点だけ独自」（2026-07-26制定）

一般的なテーマ（転職理由・お金の悩み等）を、noe-match独自の視点（結婚・婚活）で
整理し直す記事は許可する。ただし以下を必ず守ること。

- **タイトル・導入は広く**：一般ワードで検索する層（結婚を考えていない人）も呼び込む
- **本文は全項目を対等に解説**：関係ない一般論を延々と書かない。ただし各項目の
  最後は必ず「今は関係なくても、結婚を意識すると重みが変わる」という予告的な
  一文で着地させる。結婚していない読者にも押し付けがましくならない書き方にする
- **結論・まとめは結婚に戻す**：記事全体の着地点は必ず婚活・結婚に関連づける
- 判定：「この記事は転職メディア（等、他ジャンルの専門サイト）が書けるか？」
  →「結婚を軸に理由を整理し直す」視点は書けないので合格。
  →「転職ノウハウそのもの」を深掘りするなら不合格（それは他ジャンルの専門性）

このパターンにより、一般層からの流入（間口）と婚活読者への専門性（深さ）を両立する。

## サイトの守備範囲（2026-07-25拡張）

本サイトは「出会い→婚約→結婚→新生活」のライフイベント一本道を扱う。
マッチングアプリ・婚活アプリに加え、結婚相談所・プロポーズ・婚約指輪・式場探し・
ブライダルエステ・前撮り・新婚生活の準備までが正規の守備範囲である。
ただし恋愛・結婚と無関係のジャンル（転職・通信・金融単体など）の記事は生成しない。
美容・お金の話題は必ずブライダル/婚活文脈に接続して書くこと。

## 記事の品質基準（必須）

### フォーマット
- テンプレート：`articles/tokyo-guide/index.html` および `articles/osaka-guide/index.html` の構造を踏襲する
- 出力先：`articles/<slug>/index.html`（slugはキューに指定済み）
- `<head>` に必ず含める：title / meta description / canonical / og:title / og:url / BlogPosting JSON-LD / BreadcrumbList JSON-LD / FAQPage JSON-LD
- 既存記事と同じCSS（テンプレートの `<style>` ブロックをそのまま使用）
- 画像は `/images/` 内の既存ファイルから未使用のものを選ぶ

### コンテンツ
- 文字数：本文6,000〜10,000字目安
- 必須セクション：導入 / 比較表 / 本題（キーワード固有の深掘り）/ 体験談2本 / FAQ 5問 / まとめ / 著者情報
- 体験談は日本人の姓＋年齢＋職業で、**既存記事と名前・エピソードが重複しないこと**（既存記事をgrepして確認）
- 内部リンクを最低3本入れる（関連する既存記事へ。`/articles/<slug>/` 形式）
- FAQはFAQPage JSON-LDと本文の両方に同内容を記載

### 法令・表現ルール（絶対厳守）
- フッターに【PR】表記（テンプレートに含まれている。削除しないこと）
- 断定できない数値は「（各社公式発表）」「（〜より推計）」を必ず付ける
- 効果の断定表現（「必ず出会える」等）は禁止
- 各アプリの料金は既存記事の料金表をそのまま使う（勝手に変更しない）
- Pairsのアフィリエイトは2024年9月に終了している。「Pairsに登録すれば報酬」のような記述はしない

### CTA密度のガードレール（2026-07-28制定・YMYL評価の保護）

- **1記事のアフィリエイトリンクは合計4箇所まで**（CTAブロック・表内の公式ボタン・本文中テキストリンクを合算して数える）
- **同一広告主のリンクは1記事2箇所まで**。3箇所以上は重複とみなし、最も効果の低い位置（本文中インラインリンク）から削る
- 新しい案件を既存記事に追加する際は、**追加前に必ずその記事の現在のリンク数を数える**。4箇所に達している記事には追加しない（別の記事を受け皿にする）
- 月次メンテ（Phase 3）で全記事のリンク数を集計し、5箇所以上の記事があれば削減する
- 探偵・離婚・保険・住宅ローン等のYMYL寄りクラスタは**上限3箇所**とし、より保守的に運用する

- CTAブロックのデザインは既存記事の「ユーブライド公式サイトを見る」ボタン（#ff4d7e系）を踏襲する
- 提携していないサービスへの外部リンクは公式サイトへの通常リンク（rel="nofollow"）のみ
- 誇大表現（「必ず出会える」「絶対」等）をCTA周辺に置くことは禁止

### 映像作品を扱う記事のルール

- 作品レビュー記事は作らない。主語は常に「2人の関係」であり、作品は道具として扱う
  （例：×「この映画は名作」→ ○「この種の作品は会話が生まれやすい」）
- 作品名は例示にとどめ、あらすじの詳細な再現・長い引用はしない（著作権配慮）
- 特定作品への否定的な断定は避け、「傾向」として記述する
- 動画配信サービスへの言及は、デート・おうち時間の文脈でのみ行う

### 収益導線ルール（出口設計）

- アフィリエイト提携が終了しているアプリ（Pairs・with）を主題とする記事には、必ず提携中アプリ（ユーブライド・Omiai・Tapple・マリッシュ）への比較・代替導線を1箇所以上設ける
- 導線は自然な文脈で（「〜が目的なら◯◯の方が近道」形式）。無理な誘導・断定表現は禁止
- 専用ガイド記事（youbride-guide・marrish-guide・omiai-guide・tapple-guide）が存在する場合はそこへリンクする

### やってはいけないこと
- 既存記事の削除・改名
- `about.md` / `privacy-policy.md` / `disclaimer.md` / `CNAME` / `robots.txt` の変更
- 1回の実行で3記事以上の生成（品質低下防止のため2記事まで）
- キューにないキーワードでの記事生成

## note転載用の要約生成（毎回実行）

- 構成：H2見出しを2〜3本立て、note単体で完結する価値を持たせる。
  サイトへの導線は「表・シミュレーション・全データはこちら」という位置づけにし、
  「続きはサイトで」型の出し惜しみにはしない
- 末尾：「詳細なデータ・比較表はこちら →（記事URL）」で必ずサイトへ誘導
- **さらに末尾へ「▼あわせて読みたい」として関連記事2本のURLを付ける**（回遊を作るため）。
  選ぶ基準は①その記事から内部リンクしている実在記事 ②**CTA設置済みの収益記事を優先**
  ③文脈が自然につながること。3本以上は宣伝色が強くなるので付けない
- 注意：記事本文のコピペ転載は禁止（Google重複判定防止のため必ず書き下ろす）
- 文体：です・ます調（noteの読者層に合わせる。サイト記事のだ・である調と変える）
- タイトル：記事タイトルとは別の、noteで引きのある問いかけ型
  （例：「マッチングアプリで結婚した人、実は4組に1組って知ってました？」）

過去分の削除は不要。人間が投稿済みのものを判断して使う。

## タイトルCTR最適化（2026-07-26追加・Phase 2の一部）

gsc_data.jsonの by_query_page から、**平均掲載順位10位以内なのにクリック率が2%未満**の
クエリ×ページを抽出する。該当があれば、そのページのタイトル・meta descriptionを
以下の観点で改善する（1回の実行で最大2記事）。

- 数字・年号・【】等でSERP上の視認性を上げる
- 検索クエリの語をタイトル前方に置く
- 「結論が中にある」ことが伝わる文言にする（〜を徹底検証／〜の答え 等）
- 誇大化はしない（クリック後の失望は直帰としてマイナス評価になる）
- 変更したら run_log.md に新旧タイトルを記録し、2週間は同一記事を再変更しない

## クエリカニバリゼーションの自動検知（2026-07-26追加・Phase 2の一部）

gsc_data.jsonの by_query_page で、**同一クエリに複数の自サイトページが表示されている**
組み合わせを抽出する。検出した場合：

1. どちらのページがそのクエリの「正規ページ」かを判断する
   （専用記事＞総合記事。例：「with 結婚率」なら with専用記事が正規）
2. 非正規側のページから正規ページへ、そのクエリを明示したアンカーテキストで
   内部リンクを追加する（過去の実績：success-rate-data → with-seriousness-data で解消）
3. run_log.md に「カニバリ検知・正規化」として記録する
4. 2週間後も解消しない場合のみ、非正規側の該当セクションを要約に圧縮して
   正規ページへ誘導する形に書き換える（段階的対応・いきなり削らない）

## ミドル競合クエリのSERP網羅チェック（2026-07-26追加・Phase 2の一部）

Phase 2で強化対象を選定する際、**平均掲載順位11〜30位で2週間以上足踏みしている記事**に限り、
追記の前に以下を行うこと。

1. 対象クエリでWebSearchを実行し、上位表示されている記事のタイトル・要約から
   「上位陣が共通してカバーしているトピック」を洗い出す
2. 自記事に欠けているトピックを特定し、それを埋めるセクションを追記する
   （ただし記事の主語・切り口は変えない。網羅は手段であり、

適用範囲の限定（重要）：
- 競合が弱いクエリ（無料ブログ等しか上位にいない）には適用しない（過剰品質）
- 50位以下の記事にも適用しない（まず基礎評価待ち）

## アフィリエイト原理原則・補完ルール（2026-07-26制定）

### 案件選定の定量基準
アフィリエイト案件を記事に組み込む優先順位は、単価だけでなく以下の積で判断する。

　期待値 ＝ 単価 × 承認率 × 成約しやすさ（無料登録＞資料請求＞有料契約）

- 高単価でも承認率が低い・成果地点が遠い案件（有料契約のみ等）は優先度を下げる
- 承認率が公表されている案件（例：マリッシュ90%超）は同単価帯で最優先
- 同一サービスが複数ASPにある場合は、単価と承認率の両方を比較して選ぶ

### 成約導線の距離設計
読者が記事からLP（案件ページ）に到達するまでのクリック数を最小にする。

- 収益記事（CTA設置記事）へは、集客記事から1クリックで到達できる内部リンクを置く
- 「集客記事→ハブ→収益記事→LP」のような3段以上の導線は作らない
　（各段で読者は半減する。集客記事から直接収益記事へ繋ぐ）
- CTAは「読者の疑問が解消された直後」（料金表の後・比較結論の後）に置くのが原則。
　疑問が残っている段階のCTAは踏まれない

### 被リンク資産の方針
被リンクは自動生成できない唯一の要素のため、「リンクされやすい記事」を意図的に持つ。

- データ集計型記事（success-rate-data・kekkon-okane-data等の統計まとめ）は
　note書き手・他ブログが「出典」として貼りやすい型。各クラスタに最低1本置く
- 新クラスタを作る際は、商品レビューだけでなく「そのジャンルの相場・統計ハブ」を
　必ずセットで作る（例：探偵クラスタのtantei-erabikata料金相場）
- note（Noe結婚設計室）はこのデータ記事への導線を優先的に張る

### プラットフォーム依存リスク（記録）
本サイトの依存先と、障害時の影響範囲を記録しておく。

- GitHub Pages（ホスティング）：無料枠。商用利用の規約変更・帯域制限リスクあり。
　収益が月5万円を超えたらCloudflare Pages等への移行を検討事項とする
- afb/A8（ASP）：案件終了リスクは常にある（Pairs/with/Omiai撤退の実績）。
　1案件への収益依存が60%を超えたら代替案件の受け皿を先に用意する
- Google検索（集客）：note・指名検索の育成が唯一のヘッジ。集客の多角化は
　note→（安定後）X→の順で段階的に進める

## リスク分散ルール：クラスタ依存の上限（2026-07-26制定）

1ドメイン集中戦略（軸展開モデル）は、コアアップデート等のペナルティが
ドメイン単位ではなく「クエリカテゴリ単位」で来ることが多いため、
クラスタを分散させておくこと自体がリスクヘッジになる。ただし放置すると
特定クラスタが肥大化しすぎる恐れがあるため、以下を守ること。

- **YMYL厳格領域（保険・住宅ローン・探偵・離婚・資産運用）は
  各クラスタ5〜8記事を上限とし、それ以上深追いしない**。
  この上限に達したクラスタへの新規追加リクエストがキューにあっても、
  優先度を下げ、婚活アプリ本体・データ記事・地域ガイドクラスタを
  先に厚くすること
- 新規テーマを追加する際は、既存クラスタの記事数を
  `ls articles/ | wc -l` 相当の確認ではなく、テーマごとに
  `agent/affiliate_targets.md` の受け皿記事欄を数えて把握し、
  YMYL厳格領域が既に上限に近い場合は該当テーマの追加を1本に絞る
- `agent/run_log.md` に月1回、クラスタ別のGSC表示回数シェアを
  記録する（Phase 2実行時、可能な範囲で）。特定クラスタが
  サイト全体の表示回数の50%を超えて依存している場合は
  `agent/AGENT.md` にその旨を警告として書き残す
- 目的：単一クラスタへの依存を防ぎ、規制変更・アルゴリズム更新が

  法令遵守・不安煽り禁止等の既存ルールを引き続き徹底する）

## Phase 2：データ駆動の記事強化（稼働中）

`agent/gsc_data.json` が存在する場合、キュー記事の生成に**加えて**以下を実行する（詳細ルールは `agent/phase2_gsc.md`）：

1. `agent/gsc_data.json` を読む（過去28日のクエリ×ページデータ。ローカルの週次ジョブが日曜夜に更新する）
2. **強化対象の選定**：表示回数5回以上 かつ 平均掲載順位11〜50位 のクエリを抽出する
3. 対象クエリに対応する記事（pageのURLから特定）に、そのクエリの検索意図に合うセクションを追記する
   - 1回の実行で強化するのは最大2記事・1記事あたり追記2セクションまで
   - タイトル・meta descriptionにクエリ語が入っていなければ前方に組み込む（og:title/JSON-LDも同期）
   - 順位10位以内のクエリの記事は触らない
   - `agent/run_log.md` を確認し、2週間以内に強化済みの記事はスキップする
4. **新規需要の発見**：表示されたクエリに対応する記事が存在しない場合、`keyword_queue.json` に `status: "proposed"` で追加する（自動生成はしない・人間レビュー用）
5. 実行結果（生成・強化した記事、対象クエリ、判断理由の要約）を `agent/run_log.md` に追記する

`gsc_data.json` が存在しない・14日以上古い場合はPhase 2をスキップし、その旨を run_log.md に記録する。
