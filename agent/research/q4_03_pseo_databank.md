## 前提: なぜ「データバンク型pSEO」が2026年時点で成立するのか

依頼主の言う「観光庁のデータをまとめてデータバンクにする」は、英語圏では **Programmatic SEO（pSEO）× Public Open Data × Linkable Asset** の3つが交差する定番戦術で、それぞれに独立した文献体系がある。日本語圏では pSEO は「翻訳記事のみ」、公的データ活用は「データジャーナリズム」文脈で語られ、SEO文脈と接続されていないため、**接続部分がまるごと空白**になっている。これが依頼主の直感の正体である。

2026年時点で押さえるべき環境変化は3つ：

1. **Google の scaled content abuse ポリシー**（2024年3月のspam updateで "spammy auto-generated content" から改名・拡張）が、「AI製か人力かを問わず、大量に作られた低価値ページ」を明示的に対象にした。テンプレに変数を差し替えただけのページは最も分かりやすい違反例。（[Google Search Central: Spam Policies](https://developers.google.com/search/docs/essentials/spam-policies) / [Scaled Content Abuse解説](https://www.layer3labs.io/guides/scaled-content-abuse)）
2. **2025年3月コアアップデート**以降、「人間ではなく検索エンジン向けに作られた大量のプログラマティックページ」の下落が顕著に観測された。（[Programmatic SEO Trends 2026](https://www.tryvizup.com/blog/programmatic-seo-trends-2026)）
3. 逆に、**ページごとに固有データを持つpSEO**は依然として機能している。生き残りの条件が「テンプレの巧さ」から「データの独自性」に完全に移った。（[Kevin Indig: The changing dynamic of programmatic SEO](https://www.growth-memo.com/p/the-changing-dynamic-of-programmatic)）

**noe-matchの立ち位置**: 記事258本・ドメイン2ヶ月・個人運営。つまり「1万ページ生成」は最初からやってはいけない側。本レポートの手法は **「数百ページ規模で、1ページあたりの固有データ密度を極大化する」** 方向に最適化して読むこと。

## 3-01. データバンク型プログラマティックSEO（Data-Backed Programmatic SEO）

- **一言で**: 「1つの信頼できるデータセット」×「N個の切り口」で数百ページを掛け算生成し、各ページに一次データを1つ以上持たせる、pSEOの中核形。
- **海外での出典**:
  - https://backlinko.com/programmatic-seo
  - https://practicalprogrammatic.com/examples
  - https://seranking.com/blog/programmatic-seo/
  - https://www.growth-memo.com/p/the-changing-dynamic-of-programmatic
- **仕組み／なぜ効くか**: 成功しているpSEOはすべて3要素を共有する ——(a) 反復するキーワードパターン、(b) ページごとに差異を作る構造化データセット、(c) その全バリエーションに答えるテンプレート。Zapierは「アプリ×アプリ」の組合せで59万ページ、Wiseは「通貨×通貨」、Nomad Listは「都市×生活コスト/回線速度/気候/安全度」、Zillowは「地域×不動産市場データ」。共通するのは**テンプレの外側にデータの井戸がある**こと。データの井戸がないpSEOは、2025年以降ほぼ確実に潰れる。
- **具体手順**:
  1. データの井戸を1つ決める（noe-matchなら既存の「自治体43件データバンク台帳」がそれ）。井戸は「行数 × 列数」で語れる形にする。
  2. 検索需要のあるキーワードパターンを見つける（例: 「{自治体名} 婚活支援」「{自治体名} 結婚新生活支援事業」「{都道府県} 平均初婚年齢」）。
  3. 「行 = ページ1枚」の主軸を決める。自治体を主軸にするか、制度を主軸にするか、年次を主軸にするかで総ページ数が変わる。
  4. テンプレを1枚作り、**そのテンプレで最も情報量の少ない行**（データが最も薄い自治体）を先にレンダリングして、それが単体記事として成立するか目視する。成立しなければテンプレを直すのではなく、**データの列を増やす**。
  5. 段階リリース（→3-06）で50〜100ページずつ出す。
  6. インデックス率と滞在時間で次のバッチを出すか決める。
- **日本での言及度**: **低**（翻訳記事は存在するが実践論が無い）。【検索実施】 検索クエリ: `プログラマティックSEO 日本語 解説 大量ページ生成 データベース型SEO`。結果は Ahrefs日本語版（https://ahrefs.jp/blog/content-marketing/programmatic-seo/ ）、Ranktracker日本語版、01GROWTH（https://www.01growth.com/post/what-is-programmatic-seo ）など、**ほぼ全てが海外記事の翻訳か翻訳の要約**。日本の個人メディアが公的オープンデータを井戸にした具体事例の記事は1件も出てこなかった。「データベース型SEO」という語は日本のSEO業界に存在するが、これは主に食べログ/SUUMO型の巨大DBサイトの話で、**個人が公的データで井戸を作る**という発想は日本語圏に流通していない。
- **noe-match適用度**: **A**。すでに「自治体43件の一次確認済み台帳」という井戸を持っていて、build_articles.py という生成器も持っている。あと足りないのは「井戸の列を増やす」ことと「段階リリースの規律」だけ。想定工数: 台帳の列拡張に20〜40時間（自治体を43→300前後に拡張するなら別途）、テンプレ改修に8時間。
- **リスク・反証**: 井戸の行数（43自治体）に対して列数が少ないと、ページが薄くなり scaled content abuse 判定に近づく。**行を増やす前に列を増やす**のが鉄則。また、自治体の制度は年度で変わるため、更新できない量まで行を増やすと3-23の decay 地獄になる。

## 3-02. head/torso/tail のテンプレ三層設計（Head-Torso-Tail Template Architecture）

- **一言で**: 全ページを同じテンプレで出すのではなく、検索ボリューム帯ごとにテンプレの「厚み」を変え、head は手作業、torso は半自動、tail は完全自動にする。
- **海外での出典**:
  - https://seomatic.ai/blog/programmatic-seo-keyword-research
  - https://www.madx.digital/learn/programmatic-seo-keyword-research
  - https://untalkedseo.com/pseo-keyword-research/
- **仕組み／なぜ効くか**: pSEOの失敗の典型は「1テンプレ全ページ」。head（月間数千〜）は競合が本気で作り込んでいるのでテンプレでは勝てず、tail（月間0〜10）は競合が居ないのでテンプレで十分勝てる。同じ投下工数を全ページに均等配分すると、head は負け、tail は過剰投資になる。層を分けることで**限られた個人の工数を勝てる場所に集中**できる。
- **具体手順**:
  1. キーワード群をボリューム帯で3分割する（head: 1,000+/月、torso: 100〜1,000、tail: 〜100）。日本のニッチ婚活領域なら head=500+、torso=50〜500、tail=〜50 くらいに閾値を下げる。
  2. head は「テンプレを使わない完全手書き記事」に格上げする。pSEOの対象から外す。
  3. torso は「テンプレ + 手動の独自セクション（体験談・独自解釈・比較表）」のハイブリッド。テンプレの穴埋めのうち1〜2ブロックだけを人力にする。
  4. tail は完全自動。ただし tail 同士を hub ページ（→3-21）で束ねて、hub を torso 扱いにする。
  5. head→torso→tail の順に内部リンクが流れるようにする。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語SEOでは「ビッグワード/ミドルワード/スモールワード」という語彙は普及しているが、それを**テンプレの厚みの設計変数として使う**という話は見たことがない。日本語では「ロングテール戦略」が「とにかく記事数を増やす」に矮小化されている。要検証クエリ案: `SEO ヘッド トルソー テール テンプレート 使い分け`。
- **noe-match適用度**: **A**。258記事のうち、ツール17本・データ記事25本は既に事実上の torso/tail 構造になっている可能性が高い。既存記事を3層にラベリングし直すだけで、次の投資先が決まる。想定工数: 既存258本のラベリングに6〜10時間（GSCデータがあれば半自動化可）。
- **リスク・反証**: 新規ドメイン（2026年6月開設）ではGSCに十分なクエリデータが溜まっていないため、ボリューム帯の判定が推測ベースになる。開設3〜6ヶ月は「仮ラベル」で運用し、データが溜まってから再分類する前提で。

## 3-03. キーワード修飾子マトリクス（Keyword Modifier Matrix / Two-Modifier Pattern）

- **一言で**: 「head term + 修飾子A + 修飾子B」の2次元掛け算でページ候補を機械的に列挙する。キーワードリサーチを「2,000回」ではなく「1回」で終わらせる技法。
- **海外での出典**:
  - https://www.madx.digital/learn/programmatic-seo-keyword-research
  - https://hashmeta.com/blog/how-to-choose-the-right-variables-for-programmatic-seo-a-strategic-guide/
  - https://seranking.com/blog/programmatic-seo/
- **仕組み／なぜ効くか**: 「`[x] integrations` というhead termに2,000アプリを掛けると、1文字も書かないうちに2,000ページの候補ができる。リサーチは2,000回ではなく1回で済む」——これがpSEOの経済性の核心。修飾子を2軸にすると候補数が指数的に増えるので、**軸の選定が事実上の事業戦略**になる。良い軸の条件は (a) 値が有限で列挙可能、(b) 各値に固有データが紐づく、(c) 検索者が実際にその語で検索する。
- **具体手順**:
  1. head term を1つ書く（例: 「結婚新生活支援事業」「婚活支援」「結婚祝い金」）。
  2. 修飾子A候補を列挙する（地理: 47都道府県 / 市区町村1,741、年次: 2020〜2026、年齢帯、世帯年収帯）。
  3. 修飾子B候補を列挙する（intent: 条件・金額・申請方法・いつまで・対象外、比較: vs他制度）。
  4. A×Bの表を作り、各セルについて「固有データが埋まるか？」を○×で判定する。**×のセルはページを作らない**（これが3-22のファセット設計と直結する）。
  5. ○セルだけを候補リストに落とし、検索需要（実測 or 推定）で並べ替える。
  6. 上位から3-06の段階リリースに投入。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語では「キーワードの掛け合わせ」という語はあるが、それは「共起語ツールで拾う」レベルの話で、**修飾子軸を事前設計してページ空間そのものを定義する**という発想は流通していない。要検証クエリ案: `キーワード 修飾子 マトリクス SEO ページ設計 掛け合わせ 軸`。
- **noe-match適用度**: **A**。婚活・結婚領域は修飾子軸が非常に豊富（自治体 × 制度 × 年齢 × 年収 × 世帯形態 × 年次）。既存の43自治体台帳を軸1、制度種別を軸2にするだけで即座に数百セルが立つ。想定工数: マトリクス設計に4〜8時間、○×判定に台帳の列数次第で8〜16時間。
- **リスク・反証**: 軸を掛けすぎると「1741市区町村 × 7制度 × 5年次 = 6万ページ」のような、個人が絶対に品質保証できない空間ができる。**○×判定を厳格にやること自体が唯一の防波堤**。またgeo修飾子は日本では「東京都◯◯区」「◯◯市」の表記ゆれが激しく、正規化コストが高い。

## 3-04. ページごとの固有 value-add 強制注入（Unique Value-Add per Page）

- **一言で**: テンプレの各ページに「そのページにしか存在しない情報」を最低N個埋め込むことを、生成器のバリデーションとして強制する仕組み。
- **海外での出典**:
  - https://www.seoguru.ai/blog/how-to-build-programmatic-seo-pages-that-do-not-get-flagged-as-thin
  - https://customgpt.ai/programmatic-seo-quality-checklist/
  - https://seomatic.ai/blog/programmatic-seo-mistakes
  - https://www.tryvizup.com/blog/programmatic-seo-trends-2026
- **仕組み／なぜ効くか**: 「都市名や商品名を差し替えただけで、URLごとの実質が無い薄いテンプレページ」が scaled content abuse の最も分かりやすい違反例であり、Googleの分類器はこのパターンを素早く検出するよう訓練されている。逆に言えば、**「差し替えた変数の外側に、そのページ固有の実質がいくつあるか」がそのまま生存確率**になる。これを人間のレビューではなく **ビルド時のアサーション** として実装するのが英語圏の実務。
- **具体手順**:
  1. 「固有value-add」の定義を型として列挙する。例: ①そのページ固有の数値（一次データ）、②その数値から導いた独自解釈文（全国平均との比較文など）、③固有の一次ソースURL、④固有の日付（制度の申請期限など）、⑤固有の図表、⑥固有のFAQ（そのページのデータに答える形）。
  2. build_articles.py に「1ページあたり ①〜⑥のうち最低4種類・固有トークン数◯%以上」というアサーションを追加する。
  3. **テンプレ由来の固定文とページ固有文の比率**を計測する関数を書く。固有文が全体の30%を下回るページはビルドを失敗させる（=公開させない）。
  4. 全ページ間の n-gram 重複率を計測し、重複率が閾値を超えるページ対を検出してレポートする。
  5. アサーションに落ちたページは「行を消す」のではなく「列を足す」で救済する。救済できないならそのページは作らない。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語では「低品質コンテンツを作らない」という精神論はあるが、**それを生成器のCIアサーションとして数値実装する**という話は皆無に近い。ここは日本語圏の完全な空白。要検証クエリ案: `プログラマティックSEO 薄いコンテンツ 判定 固有性 チェック 自動化`。
- **noe-match適用度**: **A**。Python生成器を既に持っているので、実装コストが最も安く効果が最も大きい手法。想定工数: 8〜16時間（アサーション実装 + 既存258記事への遡及チェック）。
- **リスク・反証**: 閾値を厳しくしすぎると tail ページがほぼ全滅する。最初は「レポートするだけ・ビルドは通す」で運用し、分布を見てから閾値を決めるべき。また n-gram 重複率はテンプレのボイラープレート（免責文・プロフィール・共通FAQ）で押し上げられるので、比較対象から共通ブロックを除外する必要がある。

## 3-05. Google spam policy 準拠設計（Scaled Content Abuse Compliance）

- **一言で**: 「大量生成そのもの」は違反ではなく「大量生成 × 低価値 × ランキング操作目的」の3点セットが違反、という条文構造を理解して設計に落とす。
- **海外での出典**:
  - https://developers.google.com/search/docs/essentials/spam-policies
  - https://www.layer3labs.io/guides/scaled-content-abuse
  - https://bulkbase.ai/seo/scaled-content-abuse-googles-policy-enforcement-how-to-stay-compliant-in-2026
  - https://www.semrush.com/blog/google-completes-spam-update-rollout/
- **仕組み／なぜ効くか**: scaled content abuse は「ユーザーを助けるためではなく、主に検索順位を操作するために多数のページを生成すること」を対象とし、**そのページがAI製か人力か混合かを問わない**。2024年3月のspam updateで "spammy auto-generated content" から改名・拡張され、名称自体が「価値なきスケール」を狙い撃ちしていることを明示している。2026年時点で本トピックに関する新ポリシーの発表はない（3月・6月にspam updateは実施）。重要なのは、**Googleがアルゴリズム的enforcementと手動対策の両方を使う**こと、そして「単に成績が悪いコンテンツ」は対象外だと明記されていること。
- **具体手順**:
  1. 生成する全ページについて「このページは検索エンジンが無かったとしても作るか？」を1行で書けるようにする（書けないページは作らない）。これが「ユーザーを助けるため」の内部証跡になる。
  2. ポリシーの条文（英語原文）を build_articles.py のドキュメントに転記し、生成ルールをそこに紐づける。
  3. 「大量生成」を隠さない。逆に、データ出典・更新日・集計方法をページに明示する（→3-25）。透明性は E-E-A-T と scaled content abuse の両方に効く。
  4. 手動対策を受けた場合の想定復旧手順（該当ページ群のnoindex→削除→再審査請求）を事前に文書化しておく。43自治体規模なら復旧可能だが、6万ページ規模だと復旧不能になる。
  5. spam update のロールアウト日をカレンダーに記録し、トラフィック変動と突き合わせられるようにしておく。
- **日本での言及度**: **中**。【未検索・推定】 「スパムポリシー」「大量生成コンテンツ」自体は日本語SEOメディアでも報道ベースで触れられる。ただし **原文の条文を設計制約として実装に落とす**レベルの記事は見たことがない。日本語記事の大半は「AI記事の大量生成は危険」という一般論で止まっている。要検証クエリ案: `Google スパムポリシー 大量生成 スケールされたコンテンツの不正使用 原文`。
- **noe-match適用度**: **A**（実装工数はほぼゼロ、判断基準として必須）。想定工数: 2〜4時間（条文読み込みと設計ドキュメント化）。
- **リスク・反証**: 「ポリシーを読んだから安全」ではない。実際の判定はアルゴリズム分類器であり、条文遵守と分類器の出力は一致しない。**条文遵守は必要条件であって十分条件ではない**。最終防衛線は3-04と3-06の実測。

## 3-06. 段階リリース＋インデックス率ゲート（Staged Rollout with Indexation Gate）

- **一言で**: 全ページを一気に公開せず、50〜200ページずつバッチで出し、**前バッチのインデックス率が閾値を超えるまで次バッチを出さない**。
- **海外での出典**:
  - https://www.tryvizup.com/blog/programmatic-seo-trends-2026
  - https://www.seotakeoff.com/blog/automated-seo-publishing-qa-checklist
  - https://customgpt.ai/programmatic-seo-quality-checklist/
  - https://thestacc.com/blog/programmatic-seo-case-study/
- **仕組み／なぜ効くか**: 2026年時点の実務パターンは「1バッチ50〜200ページ、バッチ間でインデックス状況を監視」。より細かい運用では「パイロットバッチ100〜500ページをGSCに提出し、2〜4週間監視、30日以内に70%以上インデックスを目標」。**インデックス率が50%を下回ったら拡大を止める**——Googleが既に拒否しているページ群をスケールしてはいけない、というのがこの手法の本質。一気に1万ページ出すと、失敗したときに「どのバッチが悪かったか」が分からず、サイト全体の品質評価を巻き添えにする。
- **具体手順**:
  1. 生成候補ページを優先度順に並べ、バッチID（batch_001, batch_002...）を付与して台帳に持つ。
  2. batch_001（noe-matchの規模なら30〜50ページが妥当）だけをsitemapに載せて公開する。
  3. 2〜4週間、GSCの「ページ」レポートでインデックス済み/未インデックスの比率を計測する。
  4. ゲート条件を事前に定義: 例「30日で70%以上インデックス」「CTR 1.5%以上」「平均エンゲージメント時間45秒以上」。
  5. ゲート通過 → batch_002 公開。ゲート未達 → **バッチを増やさず、既存バッチの列を増やす（データ追加）** に投資を戻す。
  6. バッチごとにsitemapファイルを分ける（→3-14）と、インデックス率がGSCで直接読める。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語SEOでは「記事は毎日何本出すべきか」という更新頻度の議論はあるが、**インデックス率をゲート条件にして公開を止める**という規律の話はほぼ流通していない。要検証クエリ案: `SEO 段階的公開 バッチ インデックス率 しきい値 大量ページ`。
- **noe-match適用度**: **A**。ドメイン開設2ヶ月・個人運営という条件では、これが最も致命傷を避ける手法。想定工数: バッチID付与とsitemap分割の実装に8〜12時間。
- **リスク・反証**: 新規ドメインは総じてインデックスが遅いため、「70%/30日」は初期には達成不能な可能性が高い。**閾値は自サイトの既存記事の実績インデックス率をベースラインにして相対設定する**べき。絶対値をそのまま輸入すると、正常なのに止め続けることになる。

## 3-07. noindex→index の品質昇格パイプライン（Quality Promotion Pipeline）

- **一言で**: 新規生成ページは全て `noindex` で公開し、固有性ゲートと最低情報量ゲートを通過したものだけを自動で `index` に昇格させる。
- **海外での出典**:
  - https://www.tryvizup.com/blog/programmatic-seo-trends-2026
  - https://www.seoguru.ai/blog/how-to-build-programmatic-seo-pages-that-do-not-get-flagged-as-thin
  - https://hashmeta.com/blog/how-to-maintain-indexation-quality-on-huge-websites/
- **仕組み／なぜ効くか**: 「新規ページは、固有性ゲートと最低文字数閾値を通過するまで noindex で開始し、通過したら CMS のフィールド更新で自動的に index に切り替える。これによりGoogleのクローラーは品質基準を満たしたページにしか遭遇しない」。3-06が「時間軸のゲート」なのに対し、これは「ページ単位のゲート」。両者は直交するので併用できる。**Googleに見せる前に落とす**のが要点で、一度低品質でインデックスされてから直すより圧倒的に安い。
- **具体手順**:
  1. テンプレに `<meta name="robots" content="noindex,follow">` を出し分けるフラグを入れる（`follow` は残す。内部リンクは流したいため）。
  2. 台帳に `quality_score` 列を持たせ、3-04のアサーション結果を数値で入れる。
  3. `quality_score >= 閾値` のときだけ index にする、をビルド時に評価する。
  4. sitemap には index なページだけを載せる（noindex ページをsitemapに載せるのは矛盾シグナル）。
  5. noindex のまま滞留しているページ数を定期レポートし、「データが足りない行」のリストとして扱う → データ収集タスクのバックログにする。
  6. **昇格後に降格させることはしない**（index→noindexの往復はクロールを浪費するだけ）。降格が必要なら3-24の剪定に回す。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語では noindex は「重複ページの除外」「カテゴリページの整理」の文脈でしか語られず、**品質パイプラインのステート**として使う発想は見当たらない。要検証クエリ案: `noindex 品質基準 自動 昇格 大量ページ SEO 運用`。
- **noe-match適用度**: **A**。build_articles.py に数行足すだけで実装できる。想定工数: 4〜8時間。
- **リスク・反証**: `noindex` を長期間放置したページはGoogleが最終的にクロールを止め、昇格させても再発見が遅れる。**noindex滞留は「一時的な状態」であって「永続的な物置」にしてはいけない**。滞留90日でアラートを出す運用を推奨。また、静的サイトでは「CMSのフィールド更新」が使えないので、台帳→ビルド→再デプロイのサイクルになる（→3-26）。

## 3-08. Index bloat の剪定と「正しい削除順序」（Index Bloat Pruning / Correct Removal Order）

- **一言で**: 低価値ページを索引から抜くときの順序は **「クロール許可 → noindex → 索引から落ちるのを待つ → その後 robots.txt でブロック」**。順序を間違えると永久に索引に残る。
- **海外での出典**:
  - https://searchengineland.com/guide/index-bloat
  - https://www.greenlanemarketing.com/resources/articles/how-to-find-and-fix-index-bloat-issues
  - https://pitchbox.com/blog/how-to-improve-seo-by-tackling-index-bloat-and-crawl-waste/
  - https://hashmeta.com/blog/how-to-maintain-indexation-quality-on-huge-websites/
- **仕組み／なぜ効くか**: index bloat は「索引されているが十分なトラフィックを生まない」URLが多い状態で、サイトの品質評価を希釈し、大規模サイトではクロール予算を浪費し、重要ページの順位を抑圧する。剪定の際の**最頻出の失敗が「いきなり robots.txt でブロックする」**こと。robots.txt でブロックすると Googlebot がページを取得できないため、そこに書かれた noindex も canonical も**読めない**。結果、URLは索引に残り続ける（しかもスニペットなしの状態で）。正しい順序は「まずクロールさせて noindex を読ませ、索引から落ちたのを確認してから、将来のクロール節約のために robots.txt でパターンをブロックする」。大規模サイトでは、**最も剪定したいページほどクロール頻度が低い**ため、索引から落ちるまで数週間〜数ヶ月かかる。
- **具体手順**:
  1. GSCの「ページ」レポートを索引ステータス別にエクスポートし、「索引済み かつ 過去90日クリック0」のURLリストを作る。
  2. そのリストを「統合する / リフレッシュする / noindexにする / 削除(410)する」の4アクションに分類する（→3-23の decay triage と同じ分類軸）。
  3. noindex にすると決めたURLは、**robots.txt を触らずに** `noindex` を入れる。
  4. GSCの「除外 > noindexタグにより除外されました」の件数が想定数に達するまで待つ（数週間〜）。
  5. 完全に落ちたのを確認してから、必要ならそのURLパターンを robots.txt でブロックする。
  6. 削除の場合は 404 ではなく **410 Gone** を返す方が索引除去が速い（静的サイトでは実装が難しい → 3-26）。
- **日本での言及度**: **低**。【検索実施】 検索クエリ: `インデックス肥大化 index bloat 日本語 SEO 対策 コンテンツプルーニング`。日本語の一次的な解説はほぼMozの翻訳記事2本（Web担当者Forum、https://webtan.impress.co.jp/e/2025/12/15/51827 / https://webtan.impress.co.jp/e/2025/12/22/51828 ）に集約されており、**日本人SEOが自分の言葉で書いた実践記事はほとんど検索に出てこない**。しかも検索結果には Amazon Aurora のDBインデックス肥大化の記事が混入するほど、SEO文脈の日本語コンテンツが薄い。**「正しい削除順序」に言及した日本語記事は1件も確認できなかった**——これは本レポート中で最も言及が薄い項目の一つ。
- **noe-match適用度**: **B**。258記事の現段階では index bloat は深刻ではないが、pSEOでページを増やす**前に**手順を確立しておく価値が高い。想定工数: 手順書作成2時間、実運用は四半期ごとに2〜4時間。
- **リスク・反証**: 小規模サイトでは「クロール予算」はほぼ問題にならない（Googleは中小サイトのクロール予算を心配する必要はないと明言してきた）。noe-matchの規模で効くのは**クロール予算ではなく「サイト全体の品質評価の希釈」**の方。この区別を混同すると、不要な最適化に時間を溶かす。

## 3-09. 「Crawled – currently not indexed」のトリアージ（Crawl-Not-Indexed Triage）

- **一言で**: GSCの「クロール済み – インデックス未登録」は技術問題ではなく**品質シグナル**として読み、原因を4分類してそれぞれ別の対処をする。
- **海外での出典**:
  - https://www.mjwmedia.com/crawl-budget-google-not-indexing-pages/
  - https://searchengineland.com/guide/index-bloat
  - https://hashmeta.com/blog/how-to-maintain-indexation-quality-on-huge-websites/
  - https://www.tryvizup.com/blog/programmatic-seo-trends-2026
- **仕組み／なぜ効くか**: このステータスは「Googleは見に来た。読んだ。そのうえで索引に入れる価値がないと判断した」という意味であり、**pSEOの品質不足を最も早期に、最も正直に教えてくれる指標**。robots.txt やサーバーエラーとは根本的に違う。pSEOでは「クロールされたが索引されない」比率が、そのままテンプレの生存確率のプロキシになる。
- **具体手順**:
  1. GSC「ページ」→「クロール済み – インデックス未登録」をエクスポートする。
  2. URLパターンで分類する（テンプレA由来 / テンプレB由来 / タグページ / ページネーション / その他）。
  3. パターンごとの比率を出す。**特定テンプレだけ比率が異常に高いなら、そのテンプレの固有value-addが不足している**（→3-04に戻る）。
  4. 全テンプレで一様に高いなら、ドメイン全体の評価（新規ドメイン、被リンクゼロ）が原因の可能性が高い → ページを増やすのではなく3-18/3-19のリンク獲得に投資を移す。
  5. タグ/ページネーション由来が多いなら、それは意図通り（索引不要）なのでノイズとして除外設定する。
  6. 同じURLが90日以上このステータスなら、3-08の剪定候補に回す。
- **日本での言及度**: **低**。【未検索・推定】 「クロール済み – インデックス未登録」の日本語記事は多数存在するが、内容は「サイトマップを送りましょう」「内部リンクを増やしましょう」という汎用対処に終始しており、**テンプレ別に比率を出して品質シグナルとして読む**という運用法は流通していない。要検証クエリ案: `クロール済み インデックス未登録 テンプレート別 比率 品質シグナル`。
- **noe-match適用度**: **A**。無料・即実行可能・pSEO投資判断の中核指標。想定工数: 初回分析2〜4時間、以後は月1時間。
- **リスク・反証**: 新規ドメインでは「まだ順番が来ていないだけ」のページが大量にこのステータスに入るため、**開設6ヶ月未満のサイトでは品質シグナルとして読むと過剰反応になる**。ドメイン年齢を考慮した読み方が必要。

## 3-10. GSC Crawl Stats ＋ ログファイル分析（Crawl Budget Forensics）

- **一言で**: GSCのクロール統計は「集計値」、サーバーログは「真実」。両者を突き合わせて、Googlebotがどのテンプレに何%のクロールを割いているかを実測する。
- **海外での出典**:
  - https://www.oncrawl.com/general-seo/google-crawl-stats-report-log-file-analysis/
  - https://gautamkhorana.com/blog/log-file-analysis-crawl-budget-large-sites/
  - https://www.adamhodson.com/log-file-analysis-to-find-wasted-crawl-budget/
  - https://edwardbate.com/resources/google-search-console-crawl-stats-guide/
- **仕組み／なぜ効くか**: 「GSCは『昨日Googleが500ページをクロールした』と教える。ログは『どの500ページを、どの順で、どの速度で、どのステータスコードで』を教える」。GSCのクロール統計で読むべきは4つ——(a) Googlebotヒットの多いホスト、(b) 返したステータスコードの内訳（非200がクロール予算の何%を食っているか）、(c) ファイルタイプ別（CSS/JS/画像がどれだけ食っているか）、(d) クロール目的（**Discovery=新規発見 か Refresh=既知の更新確認 か**）。この(d)が pSEO では特に重要で、**Discovery比率が落ちているなら新規ページの発見が止まっている**という早期警告になる。さらに、Googlebotのクロール量の急減はしばしば順位下落に先行し、ログの方がGSCより早く異常を示す。
- **具体手順**:
  1. GSC「設定 → クロールの統計情報」を開き、上記(a)〜(d)を毎月スクリーンショット or メモで記録する。
  2. 「クロールの目的」の Discovery/Refresh 比率を時系列で追う。新バッチ公開後に Discovery が跳ねなければ、発見されていない。
  3. 「レスポンス別」で非200の比率を見る。10%を超えたら要調査。
  4. ログが取れる環境なら、Googlebot（UA + 逆引き検証）のリクエストをURLパターン別に集計し、「テンプレ別クロール割当%」を出す。
  5. 「クロールされているが順位もクリックも無いパターン」＝クロールの浪費として、3-08の剪定候補にする。
  6. 「クロールされていない重要ページ」＝内部リンク不足として、3-20/3-21の対象にする。
- **日本での言及度**: **低**。【未検索・推定】 「クロールバジェット」の日本語記事は多いが、大半が「Googleが中小サイトは気にしなくていいと言っている」の紹介で終わる。**クロール目的（Discovery/Refresh）の比率を pSEO の発見指標として読む**という話は日本語圏でほぼ見ない。ログファイル分析自体も、日本ではエンタープライズSEO（Screaming Frog Log Analyser / Botify 等）の文脈でしか語られない。要検証クエリ案: `Googlebot クロール目的 検出 更新 比率 読み方`。
- **noe-match適用度**: **B**（GSC Crawl Stats は A、ログ分析は C）。**GitHub Pages ではアクセスログが一切取得できない**（→3-26）ため、ログファイル分析は現状の構成では実行不能。GSC Crawl Stats だけなら即実行可。想定工数: GSC定点観測は月30分。
- **リスク・反証**: GitHub Pages 構成では真のログが手に入らないという構造的制約がある。Cloudflare を前段に挟めばログが取れる（無料枠でもある程度）が、CNAMEの付け替え・キャッシュ設計の追加工数が発生する。ログ分析のために構成を変えるのは、ページ数が数千を超えてからで十分。

## 3-11. GSC Bulk Data Export → BigQuery（全量クエリデータの確保）

- **一言で**: GSCのUI/APIでは見えない「全行」のクエリ・URLデータを、毎日BigQueryに自動エクスポートして無期限に貯める。16ヶ月の保持制限を突破する唯一の公式手段。
- **海外での出典**:
  - https://support.google.com/webmasters/answer/12918484?hl=en
  - https://developers.google.com/search/blog/2023/06/bigquery-efficiency-tips?hl=en
  - https://www.searchenginejournal.com/google-search-console-data-bigquery-enhanced-analytics/496535/
  - https://www.seoclarity.net/blog/gsc-bulk-data-exports-for-enterprise-seo
  - https://raulrevuelta.com/en/how-to-export-search-console-data-bigquery/
- **仕組み／なぜ効くか**: GSCのUIは1,000行、APIも上限があるが、**Bulk Data Export はGSCアカウントで利用可能な全行を出せる**（APIと比べて2〜10倍のデータ量が見えるという報告）。さらにBigQuery側は保持無制限なので、GSCの16ヶ月制限を超えた複数年トレンド分析が可能になる。pSEOでは「テンプレ別・バッチ別に、どのロングテールクエリが取れ始めたか」を全量で見られることが決定的に重要で、サンプリングされた1,000行では**tailの実態が全く見えない**。
- **具体手順**:
  1. Google Cloud プロジェクトを作り、BigQuery API を有効化する。
  2. GSC の「設定 → 一括データエクスポート」でプロジェクトIDを指定する。データは24〜48時間で流入し始める。
  3. **エクスポートは設定日以降のデータのみ**（遡及しない）。つまり「今すぐ設定する」こと自体が最大のアクション。
  4. `searchdata_url_impression` テーブルに対し、URLパターン（テンプレ由来の接頭辞）でGROUP BYするクエリを書く。
  5. 「テンプレ別 × 月別 の impressions / clicks / 平均掲載順位 / ユニーククエリ数」を出す。**ユニーククエリ数**が pSEO の健康指標として最も有用（1ページが何種類の検索語を拾っているか＝tailの捕捉力）。
  6. クエリ課金に注意。パーティション（`data_date`）でフィルタしないと毎回全期間をスキャンする。
- **日本での言及度**: **低**。【未検索・推定】 「Search Console BigQuery エクスポート」の日本語記事は存在するが、大半が「設定手順」の紹介で止まり、**pSEOのテンプレ別評価に使う**という応用は流通していない。個人メディア運営者の文脈ではほぼ語られない（「BigQuery＝企業のもの」という心理的障壁がある）。要検証クエリ案: `Search Console 一括データエクスポート BigQuery 個人ブログ 活用`。
- **noe-match適用度**: **A**（設定だけなら1時間、価値は時間とともに増える）。**設定が遅れるほど過去データが永久に失われる**ので、優先度は「今日やる」。想定工数: 設定1〜2時間、分析クエリ作成に4〜8時間。BigQueryの無料枠（月1TBスキャン）でこの規模なら十分収まる。
- **リスク・反証**: Google Cloud の請求先アカウント設定が必要（無料枠内でも）。また、GSCのプロパティが「ドメインプロパティ」でないと粒度が落ちる場合がある。個人メディアで課金事故が怖いなら、予算アラートを1ドルで設定しておく。

## 3-12. IndexNow ＋ Google Indexing API の「限界の正確な理解」

- **一言で**: IndexNow は Bing/Yandex/Seznam/Naver には効くが **Googleには効かない**。Google Indexing API は **JobPosting と BroadcastEvent 限定**。この2つの事実を知らずに時間を溶かす人が非常に多い。
- **海外での出典**:
  - https://www.indexernow.com/google-indexnow
  - https://indexfast.co/blog/indexnow-vs-indexing-api
  - https://crawlwp.com/indexnow-vs-google-indexing-api-vs-sitemaps/
  - https://www.seopress.org/support/guides/how-to-use-the-indexnow-api-to-instantly-index-a-url-in-bing-and-yandex/
  - https://gracker.ai/seo-101/indexnow-seo-guide
- **仕組み／なぜ効くか**: IndexNow は「URLを追加/更新/削除したことを検索エンジンに即時通知する」オープンプロトコル。2026年時点で **Googleは非対応**（2021年のローンチ後に評価はしたが、ウェブ索引には採用しなかった）。一方 Google Indexing API は「JobPosting 構造化データを含むページ」または「VideoObject 内の BroadcastEvent を含むページ」のクロールにのみ使うべきものとGoogleが明示しており、ブログ記事や一般商品には使ってはいけない。既定クォータは1プロジェクトあたり1日200リクエスト（太平洋時間の深夜リセット）。
  それでも IndexNow に価値がある理由は、**Bing 経由の流入と、Bing インデックスを参照するAI検索系の露出**。Copilot/ChatGPT検索系がBingインデックスに依存する部分がある以上、Bingへの即時通知はGoogle以外の可視性に効く。
- **具体手順**:
  1. ランダムな32〜128文字の英数字キーを生成し、`https://noe-match.com/{key}.txt` にそのキーだけを書いたファイルを置く（GitHub Pages なら単にファイルをコミットするだけ。**リポジトリ直下に `28fb2874520d40719aa81fc0618e863b.txt` が既に存在しており、これは既にIndexNowキーが設置済みである可能性が高い** → 要確認）。
  2. Bing Webmaster Tools でサイトを登録し、IndexNow のキーを紐づける（BWT内でキー生成も可能）。
  3. デプロイ後のGitHub Actionsから、更新URLのリストをJSONで `https://api.indexnow.org/indexnow` にPOSTする。
  4. Google に対しては **IndexNow ではなく sitemap の lastmod（→3-13）と内部リンク**で発見させる。Indexing API を一般記事に使わない。
  5. Bing Webmaster Tools の「URL送信」（1日あたりの送信枠あり）も併用する。
  6. Bing側の索引数とクリック数を、Google側と分けて記録する。
- **日本での言及度**: **中**（ただし誤解込み）。【検索実施】 検索クエリ: `IndexNow 日本語 導入 SEO 効果 Bing 静的サイト`。鈴木謙一氏のブログ（https://www.suzukikenichi.com/blog/bing-and-yandex-support-indexnow-to-immediately-index-content-without-crawling/ ）や個人ブログの設定手順記事（https://socratetsu.jp/seo/bing_indexnow.html ）が複数ヒットし、「Googleは非対応」も正しく書かれている。**設定手順の日本語情報は十分にある**。一方で「Google Indexing API は JobPosting / BroadcastEvent 限定」という制約は、日本語圏では**依然として誤用が広まっている**（一般記事にIndexing APIを叩くWordPressプラグインが日本でも人気）。ここが実質的な空白。
- **noe-match適用度**: **B**。静的サイト × GitHub Actions なので実装は容易。ただし婚活領域の Bing シェアは小さいため、直接の収益インパクトは限定的。「AI検索経由の可視性の保険」として位置づけるのが正しい。想定工数: 2〜4時間。
- **リスク・反証**: IndexNow を「Googleに効く裏技」として売る日本語情報・ツールが存在するが、**これは端的に誤り**。また、Indexing API を JobPosting 以外に使うことは Google のガイドライン違反にあたり、最悪クォータ剥奪の対象になり得る。

## 3-13. sitemap lastmod の誠実運用（Lastmod Hygiene）

- **一言で**: lastmod の信頼性は **サイト単位のバイナリ判定**。1度でも嘘の日付を出すと、そのサイトの lastmod は丸ごと無視される。
- **海外での出典**:
  - https://www.digitalapplied.com/blog/xml-sitemap-lastmod-hygiene-illyes-directive-seo-2026
  - https://www.searchenginejournal.com/google-seo-tips-for-news-articles-lastmod-tag-separate-sitemaps/478103/
  - https://www.womenintechseo.com/knowledge/advanced-xml-sitemap-strategies-seo/
  - https://nightwatch.io/blog/sitemap-best-practices/
  - https://www.capconvert.com/learn/blog/xml-sitemaps-and-lastmod-tags-do-they-still-matter-for-google-and-ai-crawlers
- **仕組み／なぜ効くか**: Google の Gary Illyes によれば、**lastmod シグナルは本質的にバイナリ**——Googleは日付が信頼できるかを判定し、不正確な lastmod の履歴があるサイトではタグを丸ごと無視する。2026年7月16日には、CMSのバグで日付が汚染された事例に対して「lastmod を出さない方がおそらくマシ」とまで述べている。逆に、正確な lastmod は Google が実際にクロールシグナルとして使う。`priority` と `changefreq` は濫用され尽くしたため無視される（Illyes は priority を「ノイズの袋」と呼んだ）。
  **pSEOでこれが致命的な理由**: 生成器で全ページを再ビルドするたびに `lastmod = 今日` を全ページに出力する実装が非常に多い。これは「毎日全ページが更新されている」という嘘であり、サイト全体の lastmod 信頼を1回で失う。
- **具体手順**:
  1. build_articles.py の sitemap 生成部を確認し、`lastmod` が**現在日時**由来になっていないか検査する（**noe-match で最初に見るべき1行**）。
  2. 台帳側に「そのページのデータが実際に変わった日」の列を持ち、そこから lastmod を引く。テンプレの共通部分（フッター・免責）の変更では lastmod を動かさない。
  3. `priority` と `changefreq` は出力しない（無視されるうえ、ファイルサイズを増やすだけ）。
  4. sitemap index を使う場合、index 側の lastmod は「その sitemap ファイル自体が変わった日」であり、ページの更新日ではないことに注意する。
  5. コンテンツのハッシュ（本文の正規化後SHA）を台帳に保存し、ハッシュが変わったときだけ lastmod を更新する実装にすると、嘘をつかない仕組みが自動化できる。
- **日本での言及度**: **低**。【未検索・推定】 日本語の sitemap 解説記事は無数にあるが、大半が「priority を設定しましょう」という**10年前の情報のまま**であり、lastmod がサイト単位でバイナリ判定されるという2023年以降の重要な変化はほとんど反映されていない。要検証クエリ案: `sitemap lastmod 信頼性 バイナリ 無視される Google`。
- **noe-match適用度**: **A**。既存の生成器のバグである可能性が高く、修正工数は極小、失うものが大きい項目。想定工数: 2〜6時間（コンテンツハッシュ方式まで実装しても半日）。
- **リスク・反証**: lastmod を正確にした瞬間に、それまで「毎日更新」を装っていた分のクロール頻度が落ちる可能性がある（これは正常化であって悪化ではないが、短期のクロール数減として見える）。数値の一時的な下振れに動揺しないこと。

## 3-14. sitemap 分割を「診断装置」として使う（Sitemap Segmentation as a Diagnostic）

- **一言で**: sitemap をテンプレ別・バッチ別に分割すると、GSCの sitemap レポートが**そのままテンプレ別インデックス率のダッシュボード**になる。
- **海外での出典**:
  - https://www.womenintechseo.com/knowledge/advanced-xml-sitemap-strategies-seo/
  - https://nightwatch.io/blog/sitemap-best-practices/
  - https://hashmeta.com/blog/how-to-maintain-indexation-quality-on-huge-websites/
- **仕組み／なぜ効くか**: GSCの「サイトマップ」レポートは sitemap ファイル単位で「送信数 / インデックス数」を出す。つまり **sitemap の切り方をそのまま分析軸にできる**。全URLを1ファイルに入れると「サイト全体のインデックス率」しか分からないが、`sitemap-tool.xml` `sitemap-data.xml` `sitemap-muni-batch01.xml` のように分ければ、**どのテンプレが索引されないかが無料で可視化される**。3-06のゲート判定に必要な数字がここから直接取れる。
- **具体手順**:
  1. URLをテンプレ種別で分類する（記事 / ツール / データ記事 / 自治体ページ / 一覧ページ）。
  2. さらに公開バッチ（batch_001...）で細分する。1ファイルあたり数百〜数千URLで十分。
  3. `sitemap_index.xml` から各ファイルを参照する。
  4. GSCに **sitemap index だけでなく個別ファイルも** 送信する（個別に送るとレポートが個別に出る）。
  5. 毎月「ファイル別インデックス率」を記録し、閾値割れしたテンプレを3-04に差し戻す。
  6. バッチが古くなってインデックス率が安定したら、ファイルを統合してよい（診断が終わったため）。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語では「サイトマップは5万URL/50MBまで、超えたら分割」という**容量制約としての分割**しか語られない。**診断装置として意図的に分割する**という発想は流通していない。要検証クエリ案: `サイトマップ 分割 テンプレート別 インデックス率 診断`。
- **noe-match適用度**: **A**。GitHub Pages でも完全に実装可能（静的XMLを吐くだけ）。3-06のゲートを機能させるための前提条件。想定工数: 4〜8時間。
- **リスク・反証**: sitemap の分割自体には順位効果は無い（あくまで計測用）。分割しすぎると管理が煩雑になるだけ。また、GSCのサイトマップレポートの「インデックス数」は更新に遅延があるので、日次では見ない。

## 3-15. Dataset 構造化データ ＋ Google Dataset Search（Dataset Schema / DCAT）

- **一言で**: 自作の集計データに `schema.org/Dataset` の JSON-LD を付けると、**通常のウェブ検索とは別枠の Google Dataset Search に載る**。日本語データセットは極端に少ないため、実質的に競合が居ない。
- **海外での出典**:
  - https://developers.google.com/search/docs/appearance/structured-data/dataset
  - https://support.datacite.org/docs/how-do-i-expose-my-datasets-to-google-dataset-search
  - https://docs.ckan.org/projects/ckanext-dcat/en/latest/google-dataset-search/
  - https://searchengineland.com/google-search-adds-dataset-schema-support-to-search-results-302906
- **仕組み／なぜ効くか**: Google Dataset Search は、ランディングページに露出された `schema.org/Dataset` マークアップ（または W3C DCAT）をクロールして構築される専用の検索エンジン。推奨フィールドは `name` / `description` / `creator` / `distribution`（ダウンロードリンク）/ `temporalCoverage` / `spatialCoverage` / `license` など。**Kaggle のデータセットが Dataset Search で頻繁に上位に出るのは、schema.org 準拠のメタデータが全ページに標準実装されているからにすぎない**——つまりこれは権威ではなく実装で取れる枠。
  さらに副次効果として、Dataset マークアップは「このページは一次データを持つ」という機械可読な主張になるため、3-04 の固有 value-add とセットで機能する。
- **具体手順**:
  1. 「データバンク」の各集計を1つの Dataset として定義する（例:「全国自治体 結婚新生活支援事業 給付上限額データセット 2026年度版」）。
  2. 各データセットに専用のランディングページを作り、CSV/JSONの実ファイルを同じドメインに置く（GitHub Pages はこれが得意）。
  3. ランディングページに `Dataset` の JSON-LD を入れる。`distribution` に `DataDownload`（`contentUrl` = CSVの実URL、`encodingFormat` = "text/csv"）を必ず入れる。
  4. `temporalCoverage`（例: "2026-04-01/2027-03-31"）と `spatialCoverage`（日本、都道府県）を入れる。日本語データセットが少ない領域なのでここが効く。
  5. `license` を明示する（CC BY 4.0 など）。ライセンス不明のデータセットは Dataset Search で扱いが悪い。
  6. リッチリザルトテストで検証し、データセット用の sitemap を分けてGSCに送信する（→3-14）。
- **日本での言及度**: **ほぼ無**。【検索実施】 検索クエリ: `Dataset 構造化データ schema.org データセット Google Dataset Search 登録 日本語`。ヒットしたのは鈴木謙一氏のブログ3本（2018〜2020年の公開報道記事、https://www.suzukikenichi.com/blog/google-launches-dataset-search/ ほか）、@IT の紹介記事（https://atmarkit.itmedia.co.jp/ait/articles/2007/15/news021.html ）、Qiitaの「使ってみた」1本のみ。**「自サイトのデータをDataset Searchに載せるための実装解説」の日本語記事は事実上存在しない**。さらに検索結果自体が「Dataset Searchで見つかる日本語データセットはかなり限られている」と述べており、**供給が薄い＝参入余地が大きい**ことを示している。本レポート中で最も日本語圏が空白な手法。
- **noe-match適用度**: **A**（ただし収益直結は間接的）。既に「データバンク台帳」があるので、CSV公開＋JSON-LD追加だけで実装できる。想定工数: 8〜16時間（データセット5本分のランディングページ + マークアップ + CSV出力）。
- **リスク・反証**: Dataset Search からの直接トラフィックは大きくない（研究者・ジャーナリスト中心）。**本命は「引用されること」**——記者やブロガーがデータを探して見つけ、引用リンクを張るという3-19との合わせ技で効く。また、公的データを再配布する際は各データの利用規約（政府標準利用規約2.0など）の確認が必須で、これを怠るとライセンス違反になる。

## 3-16. 再集計による新規性の生成（Derivative Data / Re-aggregation）

- **一言で**: 公開データは誰でも取れるが、**「その切り方」は自分だけのもの**。ランキング化・都道府県別・前年比・クロス集計・指数化の5操作で、公的データを「独自データ」に変換する。
- **海外での出典**:
  - https://salt.agency/blog/data-led-content-link-building/
  - https://scale-xpert.com/how-to-build-backlinks-with-original-data-research/
  - https://memorable.design/original-research-content/
  - https://practicalprogrammatic.com/examples
- **仕組み／なぜ効くか**: 「オリジナルリサーチがリンクを獲得するのは、**それまで存在しなかった事実を作り出すから**であり、そのstatを引用する記事すべてが被リンクになる」。ここで重要なのは、**一次調査（アンケート）をしなくても「それまで存在しなかった事実」は作れる**という点。公開データに対して次の操作を加えると、検索しても出てこない新しい命題文が生まれる：
  - **ランキング化**: 「結婚新生活支援事業の給付上限額が高い自治体トップ20」
  - **地理正規化**: 「人口1万人あたりの婚活支援予算 都道府県別」
  - **前年比 / 時系列**: 「婚姻件数の対前年比 都道府県別（過去10年）」
  - **クロス集計**: 「平均初婚年齢 × 平均家賃 の散布図で見る47都道府県」
  - **指数化 / 合成スコア**: 複数指標を正規化して合成した独自スコア（→3-17）
  これらは「Googleで検索しても既存記事が無い」ため、**キーワード競合がゼロの状態で作れるコンテンツ**になる。しかも各セルに一次データが入るので3-04の固有value-add要件を自動的に満たす。
- **具体手順**:
  1. 井戸のデータを「1行 = 1エンティティ（自治体 or 都道府県）、1列 = 1指標」の tidy形式に正規化する。
  2. 各列について「ランキング化する意味があるか」「人口/世帯数で割る意味があるか」を判定する。
  3. 分母データ（人口・世帯数・婚姻件数）をe-Statから取得して結合する（→カタログ参照）。**分母を持つことが再集計の生命線**。
  4. 前年データも取得して対前年比列を作る。年次が2期あれば「変化」という新しい軸が生まれる。
  5. 相関の面白い2列をクロスさせて散布図にする（→3-18で埋め込み可能な資産にする）。
  6. **各集計に「集計方法・出典・取得日・注意事項」を必ず添える**（3-25）。これが無いと引用されない。
- **日本での言及度**: **低**。【未検索・推定】 「データジャーナリズム」の文脈では日本語でも語られる（NHK・日経・データのじかん等）が、それは**報道の技法**であって、**SEOのコンテンツ供給パイプライン**としては語られていない。「オープンデータを再集計して記事にする」という個人メディアの実践論はほぼ空白。要検証クエリ案: `オープンデータ 再集計 独自データ 記事 SEO 個人メディア`。
- **noe-match適用度**: **A**。noe-matchの既存資産（自治体43件台帳 + データ記事25本）と完全に一致する。すぐ次の一手になる。想定工数: 分母データ取得と結合に8〜16時間、集計テンプレ実装に8時間。
- **リスク・反証**: 再集計は**計算ミスが致命的**（一度誤った数字を出して引用されると訂正が追えない）。必ず「元データ→集計→出力」の全工程をコードにして再現可能にし、手作業のExcelを挟まないこと。また、母数の小さい自治体を人口で割ると外れ値が暴れるので、「人口N万人以上」などの足切りを明示する必要がある。

## 3-17. 独自指数・合成スコアの設計（Composite Index / Proprietary Score）

- **一言で**: 複数の公開指標を正規化して重み付け合成し、**自分の名前をつけた指数**を作る。Nomad List の "Nomad Score" 型。指数そのものが引用対象・被リンク対象になる。
- **海外での出典**:
  - https://levels.io/nomad-list-founder
  - https://www.starterstory.com/stories/nomad-list-breakdown
  - https://www.softwaregrowth.io/blog/how-pieter-levels-grew-nomad-list
  - https://practicalprogrammatic.com/examples
- **仕組み／なぜ効くか**: Nomad List は生活コスト・回線速度・気候・安全度・医療などの外部データを集約して都市ごとのスコアを出し、**そのスコア自体が「Nomad Listでしか見られない数字」**になっている。フィルタ選択の各組合せがURLを生成し索引される構造と組み合わせることで、労力ゼロで数百ページのロングテールを作った。
  合成指数の戦略的な意味は3つ：(a) 元データは公開でも**合成物は自分のもの**なので「独自データ」を主張できる、(b) 指数は**ランキング化・比較・時系列という3つの派生コンテンツを自動で生む**、(c) 指数の名前がブランドになり指名検索を生む。
- **具体手順**:
  1. 指数の目的を1文で定義する（例:「20代後半〜30代前半の未婚者にとって、結婚・新生活を始めやすい自治体はどこか」）。
  2. 構成指標を4〜7個選ぶ。婚活・新生活文脈なら: 未婚率、平均初婚年齢、平均家賃、結婚新生活支援事業の給付上限、保育所待機児童数、住民1人あたり子育て予算、婚活支援施策の有無 など。
  3. 各指標を偏差値（またはmin-max）で正規化する。方向（高いほど良い/悪い）を揃える。
  4. 重みを決め、**重みと算出式を必ず公開する**。ブラックボックス指数は引用されない。
  5. スコアの全国分布・上位下位・都道府県別平均を出す（→3-16の派生が自動で生まれる）。
  6. 年次で再計算し、「昨年から順位を上げた自治体」という毎年使えるコンテンツ枠を作る。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本では「住みやすさランキング」「幸福度ランキング」は自治体・シンクタンク・不動産ポータルが出すもので、**個人メディアが自作の指数を持つ**という発想はほぼ存在しない。逆に言えば、婚活文脈の合成指数は日本語圏に前例が見当たらない。要検証クエリ案: `独自指数 スコア 自作 ランキング 自治体 メディア 算出式 公開`。
- **noe-match適用度**: **A**（ただしデータ拡張が前提）。43自治体では指数の説得力が弱いので、**まず47都道府県ベースの指数**から始めるのが現実的。想定工数: 指標選定と算出実装に16〜24時間、記事化に別途。
- **リスク・反証**: 指数は「恣意的だ」と批判されやすい。**重み・出典・限界を先回りして明記する**のが唯一の防御。また、指数が炎上材料になるリスク（「◯◯県が最下位」）があるため、婚活という繊細な領域では**順位の煽り方に注意**が必要（「最下位」ではなく「支援制度の拡充余地が大きい自治体」のような表現）。さらに、指数は年次更新のコミットメントを伴う——更新が止まった指数は3-23の decay 直行になる。

## 3-18. 埋め込みコード配布によるリンク獲得（Embed-Code Distribution / Widget Link Bait）

- **一言で**: インタラクティブな地図・チャートに「埋め込みコード」を付けて配布し、**他サイトが貼るたびに被リンクが増える**構造を作る。
- **海外での出典**:
  - https://handsondataviz.org/embed.html
  - https://www.datawrapper.de/
  - https://flourish.studio/visualisations/maps/
  - https://infogram.com/features/website-embeds
  - https://visme.co/blog/how-to-build-links-with-infographics
- **仕組み／なぜ効くか**: 「インフォグラフィックに埋め込みコードを添えると、他者が共有する際に自サイトへのリンクが張られる」「人はインタラクティブなコンテンツをより共有・リンクしやすい」。Datawrapper / Flourish / Infogram はいずれも iframe の埋め込みコードを生成するが、**それらのSaaSで作ると被リンクは自サイトではなくSaaS側に向かう**。ここが分岐点で、**自前ドメインで iframe を配信すれば、埋め込まれるたびに自サイトのURLが他サイトのHTMLに載る**。
  さらに重要なのは、埋め込み元HTMLに `<p>Source: <a href="https://noe-match.com/...">Noe結婚設計室</a></p>` のクレジット行を**iframeの外側に**含めた埋め込みコードを配ること。iframe内のリンクはSEO的なリンク価値を渡さないため、**クレジットのアンカーテキストはiframeの外に置く**のが英語圏の定石。
- **具体手順**:
  1. 3-16/3-17の集計から、単体で成立するビジュアル（47都道府県の色分け地図、散布図、時系列）を1つ選ぶ。
  2. そのビジュアルを **自ドメインの独立HTMLページ**（`/embed/marriage-age-map/`）として作る。軽量なSVG + 最小限のJSで、外部CDN依存なしに作る（GitHub Pages と相性が良い）。
  3. `X-Frame-Options` を付けない（GitHub Pages はデフォルトで埋め込み可）。レスポンシブに `iframe` の高さを調整する postMessage を入れる。
  4. 元記事ページに「このグラフを埋め込む」ボタンを置き、コピー用のコードを表示する。コードは `<iframe src="https://noe-match.com/embed/...">` + **iframe外のクレジットリンク**。
  5. ライセンスを明記する（「出典表示のうえ自由に埋め込み可」）。
  6. データを更新すると**埋め込み先の表示も自動で最新になる**——これが静的画像に対する決定的優位で、「最新データが自動反映される図」として売り込める。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語のリンクビルディング議論は「被リンク営業」「サイテーション」「相互リンク」に偏り、**埋め込みコード配布による受動的リンク獲得**はほとんど語られない。日本のメディアで埋め込みを配っているのはNHKや日経などの大手のみ。個人メディア向けの実践解説は空白。要検証クエリ案: `埋め込みコード 配布 被リンク グラフ iframe 出典リンク`。
- **noe-match適用度**: **B**（技術的には容易だが、埋め込んでもらう先の獲得が難所）。GitHub Pages で完全実装可能。想定工数: 埋め込み基盤の実装に16〜24時間、1ビジュアルあたり4〜8時間。
- **リスク・反証**: **作れば貼られるわけではない**。埋め込みが広がるには、そもそもデータが話題になっている必要がある（3-19とセット運用が前提）。また iframe はページ速度・CLSに悪影響を与えうるので、自サイト側では lazy load 必須。埋め込み先が増えると、データを間違えたときの訂正が全埋め込み先に即時反映される（これは利点でもありリスクでもある）。

## 3-19. 「◯◯統計」ページ＝リンク磁石（Statistics Page as Linkable Asset）

- **一言で**: 「{テーマ} statistics」型のまとめページは、記者・ブロガーが数字を探すときの入口になり、**引用のたびに被リンクを生む**恒久資産になる。
- **海外での出典**:
  - https://linkquest.co.uk/saas-seo/link-building/how-to-create-linkable-assets
  - https://salt.agency/blog/data-led-content-link-building/
  - https://outreachdesk.com/linkable-assets/
  - https://memorable.design/original-research-content/
  - https://scale-xpert.com/how-to-build-backlinks-with-original-data-research/
- **仕組み／なぜ効くか**: 英語圏では "Remote working statistics UK" のような1本の統計まとめページが **707本の被リンク**（Indeed, Deloitte, CityAM 等を含む）を獲得した事例が報告されている。仕組みは単純で、記事を書く人は「数字を1つ引用したい」ときに `{topic} statistics` で検索し、最初に見つかった信頼できるページを引用する。つまり**このページは「検索需要」ではなく「引用需要」を取りに行く**。
  重要な実装ディテールは、**「引用しやすさ」を設計すること**——事前フォーマット済みの引用ブロック（blockquote）やコピーボタンを置くと、ライターが数字をコピーして自サイトをクレジットするのが極端に簡単になる。また、統計ページは AI検索・LLM に引用されやすいフォーマットでもある（数字＋出典＋日付が構造化されているため）。
- **具体手順**:
  1. テーマを決める（例:「日本の結婚・婚活に関する統計まとめ2026」「都道府県別 結婚データ集」「新生活・引越し費用の統計」）。
  2. 20〜60個の「1文で完結する数字の事実」を集める。**各行に必ず (a) 数値、(b) 一次出典名、(c) 出典URL、(d) 調査年 を付ける**。
  3. 各統計に `id` を振り、パーマリンク（`#stat-12`）で個別に参照できるようにする。
  4. 各統計にコピーボタンを置き、クリックすると「〔数値〕（出典: 〔調査名〕, 〔年〕／ Noe結婚設計室 https://noe-match.com/... ）」がクリップボードに入るようにする。
  5. 目次を作り、カテゴリ（婚姻・初婚年齢・費用・意識・地域差）で分ける。
  6. 「最終更新日」と「次回更新予定」を明記し、実際に年1回更新する。更新しない統計ページは3-23で腐る。
- **日本での言及度**: **低**。【未検索・推定】 日本語でも「〇〇の統計データまとめ」記事は多数あるが、それらは**アフィリエイト記事の導入用**であって、**被リンク獲得資産として設計されていない**（出典URLが無い、コピー用ブロックが無い、更新されない）。「linkable asset」という概念語自体が日本語SEOに定着していない。要検証クエリ案: `リンカブルアセット 統計まとめ 被リンク 獲得 引用されやすい`。
- **noe-match適用度**: **A**。データバンク台帳と再集計（3-16）があれば、統計ページは**副産物として作れる**。婚活領域は記者・ライターの引用需要が確実にある（少子化報道が恒常的にあるため）。想定工数: 1本あたり16〜24時間（数字の一次確認が重い）。
- **リスク・反証**: 数字の誤りは信用の直撃事故。一次ソースにあたらず二次情報を孫引きすると、誤りが連鎖して自サイトが誤情報の発信源になる。**必ず一次ソース（e-Stat等）で確認し、確認日を残す**（3-25）。また、被リンクは「作った瞬間」ではなく「数字が話題になった瞬間」に来るので、成果は数ヶ月〜年単位で遅れる。短期のROIを求めると挫折する。

## 3-20. アルゴリズム的内部リンク（Algorithmic Internal Linking / Embedding-Based）

- **一言で**: キーワード一致ではなく**埋め込みベクトルのコサイン類似度**で関連ページを判定し、閾値を超えたペアに自動でリンクを張る。
- **海外での出典**:
  - https://nikoalho.fi/writing/automating-internal-linking/
  - https://www.alliai.com/ai-and-automation/automating-internal-linking
  - https://www.hashbuilds.com/articles/internal-linking-strategy-for-10-000-programmatic-seo-pages
  - https://marketingagency.sg/programmatic-seo-internal-linking/
- **仕組み／なぜ効くか**: 「各ページをベクトル埋め込みに変換し、コサイン類似度で意味的に関連するページを特定する。閾値を超えたものにCMS API経由でリンクを注入する」。キーワードマッチ方式の問題は、(a) 表記ゆれに弱い、(b) 同じ語を含むだけの無関係ページを繋いでしまう、(c) 日本語では形態素解析の精度に依存する。埋め込み方式ならこれらを回避できる。
  pSEOで内部リンクが決定的な理由は、**大量ページは被リンクを持たないため、内部リンクだけが唯一のPageRank供給源**だから。孤立ページ（orphan）は事実上インデックスされない。
- **具体手順**:
  1. 全ページの本文（テンプレ共通部を除く）を埋め込みモデルでベクトル化する。ローカルで完結させたいなら多言語対応の軽量モデルで十分。
  2. ページ間のコサイン類似度行列を作る（258ページなら一瞬、数千ページでも問題ない）。
  3. 各ページについて上位N件（N=5〜8）を「関連記事」として抽出する。ただし**類似度が高すぎるペア（0.95超）はカニバリ候補**として別途フラグを立てる（→3-24）。
  4. 相互リンクを避け、**リンク先の入リンク数に上限**を設ける（人気ページにリンクが集中しすぎるのを防ぐ）。
  5. アンカーテキストはリンク先のH1そのままではなく、リンク元の文脈に合わせた語を使う（テンプレでバリエーションを持つ）。
  6. リンクグラフを可視化し、**入リンク0のページ（orphan）が存在しないこと**をビルド時アサーションにする。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 日本語の内部リンク解説は「関連記事プラグインを入れる」「パンくずを設置する」で止まり、**埋め込みベースの類似度計算で内部リンクを設計する**という話はほぼ見ない。要検証クエリ案: `内部リンク 自動化 埋め込み ベクトル コサイン類似度 SEO`。
- **noe-match適用度**: **A**。Python生成器があるので実装は自然。258記事なら計算コストは無視できる。想定工数: 16〜24時間。
- **リスク・反証**: 埋め込み類似度は「意味が近い」を測るが「リンクすべきか」は測らない。**類似度が高い＝カニバリズムの可能性**でもあるので、機械的に張ると共食いを助長しうる。閾値の上限側にもガードが必要。また、全ページに機械的に「関連記事8本」を並べると、ユーザー価値のないリンクファームに見える。**本文中の文脈リンク**と**末尾の関連記事ブロック**は別扱いにすること。

## 3-21. hub-spoke の自動生成とリンク整流（Hub & Spoke / Link Equity Routing）

- **一言で**: tail ページを放置せず、**必ず何らかの hub（一覧・比較・カテゴリ）ページに束ねる**。hub がクロールの入口と PageRank の分配器を兼ねる。
- **海外での出典**:
  - https://atticusli.com/blog/posts/internal-linking-architecture-rankings-conversions/
  - https://andresseo.expert/seo/programmatic-breed-clustering-internal-link-hub-generation/
  - https://www.clickrank.ai/pagerank-sculpting/
  - https://www.seotakeoff.com/blog/programmatic-seo-internal-linking
- **仕組み／なぜ効くか**: 「中央のHub（ピラーページ）が権威をSpokeに流し、Spokeが関連性をHubに返す」。pSEOでは**hubの設計が、そのままクロール到達性の設計**になる。ホームから3クリック以内に全ページが到達できるかが実務上の閾値としてよく使われる。hubページ自体も torso キーワードを取れる（「都道府県別 結婚支援制度一覧」など）ため、二重に価値がある。
  「PageRank sculpting」は本来の nofollow を使った手法としては死んでいるが、**「リンクをどこに何本張るかで権威の配分を設計する」という意味では現役**。
- **具体手順**:
  1. 台帳の各軸（都道府県 / 制度種別 / 年次 / テーマ）ごとに hub ページを機械生成する。
  2. hub は単なるリンク一覧にしない。**hub 自体に集計（平均・分布・上位下位）を載せる** ことで、hubが3-04を満たす独立コンテンツになる。
  3. 各 spoke から所属 hub へ必ずリンクを返す（パンくず + 本文内）。
  4. hub を hub of hubs（トップレベルのデータバンク索引ページ）から辿れるようにする。
  5. クリック深度をビルド時に計算し、**深度4以上のページが存在したらビルドを失敗させる**。
  6. hub のリンク本数が多すぎる場合（200超）はページネーションではなく**軸で分割**する（ページネーションはクロール効率が悪い）。
- **日本での言及度**: **低**。【未検索・推定】 「トピッククラスター」「ピラーページ」は日本語SEOでもそこそこ知られている（HubSpot発の概念として輸入済み）。ただし **hub を機械生成し、hub自体に集計を載せる**という pSEO 固有の実装論は空白。また「クリック深度をCIでアサーションする」という規律も日本語圏では見ない。要検証クエリ案: `ピラーページ 自動生成 集計 クリック深度 アサーション`。
- **noe-match適用度**: **A**。データバンク台帳の軸がそのまま hub になる。想定工数: 8〜16時間。
- **リスク・反証**: hub を軸ごとに全部作ると hub 同士が薄い重複を起こす（「東京都の制度一覧」と「関東の制度一覧」など）。**hubの軸も3-22の○×判定にかける**必要がある。

## 3-22. ファセットナビゲーションの設計（Faceted Navigation: 事前生成ホワイトリスト方式）

- **一言で**: 絞り込みUIを作るとURLが組合せ爆発する。**「索引させる組合せを事前にホワイトリスト化し、それ以外はURLを生成しない」**のが唯一の安全解。
- **海外での出典**:
  - https://developers.google.com/search/blog/2024/12/crawling-december-faceted-nav
  - https://developers.google.com/search/blog/2014/02/faceted-navigation-best-and-5-of-worst
  - https://searchengineland.com/guide/faceted-navigation
  - https://resignal.com/blog/seo-friendly-faceted-navigation-to-avoid-crawl-efficiency-or-creating-index-bloat/
  - https://www.digitalapplied.com/blog/faceted-navigation-indexation-2026-seo-decision-matrix
- **仕組み／なぜ効くか**: Googleは公式ブログで「**ファセットナビゲーションは、サイト運営者から報告される過剰クロール問題の圧倒的最大の原因**であり、大半のケースはベストプラクティスに従っていれば回避できた」と明言している。1,000商品・5フィルタ・各10選択肢で理論上数百万URLが生まれる。
  Googleの推奨は明確：(a) 検索需要と価値のある組合せだけをクロール・インデックス可能にする、(b) 価値のない組合せは robots.txt でブロックするか**URLフラグメント（`#`）を使う**（フラグメントはクローラーに無視されるため、そもそもURLが増えない）、(c) 結果が0件の組合せではURLを作らない、(d) パラメータの区切りと順序を一貫させる。
  **noe-matchのツール17本は、まさにこの罠に直面する構造**。「診断ツール」「シミュレーター」の結果ページをURL化すると即座に爆発する。
- **具体手順**:
  1. ツール/絞り込みの状態を **URLに載せるか、フラグメント（`#`）に載せるか、載せないか** の3択で明示的に決める。
  2. **デフォルトはフラグメント**。`?` パラメータにするのは「そのURLで検索需要がある」と証明できた組合せだけ。
  3. 検索需要がある組合せは、パラメータではなく**静的パス（`/tool/xxx/tokyo/`）で事前生成**する。GitHub Pages では静的生成が最も安全で速い。
  4. ホワイトリストは台帳に持ち、そこから sitemap を生成する（→3-14）。
  5. ホワイトリスト外のURLへのリンクをHTML内に出さない（**リンクが無ければクロールされない**のが最強の防御）。
  6. `robots.txt` で `?` を含むパスをブロックする（ただし3-08の順序に注意——既に索引されているURLがあるなら先にnoindex）。
- **日本での言及度**: **低**。【未検索・推定】 「ファセットナビゲーション」の日本語記事はECサイトSEO文脈で存在する（絞り込み検索のnoindex/canonical）。ただし2024年12月のGoogle公式「Crawling December」シリーズの内容が日本語で消化された形跡は乏しく、特に **「フラグメントを使え」というGoogleの推奨**はほとんど紹介されていない。要検証クエリ案: `ファセットナビゲーション Google 公式 フラグメント 推奨 クロール`。
- **noe-match適用度**: **A**（既存17ツールの設計監査として即実施すべき）。想定工数: 監査4〜8時間、修正はツールの実装次第。
- **リスク・反証**: フラグメントにすると「結果をURLで共有できない」というUXの損失がある。SNSシェアを重視するツールでは、**フラグメント（`#`）は共有可能かつクロール不能**という点でむしろ最適解。パラメータをフラグメントに移行する際、既に索引済みのパラメータURLがあれば3-08の順序で処理すること。

## 3-23. Content decay の検知とトリアージ（Content Decay Triage）

- **一言で**: 全ページを「維持 / リフレッシュ / 統合 / 削除」の4分類に自動振り分けし、リフレッシュの順番をトラフィック影響で決める。
- **海外での出典**:
  - https://ahrefs.com/blog/content-decay/
  - https://searchengineland.com/guide/content-decay
  - https://www.frac.tl/content-decay-updating-underperforming-content/
  - https://prometixai.com/blog/content-decay/
  - https://www.imarkinfotech.com/the-content-decay-problem-a-data-driven-framework-for-auditing-pruning-and-rebuilding-topical-clusters/
  - https://slatehq.com/blog/content-decay-detection-tools
- **仕組み／なぜ効くか**: content decay は「かつて成果を出していたページの緩やかな流入低下」で、検索意図の変化・競合の深化・情報の陳腐化・自サイト内の新ページとの競合が原因。実務フレームは共通していて、**「全URLについて12〜24ヶ月の流入・順位・エンゲージメント・CVを取り、maintain / refresh / consolidate / prune に分類し、トラフィックと収益のインパクト順に着手する」**。閾値の例として「四半期ごとに、前年同期比で流入が20%以上落ちたページをフラグする」。
  **公的データ由来のページは decay の速度が特殊**：数字が更新された瞬間に「古い数字を載せているページ」になる。つまり decay が**予測可能**であり、データの更新周期をカレンダー化すればリフレッシュを先回りできる。これはpSEO×オープンデータ特有の優位性。
- **具体手順**:
  1. GSC（できればBigQuery、→3-11）から URL × 月 の clicks / impressions / position を取る。
  2. 各URLについて「直近3ヶ月合計 ÷ 前年同期3ヶ月合計」を計算する。0.8を下回ったら decay フラグ。
  3. decay の原因を分類する: (a) 順位は維持だがimpressionsが落ちた＝需要減 or SERP機能に食われた、(b) 順位が落ちた＝競合 or 品質、(c) 自サイトの別URLが同じクエリで上がった＝カニバリ（→統合）。
  4. **台帳の「データ更新周期」列**を作り、e-Stat等の公表スケジュールから「このページは何月に古くなるか」を事前計算する。
  5. リフレッシュの優先度を `(失われたクリック数 × 収益単価) ÷ 作業時間` で並べる。
  6. リフレッシュ時は lastmod を正しく更新する（→3-13）。中身を変えずに日付だけ変えるのは最悪手。
- **日本での言及度**: **低**。【未検索・推定】 日本語では「リライト」という語で近い概念が広く語られている（リライトのやり方記事は無数にある）。ただし **"decay" を時系列の定量指標として検知し、4分類で機械的にトリアージする**という体系は流通していない。日本語の「リライト」は感覚的・個別的な作業論に留まる。また「データの更新周期からdecayを先回りする」は日本語圏に見当たらない。要検証クエリ案: `コンテンツディケイ 検知 前年同期比 しきい値 トリアージ`。
- **noe-match適用度**: **A**（データ記事25本は特にdecayが読みやすい）。想定工数: 検知スクリプトに8〜16時間、以後は四半期ごとに4時間。
- **リスク・反証**: ドメイン開設2ヶ月では**前年同期比が存在しない**ため、この手法は最短でも2027年6月まで本格稼働しない。それまでは「更新周期カレンダー」の部分だけを先に作っておくのが正解。また、季節性の強いクエリ（婚活は年始・春に山がある）では前年同期比が唯一の正しい比較軸になるので、月次比較で早とちりしないこと。

## 3-24. 大規模剪定（Content Pruning at Scale）

- **一言で**: 「増やす」の反対側の技術。低価値ページを削除・統合してサイト全体の品質シグナルを上げる。**pSEOをやる者は必ず剪定の技術をセットで持つ**。
- **海外での出典**:
  - https://learningseo.io/seo_roadmap/deepen-knowledge/content/content-pruning/
  - https://searchengineland.com/guide/index-bloat
  - https://www.greenlanemarketing.com/resources/articles/how-to-find-and-fix-index-bloat-issues
  - https://hashmeta.com/blog/how-to-maintain-indexation-quality-on-huge-websites/
- **仕組み／なぜ効くか**: index bloat が「サイトの品質評価を希釈する」以上、低価値ページの除去は**残ったページの評価を上げる**操作になる。剪定の判断は削除だけではなく4択：
  - **統合（consolidate）**: 似たページを1本にまとめ、旧URLから301。カニバリ解消に最も効く。
  - **noindex**: 削除したくない（ユーザーには有用）が索引不要なページ。
  - **410 Gone**: 完全に不要。404より索引除去が速い。
  - **リダイレクト（301）**: 統合先がある場合のみ。無関係なページへの301は soft 404 になる。
- **具体手順**:
  1. 「公開後6ヶ月以上経過 × 過去90日クリック0 × 被リンク0」の3条件を満たすURLを抽出する。
  2. そのうち「他ページと類似度0.9超」のものを統合候補にする（→3-20の類似度行列を再利用）。
  3. 統合候補以外を「削除 / noindex」で判断する。**ユーザーにとって有用か**を基準にする（検索流入が無いだけで有用なページはnoindexで残す）。
  4. 削除するURLは 410 を返す。**GitHub Pages では任意ステータスコードを返せない**ため、代替として「該当ページを noindex 化 + 内部リンクを全撤去 + sitemapから除外」を行い、索引から落ちるのを待つ（→3-26）。
  5. 剪定の前後でサイト全体のクリック数を記録し、剪定が正味プラスだったかを検証する。
  6. **1回の剪定で全体の10%以上を削除しない**。段階的に、効果を測りながら。
- **日本での言及度**: **低**。【検索実施】 3-08と同じ検索（`インデックス肥大化 index bloat 日本語 SEO 対策 コンテンツプルーニング`）で確認したが、「コンテンツプルーニング」という語自体がほぼ日本語検索結果に現れず、代わりに「記事の削除は慎重に」「低品質記事はリライトを」という一般論が出てくる。**「削除がSEO施策である」という前提が日本語圏では十分に共有されていない**。
- **noe-match適用度**: **B**（今すぐではないが、pSEO実行の前に手順を確立すべき）。想定工数: 手順確立4時間、実施は年1〜2回で各4〜8時間。
- **リスク・反証**: 剪定は**やりすぎると単に流入を失う**。「クリック0」は「まだ順位が付いていない」だけの可能性があり、新規ドメインでは特に危険。noe-matchのように開設2ヶ月のサイトでは、**当面は剪定を実行しない**のが正しい。準備だけしておく。

## 3-25. 一次ソース台帳＝データ出所の証跡管理（Data Provenance Ledger）

- **一言で**: 「どの数字を、どのURLから、いつ取得し、いつ確認したか」を全セルについて記録する台帳。**E-E-A-T の実装であり、引用される条件であり、訂正可能性の担保**。
- **海外での出典**:
  - https://developers.google.com/search/docs/appearance/structured-data/dataset
  - https://salt.agency/blog/data-led-content-link-building/
  - https://memorable.design/original-research-content/
  - https://docs.ckan.org/projects/ckanext-dcat/en/latest/google-dataset-search/
- **仕組み／なぜ効くか**: 英語圏では「独自リサーチが見つけられ、共有され、リンクされやすい形になっている必要がある——それはライターにとっても、検索エンジンにとっても、LLMにとっても」と論じられる。出所が明示されていないデータは、記者が引用できない（社内のファクトチェックを通らない）。つまり**provenance が無いデータは、どれだけ正確でも被リンクを生まない**。
  加えて、公的データの再配布には利用規約の遵守が必要で、台帳に出典・ライセンス・取得日を持つことは法務上のリスク管理でもある。
- **具体手順**:
  1. 台帳のスキーマに最低限これを含める: `value` / `source_name` / `source_url` / `source_published_date` / `retrieved_at` / `verified_by` / `license` / `note`。
  2. **`retrieved_at` と `source_published_date` を分ける**。前者は自分が取った日、後者はデータの公表日。読者が見るべきは後者。
  3. ページのフッターに「データ出典・取得日・次回更新予定」ブロックをテンプレで自動出力する。
  4. `source_url` が404になっていないかを定期的に自動チェックする（リンク切れは信頼の直撃事故）。
  5. 訂正が発生したら、ページに訂正履歴を残す（消さない）。訂正履歴があるサイトの方が信頼される。
  6. データセット単位で `license` を明記し、政府標準利用規約2.0 / CC BY 等の条件を守る。
- **日本での言及度**: **低**。【未検索・推定】 日本語では「出典を書きましょう」という一般論はあるが、**セル単位でのprovenance管理**、`retrieved_at` と `published_date` の分離、リンク切れ自動監視といった実装論は流通していない。学術・図書館情報学の文脈では語られるが、SEO/メディア運営文脈とは接続していない。要検証クエリ案: `データ出典 管理 取得日 一次ソース 台帳 メディア運営`。
- **noe-match適用度**: **A**。依頼主は既に「自治体データ43件の一次確認」を実施済みで、事実上のprovenance管理を手作業でやっている。**それをスキーマ化するだけ**。想定工数: 8〜16時間。
- **リスク・反証**: provenance の粒度を上げすぎると入力コストが爆発する。「1データセット単位」で始め、必要になったら「1セル単位」に降ろすのが現実的。また、`retrieved_at` を表示すると「1年前に取ったデータ」であることが可視化されてしまう——これは正直さのコストであり、同時に更新を強制する健全な圧力でもある。

## 3-26. 静的サイト（GitHub Pages）でのpSEO実装制約と回避策

- **一言で**: GitHub Pages は「サーバー側の処理が一切できない」。**404/410/301のステータス制御、ログ取得、動的ページ生成、リクエスト時のnoindex切替がすべて不可能**。この制約を前提に設計を変える。
- **海外での出典**:
  - https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits
  - https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/github-pages-limits
  - https://github.com/orgs/community/discussions/153352
  - https://github.com/orgs/community/discussions/167331
- **仕組み／なぜ効くか**: 公式に定められた制限は——**公開サイト最大1GB / 帯域 月100GB（ソフトリミット）/ ビルド 1時間10回（カスタムGitHub Actionsワークフローなら非適用）/ デプロイのタイムアウト10分**。超過時は即停止ではなく「GitHubサポートから丁寧なメールが来る」ソフト運用。レート制限に触れると HTTP 429 が返る。最大の制約は**サーバーサイドコード実行が無いこと**。
  pSEOへの具体的影響：
  - ❌ **410 Gone を返せない** → 剪定（3-24）の速度が落ちる
  - ❌ **301リダイレクトをサーバーで返せない** → HTML meta refresh + canonical で代用（SEO的には劣る）
  - ❌ **アクセスログが取れない** → ログファイル分析（3-10）が不可能
  - ❌ **リクエスト時の動的処理が無い** → 全ページを事前生成する必要がある
  - ✅ **静的CSV/JSONの配信は得意** → Dataset配信（3-15）と埋め込み（3-18）には最適
  - ✅ **ページ表示速度は極めて速い** → Core Web Vitals で有利
  - ✅ **1ページあたり数十KBなら、1GB制限は実質1万〜3万ページまで許容**
- **具体手順**:
  1. 現在のリポジトリサイズを計測し、1GBに対する余裕を把握する（`du -sh`）。ページ増加率から到達時期を予測する。
  2. 画像はリポジトリに入れず、必要なら別ホスト（またはSVG/インラインで軽量化）にする。画像がサイズ制限の主犯になりやすい。
  3. デプロイを GitHub Actions のカスタムワークフローにして、10ビルド/時の制限から外れる（既に `.github/` があるので確認する）。
  4. URL設計を**最初から変えないで済む形**にする（リダイレクトが弱いので、URL変更のコストが高い）。日付をURLに入れない、カテゴリ階層を深くしない。
  5. 削除は「410」ではなく「noindexページとして残す」パターンで運用する（3-24）。
  6. ログが必要になったら Cloudflare を前段に入れる。ただしそれは数千ページ規模になってからで十分。
  7. `.nojekyll` が既にあるので Jekyll ビルドは無効。デプロイはビルド済み成果物のコミット方式である可能性が高い → **ビルド時間もビルド回数制限も実質無関係**（有利）。
- **日本での言及度**: **ほぼ無**。【未検索・推定】 「GitHub Pagesでブログを作る」という日本語記事は無数にあるが、**GitHub Pages の制約を pSEO / 大規模SEO の観点から論じたもの**は見たことがない。日本語圏ではGitHub Pagesは「エンジニアの個人ブログ」の文脈でしか語られず、「アフィリエイトメディアの配信基盤」として論じられていない。要検証クエリ案: `GitHub Pages 制限 1GB 大量ページ SEO リダイレクト 410`。
- **noe-match適用度**: **A**（構成そのものの評価なので必読）。想定工数: 現状監査に4時間。
- **リスク・反証**: GitHub Pages の利用規約は「主にビジネス目的の商用サイト」の運用を想定していないという議論が継続的にある（コミュニティディスカッション参照）。アフィリエイトメディアが規約上どう扱われるかはグレーで、**サイトが成長したら独自ホスティング（Cloudflare Pages / Netlify / VPS）への移行計画を持っておくべき**。移行時にURL構造が変わらない設計にしておくことが保険になる。

# 付録: noe-match リポジトリ現物確認メモ（2026-08-27 実施）

未解決事項 #7 / #8 を、リポジトリを直接読んで解消した。加えて、その過程で3件の追加所見を得た。

### ✅ 所見1: IndexNow キーは既に設置済み（3-12 が半分完了している）

`/home/user/noe-match/28fb2874520d40719aa81fc0618e863b.txt` の中身は `28fb2874520d40719aa81fc0618e863b`、つまり **ファイル名と同一文字列**。これは IndexNow のキーファイル仕様（`{key}.txt` の中身が `{key}`）に完全一致する。Bing の所有権確認ファイルは `BingSiteAuth.xml` なので別物。

→ **残りの作業は「デプロイ後に `https://api.indexnow.org/indexnow` へ更新URLをPOSTする」だけ**。GitHub Actions に数行足せば完了する。工数2時間以内。

### 🚨 所見2（最重要）: sitemap の lastmod が「全URL＝ビルド日」になっている

`build_articles.py` の該当箇所：

```python
def write_sitemap(lastmod):
    ...
    parts.append(f"  <url>\n    <loc>{loc}</loc>\n    <lastmod>{lastmod}</lastmod>\n    <changefreq>{freq}</changefreq>\n    <priority>{pri}</priority>\n  </url>")
...
n_urls = write_sitemap(date.today().isoformat())
```

**全URLに一律で `date.today()` が入る**。つまり再ビルドするたびに「全ページが今日更新された」と Google に申告している。これは **3-13 で述べた「lastmod のサイト単位バイナリ信頼」を失う典型パターンそのもの**。Gary Illyes の言い方を借りれば、この状態なら「lastmod を出さない方がまだマシ」。

**修正案（優先度: 最高、工数: 2〜6時間）**
1. 記事ごとの本文を正規化（テンプレ共通部を除去）してSHA256を取り、`article_slugs.json` 等の台帳に `content_hash` と `content_changed_at` を持たせる。
2. ビルド時にハッシュが変わったURLだけ `content_changed_at` を今日に更新する。
3. `write_sitemap` は URL ごとに `content_changed_at` を出力する。
4. **`<changefreq>` と `<priority>` は出力をやめる**（Google は両方無視する。priority は Illyes に「ノイズの袋」と呼ばれた）。ファイルサイズも約4割減る。

### ⚠ 所見3: sitemap のカバレッジに欠落がある

- `articles/` 配下のディレクトリ数: **305**
- 配信中の `sitemap.xml` の `<loc>` 数: **234**（トップ＋法的ページ3本を含む）

→ **単純計算で70件前後の記事URLが sitemap に載っていない可能性が高い**。また `build_articles.py::write_sitemap` の docstring は「トップ＋48記事」となっており、実際の234件とも合わない。つまり **sitemap を生成しているコードが複数系統（`complete_implementation.py` / `.apply.py` 等）に分裂している疑いがある**。

**アクション**: sitemap 生成を1箇所に統合し、「`articles/*/index.html` として実在し、かつ noindex でないもの」を機械的に列挙する方式に変える。同時に 3-14 のテンプレ別分割を入れると、インデックス率の可視化まで一気に片付く。

### ⚠ 所見4: 関連記事ブロックが最大6本の固定ロジック

`related_block()` は候補を最大6件に切って `<div class="related">` を出力している。これは 3-20（埋め込み類似度ベース）と 3-21（hub-spoke）の**置き換え対象**。現状のロジックがキーワード一致ベースであれば、コサイン類似度方式への差し替えで内部リンクの質が上がる。同時に **入リンク0のページ（orphan）が存在しないかのアサーション**をここに足すべき。
