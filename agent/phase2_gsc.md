# Phase 2：Search Console 閉ループ化設計

**ステータス：稼働中（2026-07-05有効化 / 2026-07-30に選定条件を改定）。** データ供給はローカル週次ジョブ（scripts/weekly_gsc_push.bat・日曜23:00）と GitHub Actions（.github/workflows/fetch-gsc.yml・日曜13:00 UTC）が agent/gsc_data.json を更新する。

## 目的

人間が手動でやっている「クエリ分析 → 強化対象の選定 → 記事強化」のループを自動化し、
データ駆動の記事工場にする。

## 有効化に必要な初回設定（人間の作業・約30分）

1. Google Cloud Console でプロジェクト作成
2. Search Console API を有効化
3. サービスアカウントを作成し、JSONキーを取得
4. Search Console（https://www.noe-match.com/ プロパティ）の「設定 > ユーザーと権限」で
   サービスアカウントのメールアドレスを「制限付き」ユーザーとして追加
5. JSONキーをエージェント実行環境のシークレットに登録（リポジトリにはコミットしない）

## 有効化後のエージェントフロー（週次）

```
① GSC APIで過去28日のクエリデータを取得
   （dimensions: query, page / rowLimit: 500）
② 以下の条件で「強化対象」を自動選定：
   - 表示回数 5回以上 かつ 平均掲載順位 11〜30位
   - → 「Googleが試しているが評価しきれていない」ゾーン
   - 31位以下は対象外（2026-07-30改定。追記しても順位が動かず、
     そもそも31位以下の表示はクリックを1件も生んでいない）
③ 対象クエリに対応する記事に、クエリ意図に合うセクションを追記
   - タイトル・meta description の調整（クエリ語をタイトル前方へ）
   - 1記事あたり追記は2セクションまで（過剰最適化防止）
④ 新規需要の発見：
   - 表示されたクエリに対応する記事が存在しない場合、
     keyword_queue.json に自動で追加（人間レビュー用に status: "proposed"）
⑤ コミット・プッシュ
```

## 判断ルール

- 同一記事の連続強化は2週間空ける（Googleの再評価待ち）
- 順位が10位以内に入ったクエリの記事は触らない（勝ちパターンを壊さない）
- **同一記事への追記強化は通算2回まで。2回で平均順位が3ポイント以上改善しなければ打ち切り**
  （AGENT.md「追記強化の打ち切りルール」。打ち切り済み：tokyo-guide）
- 表示回数が4週連続ゼロの記事はリライト候補としてレポートに記載（自動リライトはしない）

## 効果測定の指標（2026-07-30改定）

強化が効いたかどうかは **表示回数ではなく ①平均掲載順位の改善 ②クリック数** で判定する。
表示回数は31位以下でも積み上がるが、実測では31位以下の表示54回からクリックは0件だった。
表示回数の増加を「強化が効いた」と読んではいけない。

## 実績記録

エージェントは毎回 `agent/run_log.md` に実行結果（生成/強化した記事・対象クエリ）を追記する。
