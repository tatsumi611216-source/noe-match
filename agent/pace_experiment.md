# 公開ペースの上限（2026-08-01 実測で確定・段階的引き上げ実験は撤回）

## 結論：週2本を据え置く。上げる余地はほぼ無い

当初は「週4本→8本→12本と段階的に上げてインデックス率を測る」実験を設計していたが、
**Search Console のクロール統計を見た時点で結果が計算で分かったため撤回した。**
9週間かけて確かめる価値がない。

## 実測（Search Console → 設定 → クロールの統計情報 / 2026-08-01・過去90日）

| 項目 | 値 |
|------|-----|
| 合計クロールリクエスト | **347**（90日） |
| **1日あたり** | **3.86回** |
| ファイル形式：HTML 88% | 1日 **3.39ページ** |
| **目的別：検出（Discovery）28%** | **97回 / 1日 1.08回 / 週 7.6回** |
| 目的別：更新（Refresh）72% | 1日 2.78回 |
| 平均応答時間 | **91ms** |
| ホストのステータス | 問題なし |
| レスポンス：301 5% / 404 3% / リクエスト失敗 3% | 合計11% ＝ **38回が無駄** |

## これで観測されていた全部に説明がつく

**Googleが「新しいURLを取りに行く」動作は1日1.08回しかない。**
その間にサイトは142本を公開した。

| 観測 | 説明 |
|------|------|
| 週2本ペースのコホートが90.9% | 0.29本/日は検出能力1.08/日の**27%**。余裕で処理される |
| 一括58本・73本が24〜31% | 検出の行列に一度に積まれ、大半が順番待ちのまま |
| 2ヶ月待っても解消しない | 新しいURLが先に処理され、**古い行列は追い越され続ける** |

**2026-08-01(2) で「週2本だから90.9%」と書いたのは結果的に正しかったが、
理由は「週次という公開の仕方が良い」ではなく「検出能力の範囲内に収まっていたから」である。**

## ペース別の試算（未クロール95本の消化にかかる日数）

| ペース | 新URLに使う | 行列の消化に回る | 95本の消化 |
|-------|-----------|---------------|-----------|
| 停止 | 0.00/日 | 1.08/日 | 88日 |
| **週2本（現行）** | 0.29/日 | 0.79/日 | **120日** |
| 週3本 | 0.43/日 | 0.65/日 | 146日 |
| 週4本 | 0.57/日 | 0.51/日 | 187日 |
| 週7本 | 1.00/日 | 0.08/日 | **1,194日** |

**上げるほど既存95本が消化されない。**週7本で検出能力を使い切ると、行列は事実上止まる。
（検出リクエストはリダイレクトスタブや画像にも使われるので、実際はこれより悪い）

## 制約は「能力」ではなく「需要」側にある

Googleの枠組みでは クロールバジェット ＝ **クロール能力の上限 × クロールの需要**。

- **能力の上限は制約になっていない。**平均応答時間91ms、ホストのステータス問題なし。
  サーバーには全く余裕がある
- **したがって制約は需要側**。Googleが「このサイトをこれ以上取りに行く価値がない」と
  判断している

**需要は記事を増やしても上がらない。** 打ち手は外部評価（被リンク・指名検索）の側にある。

## やること

1. **公開は週2本を維持する。**上げない。理由は上表
2. **無駄な11%を減らす。**301（5%）はレガシーのリダイレクトスタブ48本、
   404（3%）と「リクエスト失敗」（3%）は要調査。1日3.86回しかない中での11%は小さくない
3. **sitemap-all.xml の存在意義を再検討する。**sitemap.xml と**URL集合が完全に同一**で、
   2026-07-30に再取得を促す目的で複製したもの。役目は終わっている
4. **需要側の打ち手を検討する。**記事の量ではなく、外部からの参照を得る方向
5. **月次で `scripts/index_check.py --refresh` を回し、DISCOVERED の本数の推移を追う。**
   上表の試算どおり減っていくかが検証になる

## 反証条件

- 週2本を維持しても DISCOVERED が減らない → 行列は FIFO ではなく、
  古いURLは恒久的に後回しにされている。試算の前提が誤り
- クロールリクエスト数が自然に増えていく → 需要が育っている。その時点でペースを再検討する
- 検出リクエストの割合が28%より下がる → 新規公開そのものを止めて行列の消化を優先する

**次回検証：2026-09**（クロール統計と index_status.json を同時に見る）

## 2026-08-09 追記：**「120日で95本消化」の試算は反証された。自然消化はほぼ起きない**

上の試算表は「検出能力 1.08本/日のうち 0.79本/日が行列の消化に回る」を前提にしていた。
8日後に実測したところ、**申請していない60本は8日で+1本しか入らなかった（0.125本/日）。
試算の 1/6 である。**この率だと60本の消化に**480日**かかる。

さらに悪い事実がある。`index_diff.py` の遷移集計で
**DISCOVERED → NEVER_SEEN が7本**出た。検出済みだったURLを、Googleが**認識から落とした**。

| 遷移 | 本数 |
|------|------|
| DISCOVERED → INDEXED | 19（うち19本が申請済み） |
| NEVER_SEEN → DISCOVERED | 13 |
| **DISCOVERED → NEVER_SEEN** | **7** |
| NEVER_SEEN → INDEXED | 2 |

**行列はFIFOではない。順番待ちですらなく、待っていると落ちる。**
`## 反証条件` の1つ目（「DISCOVERED が減らない → 行列はFIFOではない」）に該当する。

**この文書の結論のうち、生きているものと死んだものを分ける：**

| 記述 | 状態 |
|------|------|
| 公開ペースは週2本を維持する | ✔ **維持**。新URLを増やしても検出能力は増えない |
| 制約は能力ではなく需要側 | ✔ **維持**。応答91msでホスト正常なのは変わらない |
| 段階的にペースを上げる実験は不要 | ✔ **維持** |
| 「週2本なら0.79本/日が行列に回り120日で消化」 | ✘ **反証**。実測 0.125本/日、480日 |
| 「月次で DISCOVERED の推移を追えば検証になる」 | △ **不十分**。申請の効果と混ざるので、
  必ず `index_diff.py` で申請済み群と申請待ち群を分けて見ること |

**打ち手の変更：自然クロールを待つのをやめ、インデックス申請を標準手順に入れる。**
`agent/rule_changes.md`「2026-08-09」を参照。
