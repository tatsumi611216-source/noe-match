# 営業ソーシングツール 要件定義書

作成日: 2026-08-06 / ステータス: ドラフト（要レビュー）

## 1. 結論（実現可否）

**既存ツールをベースに構築可能。**

| 既存資産 | ソーシングツールでの転用先 |
|---|---|
| web-data-pipeline スキル（収集→保存→分析→HTMLレポートの汎用パイプライン） | 求人サイトの日次クロール・パース・レポート生成の骨格 |
| 定期実行の仕組み（Routine / cron 相当。SEOエージェントで運用実績あり） | 毎日のピックアップ自動実行 |
| Python スクリプト運用（scripts/ 配下、JSON キャッシュ・履歴管理の実績） | 分析・スコアリング・DB更新スクリプト |
| 差分キャッシュ・1件1ファイル方式のノウハウ | 「新着案件だけ取得」の日次差分運用 |

新規に作るのは「求人サイト向けの取得ロジック」「企業データベース」「カテゴリ分類ルール」「営業ステータス管理」の4点のみ。

## 2. 目的

企業が公開している求人を毎日自動収集し、カテゴリ別に分析した上で
**「採用ニーズが顕在化している企業」の営業リスト（企業データベース）** を作る。

- 求人を出している企業 = 人手不足・投資余力がある企業 → 営業アプローチの優先ターゲット
- 掲載カテゴリ・件数・掲載継続日数から、企業の課題とアプローチ角度を推定する

### 営業ターゲット（確定）: 採用・HR関連サービス

本ツールで売る商材は **採用・HR関連サービス（人材紹介／採用代行／ダイレクトリクルーティング等）**。
この場合、**求人を出している企業 = そのまま見込み客**であり、求人シグナルが直接の購買トリガーになる。
とりわけ「自力で採用できず苦戦している企業」が人材紹介・採用代行のコアターゲットになるため、
中小・地場を多く含むソース（ハローワーク）も主力として有効。

## 2.5 収集ソース戦略（規約クリーン前提）

大手有料媒体（doda／リクルート／ビズリーチ／リクナビ／マイナビ 等）は利用規約で自動収集を
明示的に禁止しており、本ツールの収集対象に**含めない**（会員ログイン先データの自動収集は
不正アクセス禁止法・偽計業務妨害のリスクもあるため）。Indeed の公開求人API（Publisher/Job
Search API）は2024年に廃止済みで、現存APIは雇用者側（求人を流し込む用途）のみのため利用不可。

採用HR営業に有効かつ規約クリーンなソースを以下の層で構成する。DBは `source_site` カラムで
複数ソースを混在管理できる。

| 層 | ソース | 役割 | 予算層カバー |
|---|---|---|---|
| 主 | 各企業の自社採用ページ（schema.org JobPosting 構造化データ） | 企業自身が機械可読で公開する求人。中〜大手を含む | ◎ |
| シグナル | プレスリリース（PR TIMES 等の公開情報） | 資金調達・増員・拠点拡大＝採用シグナルの先読み | ○ |
| 補完 | ハローワーク求人（公開データ） | 中小・地場を網羅。HR営業ではコアターゲット | △（HR営業では◎） |
| マスタ | 国税庁 法人番号公表サイト（オープンデータ） | 企業名寄せ・法人マスタの土台 | — |

## 2.6 優先度スコア（HR営業向け「採用の困り度」）

`companies.priority_score` を以下で算出する（scripts/score.py が実装）。
「採用に困っている＝人材紹介・採用代行の即ニーズ」が高スコアになるよう設計。

| 指標 | 意味 | 重み |
|---|---|---|
| 有効求人件数（対数） | 募集ポジションが多い＝採れていない | 高 |
| 平均掲載日数（上限180日） | 長く出続けている＝充足できず苦戦 | 高 |
| 直近7日の新規求人数 | 今まさに動いている＝アプローチ好機 | 中 |
| 募集カテゴリ数 | 複数職種で採用＝事業拡大・継続需要 | 中 |

## 3. 機能要件一覧

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F-01 | 日次収集 | 対象求人サイトの検索結果を毎日クロールし、新着・更新案件を取得 | 必須 |
| F-02 | 差分検知 | 前回データと照合し、新規掲載/掲載終了/継続日数を判定 | 必須 |
| F-03 | 企業名寄せ | 表記ゆれ（㈱/株式会社、全半角）を正規化し、同一企業の求人を1社に集約 | 必須 |
| F-04 | カテゴリ分類 | 職種カテゴリ（マスタ管理）にルールベースで自動分類。未分類は「その他」へ | 必須 |
| F-05 | 企業DB登録 | 企業・求人・カテゴリ・日次統計を SQLite に蓄積 | 必須 |
| F-06 | カテゴリ別分析 | カテゴリごとの案件数・新規数・掲載企業数の日次推移を集計 | 必須 |
| F-07 | 営業リスト出力 | 「新着求人あり」「未接触」等の条件で営業対象企業を抽出（ビューで提供） | 必須 |
| F-08 | 営業ステータス管理 | 企業ごとに 未接触→アプローチ中→商談→成約/見送り を記録 | 高 |
| F-09 | HTMLレポート | 日次サマリー（カテゴリ別グラフ・注目企業上位N件）を outputs/ に生成 | 高 |
| F-10 | CSVエクスポート | 営業リストを CSV で出力（他ツール連携用） | 中 |
| F-11 | スコアリング | 求人件数・掲載頻度・カテゴリから営業優先度スコアを算出 | 中 |
| F-12 | 通知 | 高スコア企業の新規検知時にレポートへハイライト表示 | 低 |

## 4. 非機能要件

| ID | 項目 | 内容 |
|---|---|---|
| N-01 | 実行頻度 | 1日1回（朝）。1回の実行は30分以内を目安 |
| N-02 | 取得マナー | robots.txt 遵守・リクエスト間隔を空ける・並行取得は控えめに |
| N-03 | データ保持 | 求人の生データはファイル保存（1件1ファイル）、DBは正規化データのみ |
| N-04 | 障害時 | 取得失敗はスキップしてログ記録。翌日の実行で自動リカバリ |
| N-05 | 運用コスト | 追加サーバー不要。既存のリポジトリ＋定期実行の枠内で完結 |

## 5. 法務・規約上の注意（重要）

- 大手求人サイト（リクナビNEXT・マイナビ・doda 等）は**利用規約でスクレイピングを明示的に禁止**していることが多い。対象サイトごとに規約と robots.txt を確認してから収集対象に加えること。
- 安全側の選択肢: ハローワークインターネットサービスの公開求人、Indeed 等の公式API、求人検索エンジンの公開フィード、自治体・官公庁の公開データ。
- 取得した企業情報は営業目的の社内利用に留め、第三者への再配布・再販は行わない。
- 個人情報（担当者名など）は収集対象にしない。企業単位の公開情報のみ扱う。

## 6. データベース要件

DB: SQLite（`sourcing/data/sourcing.db`）。スキーマは `schema.sql` を正とする。

| テーブル | 役割 | 主なカラム |
|---|---|---|
| companies | 企業マスタ（営業リストの本体） | 正規化企業名、業種、都道府県、URL、営業ステータス、初回/最終検知日 |
| job_postings | 求人案件（企業に紐付く） | 掲載サイト、サイト内ID、タイトル、カテゴリ、給与、勤務地、掲載期間、有効フラグ |
| categories | 職種カテゴリマスタ | カテゴリ名、分類キーワード（カンマ区切り） |
| sales_activities | 営業活動履歴 | 活動日、種別（架電/メール/訪問）、結果、次アクション |
| daily_category_stats | カテゴリ別日次統計 | 日付、有効案件数、新規案件数、掲載企業数 |
| crawl_runs | 収集実行ログ | 実行日、対象サイト、取得件数、新規件数、エラー数 |

ビュー:

| ビュー | 用途 |
|---|---|
| v_sales_targets | 営業対象リスト（有効求人あり×未接触/再アプローチ対象、求人件数降順） |
| v_category_summary | カテゴリ別の現在有効案件数・企業数サマリー |

## 7. 運用フロー（日次）

```
毎朝の定期実行:
  1. 対象サイトの一覧ページを取得（web-data-pipeline の手順）
  2. スクリーニング: 既知かつ内容不変の案件は除外（差分キャッシュ）
  3. 新規・更新案件のみ詳細取得 → data/raw/ に1件1ファイル保存
  4. パース → 企業名寄せ → カテゴリ分類 → DB更新（scripts/update_db.py）
  5. 日次統計を集計、HTMLレポート生成 → outputs/
営業時:
  6. v_sales_targets から対象企業を抽出（CSV出力可）
  7. 活動結果を sales_activities に記録 → 翌日以降のリストに反映
```
