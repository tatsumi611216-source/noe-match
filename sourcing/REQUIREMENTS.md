# 営業ソーシングツール 要件定義書

作成日: 2026-08-06 / ステータス: ドラフト（要レビュー）

## 1. 結論（実現可否）

**既存ツールをベースに構築可能。**

| 既存資産 | ソーシングツールでの転用先 |
|---|---|
| web-data-pipeline スキル（収集→保存→分析→HTMLレポートの汎用パイプライン） | 求人サイトの日次クロール・パース・レポート生成の骨格 |
| 定期実行の仕組み（Routine / cron 相当。SEOエージェントで運用実績あり） | 毎日のピックアップ自動実行 |
| Python スクリプト運用（scripts/ 配下、JSON キャッシュ・履歴管理の実績） | 分析・スコアリング・DB更新スクリプト |
| 差分キャッシュ・1件1ファイル方式のノウハウ | 「新着案件だけ取得」の日次差分運用 |

新規に作るのは「求人サイト向けの取得ロジック」「企業データベース」「カテゴリ分類ルール」「営業ステータス管理」の4点のみ。

## 2. 目的

企業が公開している求人を毎日自動収集し、カテゴリ別に分析した上で
**「採用ニーズが顕在化している企業」の営業リスト（企業データベース）** を作る。

- 求人を出している企業 = 人手不足・投資余力がある企業 → 営業アプローチの優先ターゲット
- 掲載カテゴリ・件数・掲載継続日数から、企業の課題とアプローチ角度を推定する

### 営業ターゲット（確定）: 採用・HR関連サービス

本ツールで売る商材は **採用・HR関連サービス（人材紹介／採用代行／ダイレクトリクルーティング等）**。
この場合、**求人を出している企業 = そのまま見込み客**であり、求人シグナルが直接の購買トリガーになる。
とりわけ「自力で採用できず苦戦している企業」が人材紹介・採用代行のコアターゲットになるため、
中小・地場を多く含むソース（ハローワーク）も主力として有効。

## 2.5 収集ソース戦略（規約クリーン前提）

大手有料媒体（doda／リクルート／ビズリーチ／リクナビ／マイナビ 等）は利用規約で自動収集を
明示的に禁止しており、本ツールの収集対象に**含めない**（会員ログイン先データの自動収集は
不正アクセス禁止法・偽計業務妨害のリスクもあるため）。Indeed の公開求人API（Publisher/Job
Search API）は2024年に廃止済みで、現存APIは雇用者側（求人を流し込む用途）のみのため利用不可。

採用HR営業に有効かつ規約クリーンなソースを以下の層で構成する。DBは `source_site` カラムで
複数ソースを混在管理できる。

### 確定した2トラック構成（起点リスト）

営業母集団を、性質の異なる2系統で構築する（DBは `is_listed` フラグで分離管理）。

**トラック①：上場企業（is_listed=1）**
- 起点: JPX 上場会社一覧（約3,900社・公開データ）
- 収集: 各社の採用ページから JobPosting 構造化データを取得。初回フルクロール → 以降は差分（`Last-Modified`/`ETag`・サイトマップ `lastmod` で変更社のみ再取得）
- 位置づけ: 確立企業で母集団が確定・網羅的。ただし人事が強く新規開拓の旨みは相対的に薄い

**トラック②：成長スタートアップ（is_listed=0）**
- 起点: 直近1年の資金調達ニュース（PR TIMES 等の「資金調達」リリース）＋ J-Startup（経産省）・主要VCポートフォリオの公開リスト
- 収集: 拾った有力スタートアップの採用ページから同じく JobPosting を取得
- 位置づけ: 「そこそこデカい未上場（シリーズB以上・従業員50〜500目安）」に母集団を絞れる。調達直後＝採用爆発の先読みで、HR新規開拓の本命

### 実測（2026-08-20・全業種79社の初回巡回）

GitHub Actions で 79社（ゲーム6・スタートアップ6・全業種67）を巡回した実測値。

| 指標 | 結果 |
|---|---|
| 接続成功 | 72社（うち13社は採用URLが外れて企業サイトから辿り直し） |
| 失敗 | 7社（403×4、429×1、タイムアウト×2）／robots.txt によるブロックは0社 |
| **求人を取得できた企業** | **1社（マネーフォワード・4件）= 79社中1.3%** |

**判明した前提の誤り:** 「採用ページに JobPosting 構造化データが無い企業は3〜4割」と
見積もっていたが、実測は逆で **ほぼ全社が取得できない**。原因は構造化データの不在だけでなく、
リンク発見が1階層・最大5リンクのため **求人一覧までは届いても求人詳細ページに到達していない**
点が大きい（JobPosting は詳細ページに置かれるのが一般的）。12ページ取得して0件の企業が複数ある。
唯一取得できたマネーフォワードは HRMOS（ATS）が一覧ページ自体に JSON-LD を出しているケース。

→ 対策として求人詳細ページへの到達経路を `scripts/job_discovery.py` に実装した（下記）。

### 求人詳細ページへの到達（job_discovery）

採用トップに構造化データが無い場合、次の順に詳細ページを探す。1社あたりの取得は
26ページを上限とし（robots/sitemap/一覧/詳細の全取得を含む）、相手サイトへの負荷を固定する。

| 経路 | 内容 |
|---|---|
| top | 起点ページ自体に JobPosting がある（HRMOS等のATSはここで取れる） |
| sitemap | robots.txt の `Sitemap:` 行 →`/sitemap.xml` 等の順に探索。sitemapindex は1段再帰し、子は求人らしい名前を優先。列挙URLから「求人詳細らしいURL」を選別して最大12件取得 |
| link2 | 採用トップ → 求人一覧（最大6ページ）→ 求人詳細（一覧1ページあたり最大4件）と2階層辿る |

「求人詳細らしいURL」の判定は、パスに求人系の語があり、かつ末尾セグメントが
`jobs` `careers` `index` のような一覧を示す汎用語ではないこと（＝個別のID/スラッグが付く）。
数字IDで終わるURLを最優先で開く。どの経路で取れたかは巡回ログの「経路」列に出る。

### ソース早見表

| 層 | ソース | 役割 | 対象トラック |
|---|---|---|---|
| 起点 | JPX 上場会社一覧 | 上場企業マスタ | ① |
| 起点 | 資金調達リリース（PR TIMES 等）／J-Startup／VCポートフォリオ | 有力スタートアップ抽出＋調達シグナル | ② |
| 取得 | 各企業の自社採用ページ（schema.org JobPosting 構造化データ） | 実際の求人を取得（両トラック共通の中核） | ①② |
| マスタ | 国税庁 法人番号公表サイト（オープンデータ） | 企業名寄せの土台 | ①② |
| 補完(任意) | ハローワーク求人（公開データ） | 非上場・非調達の中小をカバー（後日追加候補） | 追加 |

**カバレッジ上の留意点（②の運用）:**
- 資金調達の窓は「直近1年」を初期値とするが、シリーズC/D は調達後も長く採用が続くため **18ヶ月ローリング**への拡張を推奨
- ①②とも「採用ページに JobPosting 構造化データが無い企業」は一定数あり（体感3〜4割）、その場合は素のHTMLパースにフォールバックする（Phase 2で実装）
- ①②のどちらにも入らない「黒字・無借金で採用継続中の中堅中小」は取りこぼす → 必要ならハローワークを補完層として追加

## 2.6 優先度スコア（HR営業向け「採用の困り度」）

`companies.priority_score` を以下で算出する（scripts/score.py が実装）。
「採用に困っている＝人材紹介・採用代行の即ニーズ」が高スコアになるよう設計。

| 指標 | 意味 | 重み |
|---|---|---|
| 有効求人件数（対数） | 募集ポジションが多い＝採れていない | 高 |
| 平均掲載日数（上限180日） | 長く出続けている＝充足できず苦戦 | 高 |
| 直近7日の新規求人数 | 今まさに動いている＝アプローチ好機 | 中 |
| 募集カテゴリ数 | 複数職種で採用＝事業拡大・継続需要 | 中 |

## 2.7 データベースとして販売できるか（競合と優位性）

### 結論
**生の企業リスト販売は非推奨（コモディティ・強い先行者あり）。**
**「HR営業向け・採用ニーズインテリジェンス（日次更新）」としてなら勝ち筋あり。ただしニッチで刺す前提。**

### 競合状況（要注意）
- **HRog（フロッグ）**: 2014年から求人媒体150社以上・40億件超を収集し、人材業界向けに求人企業リスト＋市場分析を販売。**ほぼ同一事業の先行者。**
- **Musubu（Baseconnect）**: 140万社の企業DBで営業リスト販売、利用11万社超。
- **帝国データバンク / 東京商工リサーチ / uSonar**: 企業マスタの権威。マスタ単体は完全コモディティ。

### 差別化の置き所（生リストではなくシグナル層）
1. **データ出所の違い**: HRogは有料求人媒体が主。本ツールは自社採用ページのJobPosting＋調達＋公開マスタ。→ **有料媒体に出さず自社サイトだけで採用する企業（＝ベンチャー）を拾える**（HRogの穴）。
2. **掛け合わせのインテリジェンス**: 調達タイミング × 採用の困り度 × 規模（資本金/従業員）× グループ構造 × 外資、を日次更新。「いつ・誰に当たるか」を提示。
3. **クリーンな出所＝販売要件を満たす**: データ外販には出所の適法性・個人情報排除が必須。規約クリーン設計がそのまま商品要件。
4. **堀は時系列蓄積**: 掲載継続日数＝困り度は履歴をためて初めて効く。公開データ自体は模倣可だが、継続運用の履歴は模倣されにくい。

### 販売するなら満たすべき条件
- 出所がすべて適法（本ツールの方針どおり）／個人情報（担当者名等）を持たない
- 精度・鮮度の担保（重複排除・名寄せ・日次更新・欠損率の明示）
- ニッチ特化（特定業界 or ベンチャー特化）で HRog と正面衝突を避ける

## 2.8 上場子会社・外資系の取得方法

### 上場子会社・グループ会社（is_subsidiary / corporate_relations）
「上場子会社」には2義あり、両方を拾う:
1. **上場している子会社**（親会社を持つ上場企業）: JPX一覧の企業のうち、EDINET有報で親会社が開示されているものに is_subsidiary=1 を付与。
2. **上場企業傘下の（非上場）子会社**: 採用余力があり狙い目。**EDINET API で親会社の有価証券報告書（書類種別120）を取得 →「関係会社の状況」から子会社・関連会社を抽出** → companies に親子リンク付きで登録 → 各社の採用ページをクロール。
- corporate_relations テーブルにグループ構造を蓄積。v_group_targets で「傘下で採用中の企業」を営業リスト化。

### 外資系（is_foreign_affiliated）
単一のオープンデータでは外資フラグを完全には取得できないため、合わせ技で判定:
- **東洋経済「外資系企業総覧」**（有料）: 権威データ。ライセンス購入で精度を担保。
- **JETRO の外資系企業関連データ / 国立国会図書館の外資系名鑑**: 公開の補完。
- **EDINET 有報**: 外国親会社・外国資本比率の開示から判定。
- **商号・採用ページのヒューリスティック**: 「〜ジャパン」「〜日本法人」「K.K.」「合同会社＋外国名」、英語採用ページ、代表者国籍など。
- 判定基準は経産省定義（外国投資家が1/3超所有＋筆頭出資10%以上）を採用。foreign_ownership_pct に比率を保持。

## 5. 法務・規約上の注意（重要）

- 大手求人サイト（リクナビNEXT・マイナビ・doda 等）は**利用規約でスクレイピングを明示的に禁止**していることが多い。対象サイトごとに規約と robots.txt を確認してから収集対象に加えること。
- 安全側の選択肢: ハローワークインターネットサービスの公開求人、Indeed 等の公式API、求人検索エンジンの公開フィード、自治体・官公庁の公開データ。
- 取得した企業情報は営業目的の社内利用に留め、第三者への再配布・再販は行わない。
- 個人情報（担当者名など）は収集対象にしない。企業単位の公開情報のみ扱う。

## 6. データベース要件

DB: SQLite（`sourcing/data/sourcing.db`）。スキーマは `schema.sql` を正とする。

| テーブル | 役割 | 主なカラム |
|---|---|---|
| companies | 企業マスタ（営業リストの本体） | 正規化企業名、業種、都道府県、URL、営業ステータス、初回/最終検知日 |
| job_postings | 求人案件（企業に紐付く） | 掲載サイト、サイト内ID、タイトル、カテゴリ、給与、勤務地、掲載期間、有効フラグ |
| categories | 職種カテゴリマスタ | カテゴリ名、分類キーワード（カンマ区切り） |
| sales_activities | 営業活動履歴 | 活動日、種別（架電/メール/訪問）、結果、次アクション |
| daily_category_stats | カテゴリ別日次統計 | 日付、有効案件数、新規案件数、掲載企業数 |
| crawl_runs | 収集実行ログ | 実行日、対象サイト、取得件数、新規件数、エラー数 |

ビュー:

| ビュー | 用途 |
|---|---|
| v_sales_targets | 営業対象リスト（有効求人あり×未接触/再アプローチ対象、求人件数降順） |
| v_category_summary | カテゴリ別の現在有効案件数・企業数サマリー |

## 7. 運用フロー（日次）

```
毎朝の定期実行:
  1. 対象サイトの一覧ページを取得（web-data-pipeline の手順）
  2. スクリーニング: 既知かつ内容不変の案件は除外（差分キャッシュ）
  3. 新規・更新案件のみ詳細取得 → data/raw/ に1件1ファイル保存
  4. パース → 企業名寄せ → カテゴリ分類 → DB更新（scripts/update_db.py）
  5. 日次統計を集計、HTMLレポート生成 → outputs/
営業時:
  6. v_sales_targets から対象企業を抽出（CSV出力可）
  7. 活動結果を sales_activities に記録 → 翌日以降のリストに反映
```
